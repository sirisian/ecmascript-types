# Additive numeric interval arithmetic

The built-in `+` and `-` operations on two numeric ranges compute an enclosure of coordinate addition or subtraction. They require one agreed numeric endpoint type, retain that type, and use exact endpoint arithmetic followed by checked representation. This closes the old Number narrowing path for addition and subtraction. Binary multiplication and division remain a separate audit because product domains and divisor singularities need additional decisions.

## Required outcomes

- Preserve wide integer values and a stable result domain. Autocomplete must not advertise a typed endpoint that runtime changes to Number.
- Require an explicit numeric domain agreement; do not select a union member or promote numeric families from endpoint magnitudes.
- Enclose exact mathematical sums/differences, with checked integer/rational representation and outward floating rounding.
- Give empty images, omitted bounds, explicit infinity, signed zero and decimal cohorts deterministic representations.
- Specify validation, admission, effects and publication order. Neither success nor failure grants reference authority or extends liveness.

## Result domain

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Rebuild every result as Number | Convenient for small literals, but typed endpoints disappear and values above 2^53 change. | Rust ranges retain their endpoint type; their API does not provide interval addition. | Cheap arithmetic after lossy conversion; typed consumers need new checks. | Violates exact values and endpoint contracts. | **Reject.** These are reproduced failures. |
| Choose the left type, the wider type, or a value-dependent promotion | Mixed inputs appear convenient; reversing a sum or changing a magnitude can change result representation. | Rust numeric arithmetic normally requires explicit conversion; Boost chooses a declared interval base. Neither supplies this proposal with a promotion lattice. | Additional polymorphic result paths and conversion guards. | Left bias loses symmetry; width alone does not compare binary, decimal, rational and metadata domains. | **Reject.** |
| Join domains and choose a union member separately for each computed endpoint | Honest union signature, but no unique carrier for a sum of uint8 and uint16, or a full union range. | This proposal's reified unions are not Rust's single endpoint parameter or Boost's base type. | Selection branches, representation-dependent ICs and ambiguous metadata hooks. | A union describes alternatives, not a numeric conversion operation. | **Reject.** |
| Require one identical concrete numeric type, including metadata | A wrong mixed-type guess fails; an explicit range construction/conversion establishes the desired coordinate domain. The result has one stable type. | Follows typed-coordinate arithmetic and declared interval-base principles, without claiming an existing Rust interval operator. | Common same-type tag guard and fixed range layout; no per-member enumeration or shape mutation. | Preserves representation and full endpoint admission; no new reference permission. | **Recommend.** |

Supported concrete types are the real numeric bases covered by [range-scaling.md](range-scaling.md), including their full metadata parameterizations. Inspect each operand's stored/inferred domain and present endpoint types. A concrete domain and every present endpoint must agree by type identity. A union, nonnumeric domain, or disagreement throws TypeError, even if the result would be empty or unbounded.

`any` is an erased domain: its actual endpoints still contribute their concrete types. An endpoint-free `RangeFull<any>` contributes no carrier. Thus a full-any operand beside a byte range produces `RangeFull<uint8>` for either operator, while two full-any operands produce `RangeFull<any>`. An erased range whose present endpoints are uniformly uint8 can participate with a byte range; an erased mixed range cannot. The result carries the agreed concrete domain, or `any` only when neither operand supplies a type. This selects a domain for a newly computed range, not a conversion of either input.

For erased inputs, three alternatives were considered. Always defaulting to Number repeats type erasure; requiring annotations even when all endpoints establish one type needlessly rejects gradual code; choosing the uniquely agreed domain uses existing runtime tags and gives typed consumers a stable result. A full-any operand supplies no conflicting promise, unlike a typed full range or an explicit union. Rust's static generics have no direct erased-domain analogue. The selected rule needs only fixed guards, preserves source values and liveness, and never examines endpoint magnitudes to select a type.

## Arithmetic and metadata

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Use ordinary scalar wrapping or nearest rounding | Familiar scalar operators, but the computed bounds can exclude the exact image or reverse order. | Rust distinguishes checked from wrapping arithmetic. Boost requires exact or directed arithmetic for enclosure. | Fast native path; wrong result is not an optimization. | Unsound bounds, independent of later type checks. | **Reject.** |
| Promote on overflow, saturate, or manufacture infinity | Fewer errors, but a typed result changes domain or silently loses a finite bound. | Rust's saturating operations are explicit; interval libraries make overflow policy explicit. | More result representations or saturation branches. | Saturation can shrink the image; promotion violates the selected domain. | **Reject.** |
| Exact integer/rational results, outward floating bounds, checked failure | Stable result type; fractional/range limitations fail visibly, floating bounds may widen. | Rust checked addition/subtraction supports explicit overflow failure; Boost is the closer enclosure precedent. | Two exact calculations, native checked/directed fast paths where equivalent, operand-size fallback for large integers. No range shape mutation. | Preserves the exact image/enclosure and endpoint type. | **Recommend.** Reuse the scaling representability rules. |
| Invoke arbitrary declared scalar operators on endpoint pairs | Appears to reuse overloads, but a non-monotone body can have interior extrema absent from every endpoint result. | Neither Rust operators nor Boost's ordered arithmetic assumptions prove arbitrary user bodies enclose an interval. | Arbitrary calls and checking/effect complexity; no generally sound constant-cost algorithm. | Cannot guarantee an enclosure merely from endpoint calls. | **Reject as automatic lifting.** A custom interval operation needs an explicit enclosure contract. |

Addition uses lower-plus-lower and upper-plus-upper. Subtraction uses left-lower minus right-upper, then left-upper minus right-lower. Compute with exact mathematical values; do not first convert a factor or endpoint through Number. For exact results, a bound is open when either contributing bound is open. If floating rounding moves a lower endpoint down or an upper endpoint up, close that moved bound. Integer results must fit; rational results must fit after normalization. Finite floating overflow throws RangeError; binary subnormals and the existing decimal minimum adjusted exponent rules are the same as scaling.

These operators compute built-in coordinate arithmetic. Declared scalar operator bodies are not executed, and endpoint metadata is not treated as a program for inferring a different coordinate space. Equal full parameterizations remain the promised domain and every manufactured endpoint passes their existing admission. A units library can operate on base-coordinate bounds and separately derive the result quantity type, as the existing NumberBounds definitions do. Distinct parameterizations require an explicit common coordinate domain. This additive rule does not imply that multiplying two quantities retains their unit type; that is part of the nonlinear audit.

Stripping metadata would silently discard the promised type; unioning metadata cannot select conversion or validation order; trusting old endpoint validation would admit new values without checking them. All are rejected. Requiring the agreed full type and admitting new bounds retains autocomplete and ordinary boundary errors. Rust primitive arithmetic has no equivalent arbitrary validation hook, so this is the proposal's existing admission rule. At most two admissions use ordinary dispatch and do not invalidate range shapes. Admission cannot change the computed mathematical value, binary zero sign, or decimal coefficient/exponent; a change throws RangeError and an existing hook exception propagates.

## Empty, omitted and infinite bounds

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Compute bounds even when either input is empty | Can return a nonempty sum or overflow irrelevant crossed endpoints. | Empty-set arithmetic supplies no pairs; Rust's range API keeps emptiness distinct from iteration direction. | Wasted arithmetic/admission calls. | The image of an empty operand must be empty. | **Reject.** |
| Return a new zero-based empty range | Predictable printed zero, but zero may fail metadata or be unavailable in the domain. | Boost has an explicit empty representation; this proposal uses existing endpoint/bound forms. | Extra manufacture and admission. | An empty result should not need an unrelated admissible anchor. | **Reject.** |
| Validate both operands, then copy the first empty operand | Wrong kinds still fail consistently; existing endpoint payloads/bounds stay inspectable. | Mathematical empty-image rule; representative choice is specific to this API. | Fixed checks, no new endpoint admission. | Preserves emptiness and source values; no liveness change. | **Recommend.** Prefer the left if both are empty, and use the agreed result domain. |

An omitted contributor supplies no bound: omit that result endpoint without inventing an infinity or calling admission for it. This preserves the existing conservative unbounded-side rule. Deriving a tight bound by analyzing every possible infinity inhabitant would need a different extended-set arithmetic contract; fabricating a present infinite endpoint would change reflection and fail in integer carriers. The selected fixed presence test preserves shapes and the ordinary distinction between explicit infinity and absence. Rust's one-ended ranges support the distinction but do not determine interval arithmetic; Boost's real-set bounds are not identical to this proposal's observable infinite endpoint values.

For two present contributors, finite plus infinity and same-sign infinity addition preserve a present signed infinity in the agreed type. Subtraction reverses the right infinity sign before that rule. Opposite infinities in addition, or like infinities in subtraction, are indeterminate and throw RangeError at that endpoint calculation. Returning NaN would create an unordered range; dropping the bound or returning a full range would turn a definite invalid bound operation into an apparently successful result; selecting one infinity is arbitrary. Those alternatives are rejected. A checked failure is explicit to the caller, needs only tag/sign guards, and preserves the invariant that every published endpoint is ordered. Rust floats normally return NaN for such scalar arithmetic, which is precisely why ordinary scalar arithmetic cannot determine this range contract; Boost's infinite limits do not cover all of these represented singleton-infinity inputs.

The omitted-bound rule deliberately does not enumerate implicit inhabitants or evaluate nonexistent endpoint pairs. Consequently a full-any operand can leave an unknown bound where two explicitly supplied incompatible infinities would fail. This difference follows the observable distinction between missing information and an actual endpoint computation. Empty-image selection precedes those computations, so an empty extreme-infinity operand remains empty without an irrelevant indeterminate operation.

## Representation and failure order

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Short-circuit zero operands as identity, or cache admission from a prior call | Fewer hooks, but failures/effects depend on an optimization and new sums reuse old decimal representation unexpectedly. | No Rust interval addition identity shortcut specifies these hooks. | Potentially fewer calls at the cost of value/effect-sensitive guards. | This is a new endpoint computation, unlike the explicitly defined scaling identity. | **Reject.** |
| Compute both raw endpoints before admission, or admit in arbitrary order | Later arithmetic failure can suppress earlier required hook effects; callers cannot predict failure precedence. | Ordinary left-to-right construction is a useful analogy; Rust has no corresponding metadata transaction. | Possible scheduling freedom, but observable hooks prevent reordering. | Loses deterministic failure state. | **Reject.** |
| Validate, choose empty image, compute/admit lower, compute/admit upper, publish | Deterministic first error and effects; a failed call leaves source ranges reusable. | Extends explicit checked arithmetic with this proposal's boundary rules. | Fixed work and no rollback journal, source mutation or IC invalidation. | Every published endpoint is admitted; borrowed locations still require liveness checks. | **Recommend.** |

Operand expressions run in ordinary left-to-right order before the range operation. Inspect the left range's internal domain/endpoints, then the right's; no public property getter, ordinary coercion, or custom ordering operator runs. Establish the common type before checking emptiness. After the empty exits, calculate/admit the lower result before calculating/admitting the upper. Propagate the first error immediately. No partially constructed result is published, and user hook effects already performed are not rolled back. Adding a zero interval performs ordinary admission on both manufactured endpoints.

An exact cancellation produces positive binary zero. For zero-only contributors, addition yields negative zero only from two negative zeros; subtraction yields negative zero only from negative zero minus positive zero. Other exact zero sums/differences are positive zero. Always using the host arithmetic result is rejected because it can first narrow a wide operand; making lower exact cancellation negative merely because it is a lower bound introduces an unnecessary representation distinction. The selected rule agrees with familiar scalar zero-sign addition at exact zero, requires one sign check, and does not affect numerical ordering or liveness. Rust's floating representation provides a limited analogy, not this exact rational calculation policy.

Binary addition/subtraction of decimal endpoints uses the reduced coefficient/exponent of the computed result. Preserving the left cohort would be operand-order dependent; selecting a new preferred exponent from both source cohorts would add a representation policy absent from exact rational arithmetic. Both are rejected here. The reduced rule is deterministic and commutative for exact addition, uses the existing constructor, and has no shape effects. Rust has no built-in decimal cohort contract. Scaling identity/reflection keeps its separately specified cohort-preservation rule.

## Verification and remaining scope

The corpus covers every supported real numeric family, wide values, all four bound combinations, erased/union/full domains, empty images, finite overflow, exact outward enclosure, signed zeros, explicit infinities, metadata order and failure recovery, generic factories and reference liveness. Module checks cover imported wide ranges and float128 enclosure across suspension.

Multiplication/division still use the legacy Number implementation and are not certified by this repair. Complete static range-result typing, extended-family iteration, custom interval enclosure declarations and the existing mixed plain BigInt construction restriction also remain open. The broader checking and inference gates are unchanged.

Primary sources: [Rust Range](https://doc.rust-lang.org/std/ops/struct.Range.html), [Rust checked addition/subtraction](https://doc.rust-lang.org/std/primitive.i32.html#method.checked_add), and [Boost interval arithmetic](https://www.boost.org/doc/libs/latest/libs/numeric/interval/doc/interval.htm). Boost's inclusion and directed-rounding requirements are close analogies; its closed real-set intervals and infinity policies are not copied wholesale.
