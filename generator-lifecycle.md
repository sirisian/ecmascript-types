# Generator operation results

A generator's R describes its body's return obligation. It does not describe every completed result produced by its methods. After the body completes, another `next()` normally produces `{done:true,value:undefined}`. An external `return()` without an argument can also complete without a body payload. Rejecting such a result because R is string confuses the two contracts.

Define `GeneratorCompletionValue(R)` as the canonical union of `IteratorCompletionValue(R)` and `undefined`. This is specification notation, not a source operator or global binding. `Generator<Y,R,N>` retains its nominal identity and body obligation. Its `next`, `return` and `throw` read signatures produce `{done:false,value:Y} | {done:true,value:GeneratorCompletionValue(R)}`; the async counterparts produce a Promise of that result. These are normal-result contracts: a method can instead throw or reject, and `return` can yield from a finally block before it completes.

`next` keeps its optional N input, synchronous `return` its optional R input, and `throw` its optional gradual input. Async return accepts direct R, Promises and callable thenables as raw requests, then admits the resolved value against optional R; see [async-generator-return-admission.md](async-generator-return-admission.md). The self-iteration hook returns the same generator instantiation, preserving Y/R/N. An optional R already admits undefined, so structural conformance may express that same input as optional `R|undefined`; this does not add an input value or equate the nominal generators. Both structural views retain the completed output projection. In particular it does not turn a void input into any.

`IteratorResult<Y,R>` and the generic structural iterator protocols retain their existing written contracts. A hand-written iterator can promise a string terminal value on every successful call. A generator with body R=string cannot make that promise: it fits an exhaustion-aware `Iterator<Y,string|undefined,N>` instead. R=void still supplies the gradual discard view, and explicit undefined stays precise. Ordinary `Iterable<Y>` remains usable when the terminal value is ignored.

## Choosing the result contract

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
|---|---|---|---|---|---|
| Keep R alone and reject exhausted results | A second legal next unexpectedly fails; autocomplete incorrectly promises a string after done. | Rust's experimental Coroutine rejects resume-after-completion, but ECMAScript defines it. | No useful shape saving; causes failed receiving checks. | Contradicts ordinary generator exhaustion. No liveness benefit. | **Reject.** |
| Make every completed generator result any | Exhaustion works, but useful concrete completion information disappears and wrong guesses move to later boundaries. | Weaker than Rust's separate Yield/Return associations and TypeScript's explicit return parameter. | Same result shapes; unnecessarily loses specialization opportunities. | Conservative but discards established R. | **Reject.** |
| Track exact lifecycle state in every reference's type | Attractive first-call precision; aliases, mutation and escaped calls invalidate the user's guess. | Rust's exclusive mutable access is a much stronger alias constraint; its coroutine contract is also different. | Requires state guards, invalidation and deoptimization across aliases, beyond existing result ICs. | No general stable typestate proof exists here; cannot extend a reference across suspension. | **Reject as the default.** A future proven refinement is separate. |
| Add undefined to all structural IteratorResult declarations | Easy autocomplete rule, but hand-written precise protocols lose their contract. | Rust Iterator uses Option for exhaustion, without an arbitrary terminal payload; that is not a rule for JavaScript structural objects. | No necessary allocation benefit. | Weakens explicitly written structural obligations. | **Reject.** |
| Project only generator operation completion to C(R) union undefined | Ordinary exhaustion works; users narrow both done and undefined before relying on a concrete payload. A wrong assumption fails at its typed receiving boundary. | Follows ECMAScript lifecycle semantics while retaining Rust-like separation of yielded and body-return components. | Reuses canonical unions, result shapes and existing admission/IC guards; no per-instance typestate or wrapper. | Preserves body/input contracts, generic identity, effects and reference liveness. | **Recommend and implement**, independently of implementation effort. |

An unresolved R carries the existing deferred completion projection inside the union. Substitution closes it before ordinary canonicalization. Do not permanently replace open R with any (**reject: loses later precision**) or leave raw R in the result (**reject: reintroduces the void property failure**). This reuses the generic design in iterator-completion.md, including capture identity and idempotence. There is no new deferred operator or persistent cache state.

## Member reads, delegation and structural conformance

Dot access, a known computed String key, optional access, object-pattern extraction and the actual self-iteration Symbol use the same read contract. A shadowing Symbol or unknown key does not gain intrinsic identity. Extraction does not bind this. No getter runs to compute a type, and ordinary mutable lookup still runs at execution. The result projection grants neither readonly storage nor permanent method identity.

The terminal contribution of nominal `yield*` is the generator completion projection: a passed generator may already be exhausted. Structural delegation reads its selected result shape and retains a precise string terminal contract when that shape supplies one. A fresh-looking call does not establish a stronger contract by itself; retaining the old R-only answer for such syntax is **rejected** because replacements and aliases would make equivalent uses disagree. Rust's mutable receiver analogy cannot establish the required ECMAScript identity. This conservative choice changes type queries, not object shapes or scheduling.

Structural conformance is derived from these operation signatures. Keeping the old unconditional `Generator<Y,R,N> implements IterableIterator<Y,R,N>` claim is **rejected** because R=string would silently reintroduce the false promise through an interface. For optional return inputs, retain both equivalent spellings R and R|undefined in the declared structural view; rejecting the exhaustion-aware interface solely for that spelling difference is **rejected** because both inputs accept the same values. This is a generator declaration rule, not a general change to signature identity, member variance or readonly properties.

## External return request audit

The original result repair did not implement uniform external-request admission. Synchronous request admission and completion provenance are now specified in [generator-return-admission.md](generator-return-admission.md); the asynchronous queue/await portion is now specified in [async-generator-return-admission.md](async-generator-return-admission.md). The prior async dynamic request bypass before body entry is repaired. Async admission must also preserve provenance: an omitted external request propagated through a suspended body must not be mistaken for an explicit body `return undefined` under R=string. A finally block that actually returns a new value must still satisfy the body obligation. The linked synchronous rule also distinguishes completed delegate replacements from body returns.

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
|---|---|---|---|---|---|
| Rely on final body-return enforcement | Some states bypass the body; omitted close can fail only after cleanup. | Rust has no replaceable external return method. | Cheap but inconsistent between states. | Does not enforce requests on unstarted/completed generators and conflates body and external completions. | **Reject.** |
| Check every async operand as raw R before enqueue | A Promise resolving to R is rejected despite ordinary async assimilation; autocomplete would hide a useful operation. | TypeScript AsyncGenerator accepts return values or PromiseLike values; Rust supplies no matching rule. | Cheap immediate check, but trades away valid behavior. | Uses the wrong value stage and cannot model native rejection/cleanup. | **Reject as the general async rule.** Sync raw admission is appropriate. |
| Await before enqueue, then admit | Easy conceptual boundary but later requests can overtake the pending return; wrong guesses reorder cleanup. | Neither Rust resume nor ordinary ECMAScript async-generator queues use this pre-enqueue await. | Adds a second asynchronous scheduling path and state coordination. | Changes request order and native await/thenable effects. No suspension grants reference authority. | **Reject.** |
| Rewrite the completed payload or widen the body's R | Appears to avoid errors but hides the invalid request and weakens body diagnostics. | Neither Rust body return typing nor ECMAScript payload semantics supports this. | May add wrappers/conversions and conceal useful guards. | Changes values or admits invalid body returns. | **Reject.** |
| Admit sync requests after validation and before state change; admit async resolved values at their existing queue/await stages | Predictable sync failures; async failures follow native rejection and cleanup paths. Autocomplete can describe the raw async assimilable input separately from the resolved obligation. | ECMAScript distinguishes suspended-yield unwrapping from draining-queue return resolution. Rust is only an analogy for keeping input and body-return components separate. | Reuses existing state transitions and awaits; requires internal completion provenance, not user-visible wrappers or new result shapes. | Preserve queue order, catches/finally, omission, captures, erasure and liveness; a failed awaited admission must follow that stage's abrupt path. | **Recommend**, independently of work required. Both stages are implemented; async delegation preserves the native distinction between the awaited result object and its unawaited done-true value. |

The async implementation must also distinguish an external completion that propagates unchanged from a body or delegate that replaces it. Preserve provenance through normal finally blocks and suspension; do not attach authority to an equal primitive value. At a suspended async yield, admission failure after native Await follows the throw-resumption path and can reach catch/finally. In the draining queue it rejects that request and continues draining. These stages cannot promise identical state rollback. Specify delegate return replacement, thenable rejection, omission versus explicit undefined, validation precedence and reference invalidation together before implementation.
