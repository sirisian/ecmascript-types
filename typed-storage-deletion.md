# Deletion and removal from typed Array storage

An owned typed Array retains initialized elements throughout its published extent. Direct deletion of a protected indexed position throws `TypeError`, including through an `any` alias or `Reflect.deleteProperty`. The backing contract, not the alias or current occupancy, determines protection: all canonical array indices for growable homogeneous storage, indices below a fixed extent, and positions in the tuple backing's permitted index domain. A missing position in that domain is still protected. Noncanonical keys, symbols, and fixed nonpositions keep ordinary property behavior. In particular, the string key `"-0"` is an ordinary property, distinct from index `0`.

Static proof continues to report the existing early error. An unresolved receiver or key keeps runtime timing, including ordinary property-key conversion and its effects. Refusal neither removes a location nor invalidates a reference. The ordinary descriptor's `configurable` flag does not override this type rule.

## Direct deletion decision

| Direction | Ergonomics | Prior art, including Rust | Real-engine performance | Correctness | Other and decision |
|---|---|---|---|---|---|
| Leave a hole or make the position implicitly optional | Indexed reads and autocomplete still promise the declared element type; a mistaken delete changes later reads | Ordinary JS permits holes; Rust Vec maintains initialized elements | Requires hole-aware representations and IC checks | Violates the existing no-holes and invariant-location commitments | Rejected; optional storage would be a separate feature |
| Replace with a default | Delete appears successful while the property remains; function and symbol elements need another rule | Rust can explicitly replace a value; replacement is not deletion | May execute default code and allocate copies on a delete path | Changes delete semantics and cannot cover types without defaults | Rejected; explicit assignment already expresses replacement |
| Compact the array or shorten it when deleting the last element | A property operator unexpectedly moves other positions or changes length | Rust remove and pop are explicit operations, not property deletion | Compaction can cost O(length) and move indexed values | Fixed extents, tuple domains, and reference identities need operation-specific checks | Rejected; use the existing removal methods |
| Refuse deletion in the protected domain, independently of occupancy | An immediate error identifies the operation; removal methods remain discoverable | Closest to initialized storage with explicit removal APIs; Rust lacks JS reflection | Constant homogeneous-domain guard, no hole transition or new shape | Preserves the promised backing and reference contracts and matches existing early errors | Selected; ordinary nonpositions remain ordinary properties |

## Removing intrinsic tails

`pop`, `shift`, and shrinking `splice` must still remove positions. Simply exempting their deletes is unsafe: deleting the last own element before a final nonwritable-length failure leaves a hole. Shrinking splice also executes replacement conversions or setters after its ordinary tail-deletion loop, so even eventual success does not justify exposing an uninitialized extent to those callbacks.

| Direction | Ergonomics | Prior art, including Rust | Real-engine performance | Correctness | Other and decision |
|---|---|---|---|---|---|
| Allow every deletion while an intrinsic runs | Most successful examples work; callbacks inherit a surprising permission | Ambient mutation permission has no Rust equivalent | Cheap flag but invalid observable shapes can escape | Callback deletion and failed length updates leave holes | Rejected |
| Shrink length at each ordinary tail-delete step | Callbacks see length change earlier than the method's final length update | Rust truncation changes the initialized extent, but does not specify JS callback order | Cheap dense truncation, but repeated descriptor checks | Can preserve density with additional guards; changes when replacement callbacks see the shorter array | Rejected in favor of retaining the published extent until the specified length phase |
| Make the entire intrinsic transactional | A later failure appears to undo earlier element writes, unlike other array operations | Rust's exclusive borrowing is not a rollback guarantee | O(length) staging and hard-to-replay getters, setters and conversions; extra shape work | Cannot roll back independent effects or observations | Rejected; stronger semantics than removal needs |
| Defer all checks and removal to the final length update | Simple rule, but a known nonconfigurable tail would fail after replacement effects | Ordinary JS checks those descriptors earlier; Rust lacks such descriptors | Small plan, final truncation | Preserves density but unnecessarily changes failure precedence | Rejected; retain the original deletion-point descriptor checks |
| Check tail removability at its ordinary step; retain locations until final truncation | Callback reads and references see a complete published extent; earlier writes remain on failure | Initialized-prefix reasoning resembles Vec; descriptor/effect ordering remains JS-specific | O(1) plan plus ordinary descriptor work; dense fast paths may fuse effect-free work without changing observations | Preserves initialized storage, prior checks, and removal identity timing | Selected independently of implementation effort |

After the ordinary argument processing and existing mutation-plan validation, a shrinking intrinsic on owned typed Array backing records its published length, backing contracts, fixed extent, and proposed final length. Its reads, movement writes, species work, and replacement effects keep their order. Each ordinary trailing deletion step checks the current plan and the existing own descriptor's configurability, but retains the element and its identity. This deferral applies only to indices leaving the planned extent. A deletion of a surviving position, for example from a damaged sparse source, still follows the direct-delete refusal.

At the final length update, recheck the plan and perform normal typed length truncation. Nonwritable length refuses before any removal; earlier movement and replacement writes remain. An earlier tail-descriptor refusal retains all deferred tail locations. Final truncation rechecks descriptors because callbacks may have changed them. It retains the ordinary descending deletion rule: a barrier leaves length at one past the barrier, preserves lower positions, and retains any already completed higher removals. A requested nonwritable length is applied as the ordinary algorithm requires. The final synchronous truncation exposes no intermediate hole to user code. This is not whole-operation atomicity.

Only actual removal invalidates an element reference. Surviving references continue to name their locations and see moved or replaced values. Shortening does not itself release capacity or relocate storage. Later regrowth creates new locations and cannot revive removed references.

## Overlapping required object properties

An Array can also acquire an object contract such as `{"1": uint8}`. Removing index `1` from its sequence does not erase that independent required property. Its deletion refusal is a truncation barrier, including on an otherwise untyped Array. Restore length to one past the barrier before propagating the original `TypeError`, apply requested length writability, and retain completed higher removals. Intrinsic tail preflight checks this protection at the ordinary deletion step, before replacement effects. A property contract acquired later is checked during final truncation.

| Direction | Ergonomics | Prior art, including Rust | Real-engine performance | Correctness | Other and decision |
|---|---|---|---|---|---|
| Let the sequence operation override the required property | An existing object view loses a property it still advertises | Neither Rust field access nor JS nonconfigurable properties justify erasing another contract | Cheap removal but breaks optimized property assumptions | Violates the required-property and reference contracts | Rejected |
| Reject all overlapping-contract resizes up front | Safe removals above the required property become unavailable | Rust has no directly equivalent structural object/array overlap | Simple coarse guard | Safe but stronger than either contract requires | Rejected; preserve valid truncation |
| Retain the property's refusal and restore the truncation boundary before propagating it | The required property survives; failure state follows the familiar descriptor-barrier rule | Closest JS analogy is a nonconfigurable tail barrier; Rust has no direct analogue | Existing descending truncation and identity work, no new shape | Preserves both contracts and reports the language error instead of a host assertion | Selected; does not undo completed higher removals |

## Reentry decision

| Direction | Ergonomics | Prior art, including Rust | Real-engine performance | Correctness | Other and decision |
|---|---|---|---|---|---|
| Use the original geometry after a conflicting callback resize | A callback's independent result can be overwritten by stale work | Ordinary JS tolerates many mutations; Rust excludes overlapping mutable borrows | Few guards, but invalidation assumptions become unreliable | Can remove or write positions under stale backing assumptions | Rejected |
| Retry or roll back the outer method | Getters/conversions may run twice, or earlier effects appear lost | Neither JS nor Rust collection mutation supplies general callback rollback | Replays arbitrary code and needs extensive saved state | Independent effects and reference invalidation cannot be undone | Rejected |
| Reject when the recorded length or backing differs, retaining effects | A deterministic conflict identifies the stale operation; independent work survives | The initialized-storage analogy applies, not Rust's borrow-checking mechanism | Constant snapshot checks on effectful paths; no receiver shape change | Preserves backing contracts and existing reference rules | Selected; value-only and capacity-only changes do not themselves cancel the plan |

Check before and after each intrinsic write, after its lookup/conversion effects and before its own property definition, at each deferred deletion, and before final truncation. Scope the write check to that receiver, key, and execution context; invoked callbacks and nested methods are independent operations. Restore the scope on abrupt completion. Earlier ordinary errors keep precedence, including a read's bounds failure after its getter independently shrinks the array. No comparison promises a lease across user code: an unchanged current snapshot is not a history check, and ordinary value writes remain observable.

## Scope

This closes direct deletion and owned-Array removal publication for the established backing representations. Sparse incoming admission and existing accessor replacement remain separate audit tasks; callback tests using currently permitted existing accessors do not settle that policy. General proxy/array-like backing and unsupported tuple sequence representations remain deferred. Existing proxy prohibitions are retained. Bounded tests do not close the broader conformance gates.

Primary references: [Rust Vec guarantees, remove, pop and truncate](https://doc.rust-lang.org/std/vec/struct.Vec.html), [ECMAScript pop](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-array.prototype.pop), [shift](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-array.prototype.shift), and [splice](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-array.prototype.splice). Rust's exclusive borrow model limits the analogy to callback visibility; this proposal uses its own runtime reference-liveness rules.
