# Resizable-buffer view lifetime

A byte view describes a buffer and byte addresses, not the identities of owned array elements. A fixed Span, viewed SoA or placed allocation is **out of bounds** while the buffer no longer covers its recorded extent. Access throws TypeError during that interval. Regrowth covering the extent restores access, including through previously acquired references, whether or not an access was attempted while it was out of bounds. Discarded bytes follow ArrayBuffer's zero-fill rule; recovery does not restore their former values. Actual ArrayBuffer detachment is permanent and is checked independently, even for an empty extent.

This resolves conflicting wording: the existing Views example explicitly restores `fixed.length` after regrowth, but the surrounding prose called shrinkage detachment. Keep the example's recovery rule and distinguish the two states. This is a deliberate decision, not a conclusion drawn solely from what the interpreter already does.

A fixed Span reports length zero while detached or out of bounds and its original length when covered again. A tracking Span derives its length from the current buffer; a missing index remains an out-of-range access. Growth does not relocate the logical byte addresses, even if an engine moves the physical allocation. SharedArrayBuffer only grows, so this shrinkage state is absent; its existing concurrency and access-order rules still apply.

A reference through a fixed view retains that view's complete extent requirement. A class element retained from that view and a nested placed field retain the enclosing checks too; keeping an early field does not bypass a missing later byte of the recorded extent. A class element from a tracking view also requires its own element extent. These checks apply before field reads, writes and value copying. A detached value copy already completed is independent. A separately constructed byte view has its own extent; this does not remove an owned source's allocation-generation obligations.

This rule does not revive an owned Array or SoA element removed and later replaced, or a window invalidated by relocation of its owned source. Those operations concern element identity or the source allocation. Buffer views deliberately describe reusable byte addresses. Their types and autocomplete show the same element contracts after recovery; no new lifetime type or recovery method is introduced. A type annotation cannot prove that the current extent is present.

View construction rejects an actually detached buffer, including a zero-count or tracking Span. Bounds and argument checks retain their existing order. Failed resize attempts do not change bounds themselves; effects performed while evaluating their arguments remain observable. Checks must use the current state after intervening user code. A getter that shrinks and regrows before the next access permits recovery; one that throws propagates its error. Earlier effects and completed field writes are not rolled back when a later access fails. A failed access does not poison the view or initialize a failed destination.

## Lifetime alternatives

The valid direction must settle regrowth without an intervening read, actual detachment, references and values uniformly, preserve owned-source invalidation, and allow runtime bounds checks without a live-reference count.

| Direction | Ergonomics / autocomplete / wrong guess | Prior art, including Rust | Real-engine performance | Correctness / liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Permanently invalidate every fixed view on shrink past its extent | Simple once taught, but contradicts the existing recovery example; a reusable parser must reconstruct views. Autocomplete does not reveal a spent view. | Rust disallows conflicting mutation while a borrow is used; that is not a runtime invalidation policy. ECMAScript byte views instead test current bounds. | Needs range history or weak view/range registration at shrink, plus an invalidation bit/epoch; engines can optimize it without user-object shape changes. | Can be made safe and consistent, but changes the proposal's explicit recovery outcome. | Reject: no identity promise for raw bytes justifies permanent revocation. This is viable, not rejected because it needs more work. |
| Poison only on an attempted out-of-bounds access | Adding logging or a caught read changes whether later reads work; signatures cannot explain it. | Neither Rust's borrow rule nor ECMAScript's current bounds supports access-dependent lifetime. | Adds mutable state and guards; no IC advantage. | Identical resize histories give different recovery depending on observation. | Reject the observer-dependent outcome. |
| Recover views but permanently invalidate references through them | A fresh borrow works where an old one fails despite the same displayed type and bytes. | Rust has a different exclusive borrowing model; native ECMAScript views do not have this proposal's ref syntax. | Requires byte-removal history for references in addition to view bounds checks; shapes can stay unchanged. | Can distinguish locations from view objects, but imports owned-element identity into raw byte addressing without an existing promise. | Reject the unnecessary split. |
| Refuse shrinking whenever a live view/reference overlaps the removed range | Mutation fails at its source, but abandoned generators and long-lived parser views can prevent resizing indefinitely. | Closest to Rust's prohibition in intent, but runtime retention is not Rust's lexical proof. | Requires discovering/counting live borrowers; GC-dependent release affects resize success and adds maintenance costs. | Conflicts with the proposal's choice to check use without live-reference counting. | Reject. |
| Always use the current bounds for byte views and their references | Matches the worked example; failed accesses are recoverable. A wrong guess throws at access rather than reading unavailable storage. | Matches ECMAScript's buffer-witness checks. Rust is an analogy for checking access validity, not for revival or runtime aliasing. | Current length/detachment plus retained source guards; no resize history, per-view invalidation registry, new object shapes or IC families. Hoist only where intervening effects cannot change the facts. | Preserves byte-address meaning, actual detachment, owned-element identity and owned-source relocation checks separately. | **Choose independently of implementation effort.** Clarify the prose and repair bypasses. |
| Reject resizable buffers for fixed views and placement | Simple construction error, but removes the existing parser/storage use cases; autocomplete still advertises buffer forms. | Rust alone does not require banning a collector-backed runtime-checked view. ECMAScript supports resizable buffers. | Simplifies hot paths at the cost of capability. | Contradicts existing accepted construction and recovery examples. | Reject. |

## Retained nested values

| Direction | Ergonomics / autocomplete | Prior art, including Rust | Real-engine performance | Correctness / liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Check only the retained field/element's own bytes | A retained value succeeds while the same expression through its parent fails; the displayed type gives no warning. | Independent DataViews may have independent ranges; this is a nested borrow, not an explicit independent view. Rust does not allow a sub-borrow to waive its owner's validity. | Fewest comparisons; no shape benefit that requires this semantic difference. | Loses the fixed source's extent and any source-generation obligation. | Reject for retained nested values. Explicit independent byte views keep their own ranges. |
| Copy whenever a nested value is retained | Easy lifetime but silently loses write-through behaviour. | Rust distinguishes copying values from borrowing; copying is not a substitute for a requested borrow. | Adds allocation/copy work and changes aliasing; IC savings do not justify it. | Violates the existing ref/value distinction. | Reject. |
| Preserve enclosing guards plus the nested extent | Reading, writing and copying agree; ordinary completed value copies remain independent. | Rust's sub-borrows are a limited analogy; this proposal checks dynamically and allows aliases. | Retain compiler-owned source descriptors, flatten redundant checks in a real engine, and preserve ordinary receiver shapes/ICs. Guards can hoist across effect-free code only. | Keeps original source obligations without demanding historical invalidation for byte views. | **Choose independently of effort.** |

## Prior art sources and limits

- [ECMAScript IsTypedArrayOutOfBounds](https://tc39.es/ecma262/multipage/ordinary-and-exotic-objects-behaviours.html#sec-istypedarrayoutofbounds) and [IsViewOutOfBounds](https://tc39.es/ecma262/multipage/structured-data.html#sec-isviewoutofbounds) compare a buffer witness with a view's extent. They support recovery from temporary out-of-bounds status, not recovery from actual detachment. Their individual API error behaviour is not copied wholesale into Span.
- [Rust vectors and borrowing](https://doc.rust-lang.org/book/ch08-01-vectors.html) explain why using a reference across conflicting vector mutation is rejected. Rust supplies compile-time borrowing constraints; it does not settle this proposal's collector-backed, alias-permitting byte-view policy.
