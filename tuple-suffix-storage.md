# Storage for one rest with required suffix positions

A tuple with required fixed positions and exactly one unbounded homogeneous array rest has a unique assignment at a known length. In `[boolean, ...[].<string>, uint16]`, the first element is Boolean, the last is uint16 and every intervening element is String. An empty rest does not move the suffix into the rest's domain. The previous implementation incorrectly flattened the fixed suffix into the prefix and then used the first rest for later positions.

Retain the required prefix, the homogeneous rest and the required suffix as one complete contract. The minimum length is the sum of the two fixed widths. At length `n`, a suffix of width `s` starts at `n - s`. This is a length-derived assignment, not a partition chosen from current values. Fixed tuples and trailing homogeneous rests remain the special cases with no rest or no suffix.

## Decision: represent the domain

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
|---|---|---|---|---|---|
| Keep the first-rest approximation | Valid suffix and middle stores fail or use the wrong conversion; signatures mislead | Neither Rust tuples nor homogeneous slices discard declared field types | Small metadata but incorrect guards | Does not preserve declared positions | Rejected |
| Freeze the first observed partition as a fixed tuple | A rest unexpectedly loses its variable-length meaning after acquisition | Rust tuples are fixed, but that is not an analogy for this explicitly variable-length type | Simple fixed shape and IC guards | Invents an initial-length rule and unnecessarily prevents equal-type growth | Rejected |
| Give each index an independent union of possible types | Convenient stores can destroy the required relationship between positions | Rust enums can express alternatives, but independent fields do not preserve a whole-sequence constraint | Broad storage and value checks weaken layout specialization | A read approximation is not a writable backing contract; invariant references could gain authority | Rejected for storage |
| Retain prefix/rest/suffix and derive positions from the actual length | Declared suffixes work, including an empty rest; resizing has an explicit contract check | Rust tuple fields retain their types; Vec has one stable element type. Neither directly models a heterogeneous suffix that moves with length | Shape metadata plus length guards; homogeneous runs skip bulk per-element comparisons; no wrapper or per-index property map | Exact assignment for this subset, with survivor checks below | **Selected**, independently of implementation effort |

Overlapping acquired tuple and array obligations retain all complete domains. Their permitted lengths intersect, and each actual index has the intersection of its participating contracts at that length. A fixed extent can reduce this to fixed positions. It is incorrect to retain only the currently occupied indices or lose a suffix's alignment by flattening the conjunction. Existing backing established before or independently during admission remains authoritative.

## Decision: resizing and surviving locations

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
|---|---|---|---|---|---|
| Repartition by current values after each mutation | A location's type changes depending on nearby values, and an apparently valid method can retype aliases | Rust does not dynamically change a borrowed tuple field's type | Full scans, conversion effects, layout transitions and IC invalidation | Contradicts invariant references and current removal/relocation rules | Rejected |
| Allow retyping only when no reference is live, or invalidate all references | Permission depends on hidden alias state; ordinary assignment unexpectedly changes lifetime | Rust exclusivity is checked statically; runtime reference counting is not equivalent | Reference tracking and extra guards in real engines | Adds new authority or invalidation events not granted by the proposal | Rejected |
| Ban every length change for a suffix tuple | Predictable but even `[...[].<string>, string]` cannot grow | Rust's fixed tuples differ from this type's explicit variable-length domain | Cheap extent guard | Safe but imposes an unnecessary restriction on equal-contract positions | Rejected |
| Require SameType at every surviving index, plus the new length domain | Equal-type rest/suffix can grow or shrink; a wrong guess fails before element work in an intrinsic | Rust's homogeneous Vec retains one element type across resizing; stable field contracts motivate the invariant, while runtime liveness remains specific to this proposal | Compare declared boundary runs; no element reads, speculative conversion or reference census | Keeps every surviving location's declared type and existing identity rules | **Selected** |

A surviving index is one below both the old and proposed lengths. A direct indexed store or definition uses the resulting length to determine the destination type, and rejects a forbidden resize before value conversion. A length assignment applies the same check before deletion. Intrinsic mutation plans apply it before element work, then compare each moved source at the old length with its destination at the proposed length. Same-length replacement still uses the destination boundary. A plan is not a lease over subsequent setter, callback or proxy effects; ordinary later checks and nontransactional failure rules remain.

For example, `[...[].<string>, boolean]` normally cannot grow in place: the old final Boolean location would become String. `[...[].<string>, string]` can grow by `push` and can shrink without crossing its required minimum. Removed references remain invalid after regrowth; replacement of a surviving element does not remove its identity. No new reconstruction or retyping operation is introduced.

## Decision: static information when length is unknown

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
|---|---|---|---|---|---|
| Treat every index after the prefix as the rest type | Autocomplete omits possible suffix members and valid comparisons fail as disjoint | Rust tuple indexing has an exact fixed field; that analogy does not justify this guess | Cheap but unsound checker result | Claims a type the index need not hold | Rejected |
| Erase every such read to unknown | Avoids the wrong promise but loses useful alternatives and diagnostics | Rust requires explicit type structure rather than erasing known alternatives | Simple checking; fewer optimization facts | Conservative but unnecessarily imprecise for this exact subset | Rejected for required single homogeneous rests |
| Use the union of types that can occupy that index over permitted lengths | Autocomplete exposes genuine alternatives; a read does not authorize writes to all of them | Rust enum alternatives are only a partial analogy; Rust has no corresponding variable-length tuple index | Declaration-sized static unions; runtime storage stays exact and ICs still guard its shape/length | Preserves all possible reads while stores and references use the actual backing type | **Selected** |

Within established static positional-read analysis, for prefix width `p`, index `i >= p` may hold the rest type or suffix entries `0` through `min(i-p, s-1)`. Later suffix entries cannot reach that index at any permitted length. For a literal with a known length, use the exact position instead, including contextual generic-callable typing and numeric literal adaptation. Expanding a statically fixed spread can establish that length. An unresolved spread does not establish it. Existing nonliteral rest-key deferrals remain; this changes their covered peers' type domains without broadening that proof boundary. This increment does not claim complete contextual analysis for unknown spreads, generalized rests or type-level indexed access.

## Admission, methods and limits

Retained admission evidence supplies the selected element values and callable contracts. It supports ordinary stores, reflection, reference argument admission, value-class copies, and delayed publication without rereading elements merely to stamp storage. Numeric elementwise conversion uses the exact destination map. Search uses the union of complete backing domains, including an unoccupied rest; conjoined domains contribute their intersections over possible alignments. `with` checks its replacement against the actual position. Copy methods keep the existing policy: no fixed positional shape is invented for an unbounded rest result; a genuinely fixed combined domain can retain its guaranteed positions.

This closes the required single unbounded homogeneous rest with fixed prefix/suffix subset. Multiple rests, finite or nested rest operands and defaulted positions still need their full assignment representation. General proxy/array-like backing transport, reentrant adoption, descriptors that create holes, and sparse growth remain separate audits. In particular, an ordinary length increase or skipped-index store can create holes in existing homogeneous/rest storage. This increment neither treats those holes as valid initialized values nor introduces default filling. The survivor contract check is necessary for resizing, not a complete initialization algorithm. Rust Vec's requirement that newly exposed positions be initialized is useful prior art for that next decision, not evidence that JavaScript holes already satisfy this proposal.

Primary prior art: [Rust tuple fields](https://doc.rust-lang.org/reference/types/tuple.html) and [Rust Vec](https://doc.rust-lang.org/std/vec/struct.Vec.html). Rust's compile-time borrow discipline differs from the proposal's runtime reference liveness; it is not permission to add invalidation events here.

Conjunctions also support the finite non-singleton length domains of [defaulted no-rest tuples](defaulted-tuple-admission.md). A finite maximum alone must not flatten a conjunction to that one length.
