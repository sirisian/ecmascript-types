# Object-valued rests: prototype and descendant dependencies

General object-valued conversion planning remains incomplete; the bounded ordinary constructor extension below now supplies selected plans. Ordinary nominal tuple membership is now backed by the correlated prototype mechanism below. Recognizing an intrinsic numeric payload represented by an interpreter Object does not establish support for a nominal or structural Object destination. The complete heterogeneous-rest design remains the recommendation; this note specifies its next proof obligations rather than changing class membership.

## Original reproduced gaps

At engine262 commit `5f92785d37ecb497838c66e8b301188ede1a2677`, this converting boundary invokes the constructor twice and returns a sequence that is not a member of its annotation:

```js
let calls = 0;
class C { constructor(value: any) { calls++; } }
type T = [...[].<C>, ...[1].<string>, ...[].<boolean>];
const source: any = [1, "s"];
const admitted: T = source;
const result: any = admitted;
calls + "/" + String(result is T); // observed "2/false"
```

The required String cannot be consumed by the first rest. Removing its required count can legitimately let the greedy conversion select two C constructions, so constructor count alone is not the criterion.

Even a constructor-free successful admission needs more than retained Object identities:

```js
class C {}
type T = [...[].<C>, ...[].<string>];
const child: any = new C();
const source: any = [child, "s"];
const admitted: T = source;
Object.setPrototypeOf(child, null);
source is T; // observed false
```

The current nominal membership operation follows the object's prototype chain to the constructor's prototype. The example mutates that dependency without replacing either array element. A retained class Type Record or an earlier successful `is` is not evidence that this chain remains valid. These observations are discovery evidence, not accepted conformance outcomes. Neither defect is repaired by the numeric-source planning increment.

## General implementation boundary

The ordinary exact-class and tuple-membership mechanisms below identify fixed constructor/prototype dependencies, including inherited links. General nominal conversion and exotic backing must additionally distinguish their applicability and persistent evidence from observable Proxy or constructor-property operations. A prospective prototype change must leave all affected acquired sequence and child obligations valid before publication. A valid changed chain must establish dependencies on its new links. Replacement/removal must retire obsolete relationships; weak dependency handling must avoid retaining dead arrays through surviving children. Independently completed nested boundaries remain in force.

Conversion planning must reserve finite runs without invoking constructors or operators while searching. Constructor applicability, selected execution, and successful backed result are distinct facts. Retain operation observations; execute only the selected conversions in index order; propagate a selected failure without retry; revalidate earlier results and relevant backing after later user effects. General constructor signatures, specialization, proxy membership and metadata cannot be replaced by a blanket one-parameter constructor test.

Structural roles additionally need the selected property/callable/default obligations and their alias relationships. Do not infer a child's writable property contract merely from its observed value or silently broaden existing backing. Establish which evidence remains valid under child writes and which dependency must be checked. Metadata judgments require their existing effect discipline; unchanged ordinary properties are not a permanent cache key.

Validation must cover the two witnesses above, inherited prototype mutations, valid changes, unrelated changes, multiple parents and guards, replacement/removal, constructor failure and reentrancy, Proxy routes, and invariant references with independent removal/relocation liveness. Until that coherent domain is implemented and specified, keep these object destinations out of the pure scalar specialization. This is a staged implementation boundary, not a recommendation to reject all heterogeneous object tuples in the finished language.

## Implemented prerequisite: exact ordinary class boundaries

An exact receiving operation for a resolved, non-generic source class now retains the class prototype it requires. This includes ordinary checked and explicit conversions, parameter and return boundaries that perform them, and the corresponding elided annotation path. The target constructor must have a nonwritable, nonconfigurable own prototype identity; the instance's consulted prototype prefix must be ordinary. A completed conversion cannot publish an ordinary result whose chain misses that target, including when a converting constructor returned an unrelated object. Earlier constructor effects and abrupt completions retain their order.

```js
class C {}
const source: any = Object.create(C.prototype);
const admitted: C = source;
Reflect.setPrototypeOf(source, null); // false, before changing the link
source is C;                        // true
```

An exact class contract is retained on the received value, like an acquired storage obligation. It is not released merely because one binding goes out of scope or an alias changes: other typed aliases may still rely on it. Additional exact class admissions are conjunctive. This does not replace membership with a permanent brand; membership still follows the prototype chain, and an unadmitted object can still change that chain.

The dependency prefix includes the instance and each intermediate object whose outgoing link is needed to reach the target prototype. It excludes the target's outgoing link. Replacing a prefix with another valid one updates the dependencies; obsolete links immediately stop constraining that instance. Shared links remain constrained by other live instances. Weak instance/dependency links and cleanup prevent a surviving class prototype from retaining all admitted instances. The interpreter uses host weak references and finalization for metadata cleanup. This does not promise prompt release after an instance becomes unreachable: a surviving intermediate prototype can remain constrained until the weak instance is cleared. Programs must not rely on collection occurring before a prototype mutation. Finalizer records hold the target prototype weakly too, since a user property on that target can point back to the instance.

### Boundary of this milestone

Pure `is` does not acquire an obligation. Whole membership in `C | D` does not acquire an exact C obligation just because C was the successful alternative. Likewise, this helper is not permission to turn a heterogeneous rest's successful partition into permanent exact child contracts. At the exact-class prerequisite milestone, both original heterogeneous-rest witnesses remained open. The subsequent ordinary tuple-membership extension below closes the prototype invalidation examples; constructor planning remains open. An independently selected conversion to C is an exact receiving operation and completes its own obligation before a later enclosing failure.

General composite descendant acquisition, generic class specialization, unresolved or replaceable constructor prototypes, initial Proxy/exotic chains and metadata remain separate coverage. The next section covers correlated ordinary nominal tuple owners. Class construction without an exact receiving operation is not itself generalized by this milestone. Copies must acquire any required obligation on the actual published result; broader copy/adoption transport needs continued audit. Weak dependency metadata does not close portable evaluation-budget or cache-accounting gates.

## Implemented extension: ordinary nominal tuple membership

Successful owned-Array membership admission now retains an ordered guard for tuple patterns containing ordinary identity classes and the supported unparameterized scalar types. Required positions, finite runs and dynamic runs keep their counts; zero contributes no role. Nominal targets must be resolved, non-generic source classes with the permanent prototype identity described above. Value classes, metadata, unions used as element types, defaulted positions, unknown counts and initially exotic nominal evidence remain outside this extension. Stable fixed/prefix/suffix tuple shapes keep their declared location contracts and acquire the same nominal child protection.

```js
class C {}
class D {}
type T = [...[].<C>, ...[].<D>];
const child: any = new C();
const source: any = [child];
const received: T = source;
Reflect.setPrototypeOf(child, D.prototype); // true: the whole tuple still fits
Reflect.setPrototypeOf(child, null);        // false: no valid role remains
```

For `[a, b]` initially containing two C instances, changing only `a` to D is refused when `b` still requires C: `[D, C]` violates the ordering. Changing `b` to D succeeds. Thus this is a sequence promise, not an independently writable element union or an exact class stamp on each child.

The guard checks all acquired patterns against the same prospective values. A child may satisfy several classes, and two owners may use it differently. Matching one class in one successful assignment is not a permanent choice. Each affected owner re-evaluates its complete pattern using ordinary internal links with the proposed replacement substituted. These checks invoke no getters, conversion operators, constructors or Proxy traps. If no ordinary witness remains, the mutation fails before publishing the link or changing live dependencies. A valid change installs the new dependencies and retires obsolete ones. Negative roles do not need independent watchers: losing an unused possibility cannot invalidate the retained accepting witness; any change to that witness triggers a fresh whole-pattern check.

Element replacement and successful length publication refresh dependencies from actual owned data. Removing a child retires that owner's relationship, including when a failed truncation removes only a suffix. Another occurrence, another owner or an independently completed exact C boundary can still constrain it. Newly inserted or reflectively replaced children acquire the owner relationship without a hidden narrow class stamp at a broad projected location. Non-index property changes require no sequence scan; staged growth attaches new child dependencies at length publication rather than rescanning once per unpublished tail slot. No user code runs between these publications and dependency updates.

Admission revalidates retained values and their current ordinary roles before publishing a new guard. A prior getter can change a prototype; retaining the same Object identity does not validate the earlier class role. During later effectful scalar stores, the owner's guards already protect its published state, and the prospective converted sequence is rechecked after effects. A failed outer check preserves valid earlier effects and independently completed guards. Pure `is` acquires nothing.

Owner links and dependency paths are weak. The inspector is an engine operation that reads the currently retained owner; its finalizer record captures no array, element or constructor graph. The previous weak-cleanup timing decision applies to unreachable owners too. This does not change language-level weak-target eligibility or reference removal/relocation rules.

The original direct and inherited nominal-rest prototype witnesses are repaired for this ordinary family. ## Implemented extension: selected ordinary constructors

The required-String witness now returns `1/true`: one C construction, the retained String, and a result that satisfies T. A complete unchanged sequence still wins before conversion planning. Otherwise, declared counts reserve every required run before any constructor executes. Making the String run optional can legitimately select more C conversions under the existing leftmost-greedy rule.

[Rust From](https://doc.rust-lang.org/std/convert/trait.From.html) is intended for infallible conversions and points fallible conversions to TryFrom. This proposal's converting constructors can throw, so neither trait provides its implicit greedy ranking. [Rust variance](https://doc.rust-lang.org/reference/subtyping.html) remains a limited analogy for stable mutable-place types. ECMAScript's existing call and prototype publication order remains relevant; the runtime ordered guard is an additional proposal rule.

The implemented applicability proof is deliberately bounded. The destination is an ordinary identity class in the membership family above. It declares exactly one simple binding parameter with no optional marker, default, rest, reference, or destructuring. An unannotated or resolved any parameter is admissible. A resolved primitive parameter may admit an existing member or an intrinsically pure checked conversion; an ordinary identity-class parameter may admit an existing member. Read the parameter's retained declaration-context Type Record. Do not resolve its spelling in the caller's scope or infer any from an unavailable signature. Generic destinations, metadata/structural/union parameter checks, effectful parameter conversions, constructor defaults and general source/inbound operators are not classified by this proof.

A rejected pure parameter conversion supplies a retained failure fact, in the same input/run order as scalar failures. It does not preempt a viable complete assignment. A selected constructor executes once in input order; its actual parameter boundary remains checked even when the enclosing tuple uses an explicit cast. A selected throw propagates without trying another class or partition. A returned value outside the selected ordinary class throws TypeError. A successful selected conversion establishes its own exact class obligation, which survives later enclosing failure or removal from an array. Existing unchanged children acquire only the correlated owner guard.

After all selected operations, revalidate the complete sequence against every pattern. Later effects may validly repartition an earlier unchanged child, or may invalidate it despite retaining its identity. Refuse an invalid result before publishing the new Array and attach ordinary nominal dependencies before publishing a successful one. Source Gets remain operation-local retained observations. Stores also revalidate the consulted owner, length and backing after effects and preserve independent writes on failure.

Only the value supplied by the current insertion write can convert. A previously prepared private-tail entry, including a relocated element or an earlier inserted value, is already fixed for this write. Searching a later insertion must not reconstruct it or execute discarded conversion candidates. Movement retains SameType location checks and value identity; geometric failures still precede construction. Reflective data definitions use the same selected boundary conversion rules as existing scalar storage.

## Implemented extension: selected source and inbound operators

The ordinary nominal rest planner now retains source and inbound conversion declarations by their resolved target Type Record, including declaration identity, instead of using a display name as proof. ## Inbound conversion receiver context

The one-parameter inbound form runs with `undefined` as its receiver. Its parameter initializers and body therefore check `this` as `undefined`; lexical arrows keep that context. Nested ordinary functions, methods and classes use their own receiver rules, and leaving them restores the enclosing context. Source conversions with no parameter keep their source receiver. The inbound rule is independent of a static modifier, heritage or generic parameters. Names and captured type/value parameters still resolve in the declaration environment, and the result contract still applies.

Previously `operator C(value: any) { const answer = this === undefined; return new C(); }` was refused as a disjoint C/undefined comparison before evaluation. The runtime already supplied undefined. The checker now selects the inbound receiver before checking the element, so parameter initializers, body checking and nested contribution queries agree. This adds no runtime receiver allocation, shape change or inline-cache invalidation.

The alternatives were evaluated against the same five criteria:

| Direction | Ergonomics | Prior art, including Rust | Real-engine performance | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Keep the runtime receiver undefined and type it as any | Completion cannot offer a reliable receiver contract; wrong instance accesses fail late | ECMAScript permits gradual calls, but Rust's receiverless associated functions supply no arbitrary self | No new runtime work; discards useful checking facts | Avoids the false comparison error but leaves known invalid reads unchecked; no reference benefit | Rejected: erases an established fact |
| Prohibit every use of this in an inbound body | Stops mistaken instance access, but also rejects harmless checks and lexical arrows | Rust has no self binding in a receiverless associated function; JavaScript still has its ordinary this expression | Syntax/context check is cheap; no shape benefit | Could be coherent only with a new syntax restriction; adds no liveness protection over precise typing | Rejected: unnecessary language restriction |
| Create a target instance as receiver | Completion suggests usable instance fields before conversion has produced a result; constructor effects become surprising | Neither Rust receiverless construction nor ECMAScript strict calls creates this extra instance | Adds allocation, initialization and possibly user effects; changes shape and IC inputs | Conflicts with no-receiver conversion and result construction; introduces new obligations before success | Rejected: changes runtime semantics |
| Supply the target class object as receiver | Static members become available, but an instance-spelled inbound declaration gains unexpected static behavior | Some languages provide class methods; Rust associated functions use Self as a type, not an implicit class-object value | A retained class object can be cheap; changed call receiver may affect IC specialization | Conflicts with the existing undefined receiver and does not solve a reference problem | Rejected: no demonstrated benefit for changing the contract |
| Keep the undefined receiver and type it precisely | Completion offers no fictitious instance members; valid comparisons work and invalid property reads fail before effects | Closest to ECMAScript's strict receiver binding; Rust's associated-function distinction supports the absence of an instance, not the JavaScript undefined value | One compile-time receiver-context selection; no extra allocation, shape or call IC changes | Matches existing runtime calls, lexical arrow capture and checked result boundaries; references and liveness are unchanged | **Recommended and implemented** |

Keeping a class-instance static type while passing undefined is ruled out directly: it is the unsound mismatch being repaired. [Rust associated functions and methods](https://doc.rust-lang.org/reference/items/associated-items.html#associated-functions-and-methods) distinguish functions with a self parameter from those without one. [ECMAScript OrdinaryCallBindThis](https://tc39.es/ecma262/multipage/ordinary-and-exotic-objects-behaviours.html#sec-ordinarycallbindthis) preserves the supplied receiver for strict functions. Neither analogy supplies this proposal's conversion ranking; that policy is unchanged.

Coverage includes direct and contextual-arrow reads, nested arrows, explicitly typed captured returns, nested ordinary functions/classes, class expressions, derived classes, enclosing methods, generic captures, parameter initializers, and assignment/argument/return/explicit/rest boundaries. Static, generic-with-default and partial declarations have checking coverage; this does not complete their runtime conversion registration. Existing void inference is preserved: a participating block-bodied helper whose only return contribution is undefined infers void, and a typed consumer of that result is refused. Explicitly declaring its return as undefined tests the receiver contract without changing that independent rule.


## Generic conversion registration and declaration context

A generic class declaration retains its conversion declarations without applying its own parameters or their defaults. An application registers concrete targets and signatures on that specialization. An enclosing generic frame is not an application of a nested class, even when the parameter names agree. Existing declaration/body checking still runs; deferral does not excuse an invalid inbound receiver or an omitted required argument.

For example, `class C<T:type> { operator C(v:T) { return new C.<T>(); } }` must publish without demanding T. A later boundary at `C.<string>` resolves that specialization and uses its inbound operation. Both target-side forms use the concrete target, including when the annotation still holds the unspecialized constructor. Repeated lookup reuses existing materialization and does not replay static initialization. Constructor/source/inbound precedence, ordinary parameter admission and no retry after a selected failure remain unchanged.

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Apply defaults or implicit any while publishing | Merely declaring a required generic fails or silently supplies a different contract; completion misstates the application | Rust generic defaults do not make every declaration an application | Eager specializations and static effects for unused classes; needless cache entries | Changes parameter obligations and effect timing; no reference benefit | Rejected |
| Treat any ambient generic frame as this class's application | Nesting a class or reusing T changes its meaning unexpectedly | Rust scopes generic parameters to their declaring item; its nested items do not capture function parameters as this proposal can | Cheap frame test but invalid specialization keys and cached metadata | Confuses enclosing captures with own arguments and can bind the wrong declaration | Rejected |
| Never register generic conversions | Completion advertises an operation that valid applications cannot execute | Rust's generic conversion implementations are usable for valid concrete types | Saves metadata by dropping a required feature; no acceptable IC benefit | Refuses valid conversion contracts | Rejected |
| Resolve targets only after entering a conversion body | Wrong guesses run user effects before the operation's applicability is established | Rust type checking is not a precedent for speculative runtime conversion bodies | Loses reusable applicability data; extra user calls and late failures | Too late for selection and required failure precedence; no rollback of reference-invalidating effects | Rejected as observable semantics; internal laziness is allowed if required timing is preserved |
| Register on the class's own specialization and consult the actual target | Completion and explicit applications agree; required arguments and concrete signatures remain visible | Rust's parameter scoping and From<T> support typed application and target identity, within the limits below | Reuse constructor/prototype metadata and specialization caches; no extra instance or per-conversion user-object shape | Retains declaration identity, required arguments, static-effect order and independent liveness checks | **Recommended and implemented for the covered ordinary class path** |

Materialization must also retain where the declaration came from. Resolving an imported target in the importing scope can capture an immutable import binding instead of the exporting module's mutable local. A caller's generic parameter or private scope can similarly replace the intended context.

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Use the converting caller's context | Moving a conversion into another function or module changes captured names and can turn a valid write into a const error | Rust declaration scope supplies no caller-dependent name lookup; JavaScript closures retain lexical scope | Avoids capture storage but produces invalid cache/IC assumptions | Breaks lexical binding identity and captured generic contracts | Rejected |
| Retain only the lexical environment | Ordinary names work while type/value parameters, private names or realm-created objects can still be wrong | Rust has no JavaScript realms/private-name environment; lexical closure analogy alone is incomplete | A smaller descriptor omits facts needed for correct specialization | Incomplete declaration capture and caller restoration | Rejected |
| Retain declaration lexical/private environments, generic bindings, realm and script/module; restore the caller on every exit | Moving the call preserves meaning; completion refers to the declaration's types and names | JavaScript lexical scope is the direct analogy; Rust parameter scoping reinforces binding identity without defining this runtime mechanism | Share a captured descriptor owned weakly by the class; cached specializations avoid rebuilding it at each conversion; no user-object shape changes | Preserves declaration captures, realm-sensitive allocation and normal/abrupt restoration; references still validate at their own boundaries | **Recommended and implemented for conversion-triggered materialization** |

[Rust generic parameters](https://doc.rust-lang.org/reference/items/generics.html) are scoped to their item; nested items do not automatically inherit an enclosing function's parameters. This proposal supports captured parameters, so the analogy establishes binding identity rather than a ban on capture. [Rust From](https://doc.rust-lang.org/std/convert/trait.From.html) describes a conversion to Self from T; it does not specify JavaScript class materialization, runtime effects or this proposal's competing conversion forms.

The covered paths include required/defaulted type parameters, value parameters, nested and same-name parameters, source and inbound conversions, stored applications, derived classes, class expressions, imported declarations, separate Scripts, Function/eval, private capture and foreign inputs/targets. The implementation explicitly marks a class's own specialization instead of inferring it from an ambient frame. Declaration-context materialization restores lexical, variable, private, generic, realm and script/module state after completion or failure.

This increment does not complete generic rest planning, static/partial registration, general non-rest overload/result admission, or declaration-instance cache identity. Escaped generic class families and other materialization entry points remain separate coverage. General effectful/composite parameter checks, constructor overloads/defaults, metadata/value-class transport and the broader completion gates remain open.


## Evaluated generic class families

A generic class factory must keep each evaluation's captures and class identity. The source declaration plus own argument types is insufficient: two calls evaluating the same `class C<T>` can capture different values. A specialization cache keyed only by that source node made two factory conversions return `a/a` instead of `a/b`. Separately, direct construction through an escaped family lost its enclosing type parameter. Conversion-triggered materialization already captured that context; the other application paths need the same declaration context.

The required properties are: stable repeated applications within one family; distinct evaluated families; correct lexical, generic, private and realm captures; caller evaluation of supplied arguments; declaration evaluation of defaults and constraints; precise recursive-application identity; no completed cache entry after failure; preserved selected-case, partial-extension and reflection identity; and unchanged reference liveness.

| Direction | Ergonomics, completion and wrong guesses | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Source node plus arguments, using the caller's context | Factory results can read another invocation's captures; moving a call changes meaning despite unchanged declarations | Rust scoped generic items are not dynamically evaluated JavaScript class factories | Small key but invalid captured-environment and constructor assumptions undermine specialized ICs | Fails family identity and captures; no reference benefit | Rejected |
| Disable specialization caching | Repeated applications can produce different constructors and replay static effects | Rust stable instantiated types do not justify a new runtime type object on every access | Repeated class/prototype allocation and polymorphic IC churn | Breaks established identity and single-initialization behavior | Rejected |
| Cache by captured values or a serialized environment | Equal current values can merge unrelated families; mutable captures make identity change unexpectedly | Rust type identity is not arbitrary closure-value equality | Expensive traversal, retention and invalidation; getters cannot safely be invoked for key construction | Cannot represent binding identity reliably and can execute forbidden effects | Rejected |
| Family identity plus arguments, retaining the declaration context | Factory results keep their own captures; completion and reflection follow stable concrete applications | JavaScript class/closure evaluation supplies the direct identity model; Rust supports scoped type arguments but not dynamic factory identity | Weak family-owned specialization tables and canonical argument keys preserve stable constructors, shapes and IC reuse; no extra user-object properties | Satisfies the listed requirements while keeping reference checks independent | **Recommended independently of implementation effort** |

[ECMAScript ClassDefinitionEvaluation](https://tc39.es/ecma262/multipage/ecmascript-language-functions-and-classes.html#sec-runtime-semantics-classdefinitionevaluation) creates a class scope, constructor and prototype for an evaluation. Extending that identity to a generic family's applications is this proposal's design choice. [Rust generic parameter scope](https://doc.rust-lang.org/reference/items/generics.html#items.generics.syntax.scope) keeps parameters within their declaring item and excludes automatic capture by nested function-body items. This proposal allows such captures, so Rust supplies a binding-scope comparison rather than an equivalent runtime factory mechanism.

A forward alias and the class that later initializes its lexical binding must agree on the same family identity. Therefore runtime class records carry an opaque declaration-instance identity through interning, applications, inherited contracts, partial additions and reflection. A class expression without an outer declaration binding introduces its own identity. Reapplying a specialized constructor keeps the originating family. No source-text matching or latest-evaluated-constructor fallback may establish a family cache hit.

Written arguments resolve in the caller before defaults, constraints and class construction enter the retained declaration context. The existing shared argument-record binder supplies named arguments, packs, defaults and constraints; there is no separate class-only interpretation of those inputs. Recursive work is indexed by family and arguments, and records the fresh constructor before static initializers run. Failure removes only that application from the active table. Successful results are published after required extension application; completed user effects remain observable.

The broader completion gates remain open. This increment does not complete general effectful conversion planning, every class/decorator or metadata transport, arbitrary symbolic class templates, inference convergence, portable budget accounting, or final full-suite verification.
