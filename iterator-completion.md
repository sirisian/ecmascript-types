# Iterator completion values

A completion contract and a completed result's `value` are separate. Define `IteratorCompletionValue(R)` as `any` when R is exactly `void`, and R for other established value types. An open parameter or deferred computation retains this operation until substitution determines its operand. This is a specification operation, not a new global type or source operator.

`IteratorResult<T,R>` is `{value:T, done:false} | {value:IteratorCompletionValue(R), done:true}`. Its shorthand still defaults R to `void`. Thus a discarded completion is gradual, while explicit `undefined` remains precise. A read without narrowing can become gradual when the completed arm is gradual; narrowing `done === false` recovers T. An ordinary `{value:void}` remains uninhabitable, and the yielded T is not rewritten. The operation does not distribute a discard interpretation into arbitrary written unions or other type constructors.

The same result is used by `next`, optional `return` and optional `throw`, with the existing Promise wrapper for async protocols. `return` still has its optional R input, `next` its optional N input, and `throw` its gradual input. Normalizing a result does not widen those input contracts. Generator identity retains its original Y/R/N arguments. `IteratorResult<T,void>` and `IteratorResult<T,any>` have the same structural result, but the corresponding full protocols can differ because their `return` inputs differ.

A generator body's written return obligation is also unchanged: this implementation admits bare return/fallthrough at written R=void and rejects a non-undefined returned value, including a gradual value at runtime. This result-view repair does not convert R=void to R=any on the generator itself. Inferred undefined completion remains undefined. Ordinary function void rules are unchanged.

## Choosing a completion representation

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
|---|---|---|---|---|---|
| Keep `{value:void,done:true}` | Ordinary completion fails admission; a typed Promise callback cannot observe it. Wrong guesses can stall the caller's expected callback path. | Rust's unit is inhabited; its uninhabited types are not a model for successful completion. | No useful representation saving; causes failed checks. | Confuses a discarded contract with an impossible value property. No liveness benefit. | **Reject.** |
| Reinterpret every discarded completion as undefined | Attractive completion autocomplete but claims an absent value even for replaceable or hand-written protocols. | Rust `Iterator::next` returns `Option<Item>`; it does not expose JavaScript's arbitrary terminal payload. | Same shapes, but false precision can justify invalid check elision. | The discard view does not establish method identity or a particular runtime payload. | **Reject.** Use explicit undefined when it is established. |
| Add a special discarded property kind | Can prohibit reads while allowing result construction, but users must learn a new property rule. | Neither Rust unit nor TypeScript void is the same as a new ECMAScript property category. | Adds property admission, reflection and cache distinctions. | Would require new rules across structural subtyping, reads, writes and generic substitution. | **Reject for this problem.** |
| Replace every R, including concrete R, with any | Easy to implement, but loses useful terminal information and accepts wrong guesses. | Weaker than Rust coroutine completion and TypeScript's distinct yield/return components. | No necessary runtime saving; discards specialization opportunities. | Erases established contracts without a liveness reason. | **Reject.** |
| Map only discarded R=void to a gradual completed-value contribution | Completion works; autocomplete retains Y after narrowing and concrete R when supplied. A gradual completed value pays at its next typed receiving boundary. | Closest to a discarded result view while retaining ECMAScript's actual payload. Rust `CoroutineState<Y,R>` separates yield and completion, but is experimental and does not define JavaScript discard semantics. | Reuses existing result shapes, union checks and IC guards; no wrapper or per-result tag. | Keeps body return obligations, input contracts and receiving checks separate. Grants no reference authority or extended lifetime. | **Recommend and implement**, independently of work required. |

## Generic substitution and self-iteration

An unresolved R cannot simply stand for the completed value: specialization at void would produce an uninhabitable field again. Carry the unary completion operation as an existing deferred Type Record over that specific operand, preserving declaration identity. Substitute the operand and reduce it through the same rule. Reapplying the completion operation to its own open result is idempotent; do not grow a new deferred layer at every delegation. Do not cache by the spelling R or create persistent runtime state. Closed aliases, captured closures, interface members and published results must agree with direct application. Reflection of an open operation follows existing deferred-record reflection; there is no callable global constructor to resolve.

| Direction | Ergonomics and autocomplete | Prior art | Real-engine performance | Correctness and reference liveness | Other / decision |
|---|---|---|---|---|---|
| Normalize once and leave an open R unchanged | Looks precise until `R=void` breaks an otherwise valid specialization. | Rust associated computations retain their operands rather than replacing them by a similarly named parameter. | Small immediate cost, incorrect specialization. | Loses the operation and can confuse declaration identities. | **Reject.** |
| Turn every open R into any permanently | Avoids void failures but never recovers concrete completion precision. | Weaker than Rust's instantiated associated types or TypeScript generic result substitution. | Cheap, but prevents specialization even when the answer closes. | Conservative but unnecessarily erases known later contracts. | **Reject.** |
| Retain the operation through existing deferred substitution | Closed instances agree with direct spelling; wrong concrete guesses still fail. | Rust projections provide a partial analogy; this is a built-in value-view computation, not a trait lookup. | One internable unary type computation per operand, with existing substitution/cache accounting; no object-shape cost. | Preserves operand identity and existing capture scopes, with no effect on reference liveness. | **Recommend.** |

`IterableIterator<T,R,N>` and its async counterpart preserve all three arguments through their self-iteration hook. Ordinary `Iterable<T>` keeps its shorthand discard contract. Losing R/N on the self hook would make equivalent direct and delegated uses disagree. Reject keeping that loss merely to share an implementation helper: Rust's shared item association motivates consistency, while JavaScript still requires ordinary hook lookup. Preserving the arguments changes type queries, not runtime shapes, allocation or aliasing; it is the recommended direction.

Nominal generator `yield*` uses `GeneratorCompletionValue(R)`, the union of this completion view and undefined, for its terminal contribution; see [generator-lifecycle.md](generator-lifecycle.md). Structural delegation obtains the same contribution from the selected result shape. Async-from-sync continues to assimilate its terminal value; real async delegation and an explicit async return retain their existing, separate assimilation stages. No getter, iterator, callback or Promise job runs to compute the static type. Receiving checks retain effects, failed state and reference-liveness rules.

## Scope and subsequent audit

This change repairs completed-value representation. It does not establish runtime intrinsic identity from a member name, widen void inputs, alter body return enforcement, install wrappers, change Promise scheduling, or repair all generator lifecycle contracts. Repeated completion for non-void R is now covered by generator-lifecycle.md. Synchronous external return admission is specified in [generator-return-admission.md](generator-return-admission.md); the async queue/await stages remain a separate admission audit. A protocol result view alone is not proof of which intrinsic method will run.

Primary references: [ECMAScript GeneratorResumeAbrupt](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-generatorresumeabrupt), [Rust CoroutineState](https://doc.rust-lang.org/std/ops/enum.CoroutineState.html), [Rust Iterator](https://doc.rust-lang.org/std/iter/trait.Iterator.html), and [TypeScript 5.6 iterator return checking](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-6.html#strict-builtin-iterator-checks-and---strictbuiltiniteratorreturn). Rust's coroutine API is experimental; Rust unit is a value, whereas this proposal's void admits none. TypeScript's erased checks and strict built-in undefined completion are not a runtime admission rule for arbitrary mutable ECMAScript protocols. Performance comparisons above are design reasoning, not benchmark results.

## Next lifecycle decisions

The preceding completion-representation increment recorded two unchanged baseline probes. A generator with R=string returns a string once, then normal ECMAScript exhaustion supplies undefined; the existing precise result view rejects that second result. A dynamic external `return("terminal")` before a written-void generator starts returns the supplied payload without entering the body. These are separate from completed-void representation.

For non-void exhaustion, the actual directions are: keep the current rejection (**reject**, contradicts normal ECMAScript use with no shape or liveness benefit); make every completed result any (**reject**, erases concrete R and autocomplete precision); track each generator's exact lifecycle in its type (**reject as the general rule**, mutable aliases and replacement make a stable guarantee unavailable, and state/IC/deoptimization cost is substantial); or include undefined in the normal result view of generator operations whose lifecycle permits it (**recommend; synchronous rule now implemented**). The last keeps concrete R and ordinary result shapes without extending lifetimes. Rust's experimental coroutine treats resume-after-completion as an error, so it cannot determine ECMAScript's repeated-exhaustion contract. Generic structural iterators must be considered separately from branded generators; adding undefined to every written IteratorResult would erase a valid structural obligation.

For external return admission, the directions are: rely only on body return enforcement (**reject**, a completed or unstarted generator can bypass the body); rewrite output values to match R (**reject**, changes observable payloads and cleanup effects); or enforce the established request obligation at its specified request stage (**recommend; synchronous rule now implemented**), separately from completed-value typing. Users should receive predictable rejection before the relevant state change, while valid requests preserve ECMAScript cleanup and Promise assimilation. Rust has no matching replaceable external-return method. Existing boundary checks can avoid wrappers and new result shapes, but the async operand/await stage, omitted argument, finally blocks, erasure and captured generic types must be specified together. No choice may grant a reference permission across suspension. These recommendations are independent of implementation effort. The result-view recommendation is implemented in generator-lifecycle.md; its request-stage audit refines the remaining admission recommendation, including native async queue and await stages.

The synchronous request rule, including omission, reentrant admission effects, finally provenance and delegate replacement, is implemented in generator-return-admission.md. The async request rule remains open.
