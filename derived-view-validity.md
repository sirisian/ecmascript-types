# Derived-view source validity

A view derived by `subarray`, `window` (including its fixed-count form), or reinterpretation retains the source's original owned-allocation obligation. It does not refresh a generation from the current owner. Deriving from an already invalid source fails with TypeError, including an empty result. Deriving while live and then relocating the owner invalidates both views. A new view taken directly from the owner's current storage can succeed.

This applies transitively through a viewed SoA and its `fields` projections. Although the viewed SoA has a fixed extent and cannot relocate itself, the allocation from which it was derived can move. Its reads, writes, copies and projections must still check that original allocation. Owned-array subwindows retain the same original generation as their source window.

Check source validity before publishing a derived view, after the operation's existing argument conversions and applicable type, layout and count checks. Preserve ordinary expression evaluation, lookup and argument order. An argument expression runs before intrinsic entry; an internal coercion may run later. Either can invalidate an established source view. A coercion that throws propagates its own error; the new liveness check is not run in place of that error. A failed derivation publishes no new view, leaves an assignment destination unchanged and retains earlier effects. This adds no argument coercions or authority to bypass existing count checks.

Byte extent and allocation validity are separate. A valid fixed Span of eight bytes can produce a two-byte view; if a later buffer resize leaves four bytes, the child can still be accessed while its parent is out of bounds. Derivation must first succeed from a valid source. Retain the allocation guard, not every ancestor's byte extent. After construction the child uses its own current-bounds rule, including recovery after shrinkage and regrowth. This differs from retaining a nested field or element through its parent, which keeps the enclosing access checks described in [resizable-buffer view lifetime](resizable-view-lifetime.md).

Reinterpretation of an accepted native TypedArray source also checks that source's current validity. A buffer-backed source does not become valid merely because the requested result fits. The result still has its own extent after construction. Existing source categories, offsets, strides, count arithmetic and copying operations are unchanged; an array-backed Span without exposed bytes does not acquire byte reinterpretation support.

## Which obligations survive derivation?

A valid direction must preserve aliasing, refuse stale source storage, survive arbitrarily many derivations without resetting history, retain current-bounds recovery, and avoid live-reference counting.

| Direction | Ergonomics / autocomplete / wrong guess | Prior art, including Rust | Real-engine performance | Correctness / liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Drop source checks and retain only buffer/offset/count | Derived calls appear to repair a stale view but silently address storage the owner abandoned. Signatures do not reveal the change. | Native TypedArray subarrays share a buffer; they have no movable owning SoA to track. Rust sub-slices do not acquire a fresh independent lifetime. | Fewer guards, but no shape or IC requirement justifies changing the storage promise. | Loses the source allocation obligation. | Reject. |
| Capture the owner's current generation when deriving | Already stale parents produce apparently fresh children; a wrong guess can mutate the wrong allocation. | Rust borrowing does not renew a stale source. ECMAScript has no equivalent owned-allocation generation. | One scalar capture instead of copying an existing scalar; no meaningful production saving. | Erases history and makes derivation depth affect validity. | Reject. |
| Retain every parent object and its full bounds checks | Safe but a small independent byte view fails when unrelated parent bytes disappear; autocomplete cannot show the hidden extent chain. | Rust sub-slices keep a storage lifetime, not a requirement to access every element of the original slice. Native byte subviews have their own extents. | Can accumulate descriptor chains and checks; engines could flatten them, but that does not correct the semantics. | Overconstrains independent byte extents and the accepted current-bounds rule. | Reject for explicit derived views; retained nested values remain a distinct operation. |
| Copy on every derivation | Lifetime is easy, but writes stop reaching the source despite the advertised window API. | Rust `to_vec` and ECMAScript `slice` are copying operations, distinct from sub-slicing. | Allocation and copying replace constant-size descriptors; hidden ownership changes do not help ordinary ICs. | Violates aliasing and the Span/owned-array distinction. | Reject. |
| Refuse all further derivation of borrowed storage | Predictable errors but disables routine slicing and reinterpretation that signatures advertise. | Rust and ECMAScript support subviews; neither analogy calls for this blanket prohibition. | Simplest runtime, but removes capability rather than solving the obligation. | Avoids stale reuse at the cost of valid programs. | Reject independently of its implementation ease. |
| Validate the source and retain its original allocation obligation, with the child's own byte extent | Nested calls behave consistently; invalid use throws instead of silently changing targets. Element/extent signatures remain useful and no lifetime syntax is needed. | Rust sub-slices are a limited analogy for retaining storage origin; this proposal uses dynamic guards and permits aliases. Native TypedArray supplies the independent-extent analogy. | Copy a compact source/epoch descriptor; flatten transitive derivation rather than creating a parent chain. Hoist guards only across effect-free regions. No user-object shape or IC family change. | Preserves aliasing, original history, transitivity, independent extents and recovery. | **Choose independently of effort.** |

## Check timing

| Direction | Ergonomics / autocomplete | Prior art, including Rust | Real-engine performance | Correctness / liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Check once before argument processing | Fails early but can publish a stale result after an offset conversion relocates storage. | Rust excludes the conflicting mutation statically; ECMAScript conversions can execute code. | A single early guard is easy to optimize but proves too little. | Does not cover reentrancy. | Reject. |
| Add a new initial rejection and recheck at publication | Safe, but changes which existing conversion errors and effects occur for stale inputs; signatures do not announce that change. | Rust has no such runtime conversion ordering. ECMAScript APIs specify their own sequences rather than one universal early guard. | Can elide redundant guards, so cost alone is not a reason to reject. | Can be correct under a changed ordering contract. | Reject the unnecessary precedence change for these existing operations. |
| Preserve existing processing and check before publication | Existing argument exceptions keep their meaning. No successful derivation is produced from a stale source. | Fits ECMAScript's explicit sequencing; Rust is only an analogy for the resulting validity obligation. | Checks at an effect boundary, with no new conversion or object-shape changes. | Detects intervening invalidation without replacing an earlier abrupt completion or refreshing history. | **Choose independently of effort.** |

## Explicit raw-buffer exposure

A proposal Span's `buffer` accessor requires a valid source. A raw ArrayBuffer successfully obtained while the view was live is independently retained storage. Later owner relocation does not detach that buffer: a new byte view made explicitly from it can still use the old bytes, and does not claim to follow the owner. There is no hidden owner provenance on every ArrayBuffer. Native TypedArray buffer accessors retain their ECMAScript behaviour. Metadata such as length is not proof that acquiring or accessing storage will succeed.

| Direction | Ergonomics / autocomplete | Prior art, including Rust | Real-engine performance | Correctness / liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Let an invalid proposal view expose its old buffer | Convenient recovery spelling, but quietly turns an invalid location into a different storage contract. | Native buffers have collector-owned identity; Rust raw pointers do not provide this safe independent-storage contract. | No acquisition guard; no IC justification for bypassing source validity. | Permits stale-source acquisition that direct reinterpretation refuses. | Reject. |
| Attach owner invalidation to every exposed ArrayBuffer | Raw bytes unexpectedly expire after unrelated owner operations; standard buffer signatures cannot express that. | Neither standard ArrayBuffer nor Rust's raw-pointer API has this collector-backed revocation contract. | Requires propagation into native views and buffer operations, additional guards and metadata. | Changes existing buffer identity and interoperability semantics. | Reject. |
| Remove buffer exposure or return a copy | Hides stale bytes but removes aliasing/native interoperation or silently introduces copying. | Rust distinguishes copying from pointer/slice exposure; ECMAScript buffer getters do not copy. | Extra copying or lost functionality; no shape benefit warrants it. | Breaks the established byte bridge. | Reject. |
| Validate proposal-view acquisition; retain independent raw buffer identity after success | The explicit `.buffer` step changes the contract visibly. A wrong attempt on a stale view throws; an already captured raw buffer remains useful. | ECMAScript buffer identity is the useful analogy; Rust's lifetime and unsafe-pointer rules are different. | One acquisition check, no per-buffer owner registry or added native IC guards. | Preserves source checks and explicit independent-storage access without reviving the original view. | **Choose independently of effort.** |

Sources: [Rust slice splitting](https://doc.rust-lang.org/std/primitive.slice.html#method.split_at) and [ECMAScript TypedArray subarray](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-%typedarray%.prototype.subarray). Neither supplies this proposal's complete runtime liveness policy; the allocation/extent separation above is the selected proposal rule.
