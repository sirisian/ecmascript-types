# Static results of intersection and containment

A known built-in range's `contains` method contributes `boolean`. Its argument is inspected by the existing ordering/subset operation; the result contract does not convert it to the receiver's endpoint type. `intersect` contributes `RangeBounds<T | U>` from the two established endpoint domains. A statically known `RangeFull<any>` is neutral. Every other erased or unresolved argument contributes `any`, so an unknown argument cannot disappear from the union. These contracts preserve the runtime selection rules in [range-selection.md](range-selection.md).

The return view admits absent endpoints. It preserves complete metadata and generic or class identities, without predicting the concrete shape, selecting endpoints during checking, or claiming that the call will complete. Dot access, established computed keys, finite key domains, optional chains, immutable extracted methods and object patterns share the member/call rules. Extraction does not bind `this`. Existing participation rules still leave an untyped receiver gradual.

## Intersection result directions

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Production performance, shapes and ICs | Correctness and reference liveness | Other and decision |
|---|---|---|---|---|---|
| Keep the result unknown | Loses range members and defers wrong annotations until execution. | Rust preserves endpoint types in its range abstractions. | Discards available type facts without avoiding runtime work. | Does not implement the existing union result contract. | **Reject.** |
| Reuse arithmetic's identical-domain rule | Same-domain calls are simple, but supported heterogeneous calls lose information. | Rust's comparison bounds do not require endpoint identity; it has no standard intersection API to copy. | Cheap identity comparison; no benefit to runtime layout. | Selection can retain values from either domain without manufacturing an arithmetic carrier. | **Reject.** |
| Copy the receiver's domain or infer from the winning endpoints | Attractive narrow autocomplete; a wrong guess hides another endpoint type or changes after a comparison. | Rust's declared endpoint type is not inferred again from selected values. | Needs endpoint/comparison work to predict winners; user ordering defeats cheap static specialization. | Contradicts declared-domain retention and can execute effects during checking. | **Reject.** |
| Use a canonical union and the proven full-any identity | Honest autocomplete, with both endpoint types and possible absence. A narrower annotation fails at the receiving site. | Rust `RangeBounds<T>` motivates a shape-independent endpoint view, but Rust has neither this reified union contract nor this intersection operation. | Type-record joins without endpoint reads; ordinary guarded ICs specialize actual runtime shapes. | Preserves domains and existing liveness; selection and reflection remain runtime operations. | **Recommend.** |

A `RangeBounds<any>` may have endpoints, even if its current value happens to be full. Its static type alone cannot establish the full-any identity. By contrast, `RangeFull<any>` establishes absence. A full range with a specific domain still participates in the declared union. Distributing over a known argument union includes every alternative; unknown or cyclic alternatives supply `any`, not a partial result that drops that alternative. The method itself still establishes a range result. A whole unknown receiver establishes no built-in method contract.

The normal-result judgment reads the argument's established range view independently of the destination annotation. The destination cannot narrow a participating domain, select an arithmetic carrier or cause a fresh argument range to be reconstructed at a more convenient endpoint type. Generic method views carry their receiver domain through specialization, including when a receiver's free parameter is itself named `U`; a method's own binder must not capture it.

## Containment argument directions

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Production performance, shapes and ICs | Correctness and reference liveness | Other and decision |
|---|---|---|---|---|---|
| Require `T` or `RangeBounds<T>` | Suggests same-type membership, but rejects supported cross-family comparisons. Literal guesses may be converted unexpectedly. | Rust's `contains<U>` requires mutual `PartialOrd` bounds; it does not require identical types. | Unnecessary conversions or admission checks before the comparison; no layout benefit. | Changes exact comparison, hook effects and failure precedence. | **Reject.** |
| List a closed union of numeric candidates | Better-looking suggestions until a dependent width, metadata type or ordered class is omitted. | Rust uses capabilities, not a fixed primitive list. | More dispatch/type-list maintenance; no useful shape change. | Incomplete for existing supported candidates; conflates ordering with conversion. | **Reject.** |
| Introduce a new static mutual-ordering preflight in the result rule | Could catch some invalid calls earlier, but changes when effects occur and conflates a result contract with capability checking. | Rust checks explicit comparison trait bounds; this proposal also has runtime candidate dispatch and subset/empty shortcuts. | Requires a separate capability analysis; speculative comparison is unacceptable. | Requires its own complete failure/short-circuit design and cannot be inferred from the result type alone. | **Reject for this result judgment.** A separately specified preflight remains possible. |
| Keep candidate dispatch and publish Boolean | Autocomplete shows the result and an unrestricted candidate. Supported heterogeneous queries keep their behavior; incomparable cases retain runtime failure. | Rust supports heterogeneous comparison with explicit bounds. JavaScript's gradual candidates and range-subset overload have no direct Rust counterpart. | No new argument conversion, enumeration or layout; existing exact numeric/class dispatch remains. | Preserves argument evaluation, ordering, empty-subset behavior, NaN handling and liveness. | **Recommend.** |

The sketch is `contains(value: any = undefined): boolean`. A range candidate selects the subset operation; another candidate selects the scalar operation. It does not establish a flow-narrowing predicate for the candidate. Omission retains the runtime's `undefined` candidate behavior. A sized integer range can contain a differently sized value or a BigInt; numeric text is not converted to that integer. Supported nonnumeric candidates and incomparable pairs keep the runtime policy; this increment does not extend ordering capabilities.

## Replaceable methods and receiving boundaries

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Production performance, shapes and ICs | Correctness and reference liveness | Other and decision |
|---|---|---|---|---|---|
| Treat a known member name as proof of the original intrinsic | Fast-looking type guarantees can silently accept a replacement's wrong result. | Rust's ordinary methods are not JavaScript's writable properties; this analogy fails. | Allows unsafe check elision after property mutation. | Violates the receiving contract and source-position effects. | **Reject.** |
| Make public methods immutable | Stable dispatch, but breaks existing replacement behavior. | Closer to static method resolution, requiring an unrelated object-model change here. | Simplifies IC guards by changing the API. | Not authorized by these result contracts. | **Reject.** |
| Keep ordinary access and required result admission | Predictable annotations and failure after the actual call. | Rust's checked typed boundaries are a broad analogy only; dynamic property replacement is specific to this proposal. | A real engine can remove checks under an independent guarded implementation proof; shapes remain unchanged. | Preserves getter/argument/call effects, abrupt completion, failed-initializer TDZ and liveness. | **Recommend.** |

Inferred bindings and annotated returns must reject incompatible replacement results. Explicit `any` destinations remain erased. Optional short-circuiting skips argument evaluation, and a failed admission preserves already-performed effects. No new public function identity or reference capability follows from the engine's internal normal-result contribution.

## Sources and scope

[Rust Range::contains](https://doc.rust-lang.org/std/ops/struct.Range.html#method.contains) has a separate candidate type constrained by comparison in both directions. [Rust RangeBounds](https://doc.rust-lang.org/std/ops/trait.RangeBounds.html) exposes a common endpoint interface. These are primary-source analogies, not prescriptions for JavaScript property mutability, range-subset containment, reified unions or full-range domain identity.

This increment covers normal results and their receiving boundaries. General iterator result/context transport (`step`, `reverse`, callbacks), static ordering/capability preflight and custom enclosure APIs remain separate work. Existing runtime tests continue to cover endpoint ordering and selection. No full regression-suite completion is claimed by the focused result tests.
