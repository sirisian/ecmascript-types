# Metadata range endpoint domains

## Decision

Normalize present range endpoints against the endpoint type of the owning field's instantiated range shape. The host type supplies that domain only through an explicitly declared meta parameter: `RangeBounds.<T>` uses the substituted `T`; `RangeBounds.<uint16>` remains `uint16` even on a `uint8` or `string` host. This replaces the previous unconditional host-base sentence.

An open endpoint is still a stored endpoint value. `0..<256` is valid in a `RangeBounds.<uint16>` metadata field on `uint8`; it is invalid in a `RangeBounds.<uint8>` field. A library requiring host-domain bounds can use `0..=255` or an omitted upper endpoint. This is separate from the existing judgment over values produced by range iteration, where `0..<256` fits `uint8`.

The rule is shared by defaults, written arguments, builders, captures, hook results and reflection. Written numeric endpoints retain source digits until the declared numeric domain is available. A computed Number supplies its actual value, not lost source digits. Already typed atoms retain their domains. A mismatched domain, unrepresentable endpoint or wrong range shape is rejected at the existing checking boundary; normalization never wraps, calls a user conversion, clamps, or rewrites an open bound as a closed bound. Missing endpoints stay missing; SameValue preserves signed zero and typed-domain distinctions.

A generic default is evaluated and snapshotted once. Its unbound endpoint domain is not a completed membership decision: when a concrete host is supplied, normalize and check the completed portion against that host's instantiated shape before a capture or hook reads it. Default participation comparisons use that same instantiated default, so a representation change cannot spuriously activate a hook. Rejecting every unbound default would forbid valid generic declarations; permanently accepting it would skip the eventual field contract; reevaluating its expression per host would contradict once-only snapshot effects. Retaining the snapshot and completing its domain per host is the recommendation: autocomplete still reports the instantiated field type, Rust's generic type checking is only a partial analogy (these defaults are runtime snapshots), production engines can cache by owner and host without user shape changes, and no live reference or extra effect is introduced.

An optional range field supplies the same endpoint context when present. A union with several possible range domains does not choose by source order: it supplies no single endpoint context, and the supplied value must satisfy a complete alternative. `any` and `RangeBounds.<any>` retain admitted endpoint atoms without imposing the host's domain. This does not extend the closed metadata value language or authorize live references.

## Available directions

All valid directions must preserve exact numeric identity, field-type truth, origin independence, reflection round trips, omitted endpoints, existing phase/rollback rules and reference liveness. Implementation effort is not a selection criterion.

| Direction | Ergonomics, autocomplete and wrong-guess cost | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Always normalize to the host | Familiar for simple numeric bounds, but autocomplete promises the field's declared endpoint type while hooks receive the host; nonnumeric hosts and wider bounds become surprising errors | Rust `Range<Idx>` stores `Idx`, independent of a separate value being constrained; no close support for a host override | Cheap scalar conversion, but adds host dependence to otherwise fixed metadata and cache keys | Conflicts with fixed field types and declaration defaults that have no host yet; no liveness advantage | Reject: the old sentence cannot override the shape contract |
| Preserve every endpoint without contextual normalization | Explicit typed endpoints work, but every ordinary literal must be cast to obtain the type shown by autocomplete; equivalent intended origins can diverge | Rust infers unsuffixed literals from context; preserving already typed values is analogous, omitting context is not | Avoids conversion but increases distinct canonical values and loses shared normalization paths | Can be sound with strict rejection, but conflicts with existing contextual numeric metadata and written exact-digit rules | Reject |
| Use the instantiated field endpoint domain | The declaration predicts hook/reflection values; a wrong domain fails at construction, and wider fields express exclusive sentinels explicitly | Rust stores both endpoints as the range's generic argument and infers literal types from context. Rust is not this proposal's runtime metadata system. .NET `Range` stores index-domain bounds independently of the collection element type, a narrower analogy | Normalize once at construction and compare canonical atoms; no fields are added to user objects, no shape/IC changes, no runtime per-element conversion | Preserves declared types, exact atoms, default/capture identity and liveness; host dependence appears only when declared | Recommend |
| Widen, clamp or change inclusivity automatically | Makes a common maximum sentinel convenient but changes the domain shown by autocomplete, or the endpoint reflected by the program | Rust's endpoints still occupy `Idx`; .NET's index domain is explicit rather than inferred from collection limits | Requires extra canonicalization, overflow/next-value logic and domain-sensitive cache state | Widening violates the field type; clamping or changing bounds changes structural metadata identity; arbitrary dense domains have no next value | Reject |
| Separate mathematical endpoint representation from the declared range domain | Could model sentinels without widening the declaration, but requires a new endpoint API/type for hooks and reflection | Some interval libraries separate bounds and elements; neither Rust's generic range fields nor the current proposal does so | Potentially efficient, but changes representation and all endpoint operations instead of solving this metadata boundary | Could be made sound by redesigning range types, but contradicts the existing endpoint accessor contract without that redesign | Reject for the current range design |

The union choice has three directions: select the first convertible arm, reject all union-valued fields, or require a single contextual domain and otherwise check the supplied domains against whole alternatives. First-arm choice makes canonical identity depend on ordering and offers misleading completion; blanket rejection removes valid explicitly typed values. Recommend the last: it matches existing numeric metadata, adds no user conversions or shape mutations, and preserves typed identity. Rust's unique-context literal inference is the close comparison; it does not decide this proposal's gradual `any` behavior.

## Verification boundary

Endpoint admission remains distinct from endpoint normalization and field membership. The implementation checks canonical metadata endpoint domains at metadata shape boundaries; it does not redefine ordinary range iteration or ordinary range membership in this increment. The latter's currently permissive endpoint-domain checks remain a separate audit. Deep downstream stack safety, full portable accounting, generic family availability and all special carriers remain open.

Primary comparisons: [Rust Range fields](https://doc.rust-lang.org/std/ops/struct.Range.html), [Rust literal inference](https://doc.rust-lang.org/reference/expressions/literal-expr.html), [.NET Range](https://learn.microsoft.com/en-us/dotnet/api/system.range). These support the comparisons above, not a transfer of their complete semantics.
