# Runtime identity of inferred Symbol keys

A fresh Symbol's checking identity describes its source declaration; it is not the Symbol created when that declaration executes. In `const k = Symbol("p"); const h = { [k]: uint8(1) };`, the inferred object boundary must check the actual property keyed by `k`. The same declaration can execute again, creating a different Symbol, and two Symbols with the same description remain distinct.

This extends [named-object result dependencies](composite-result-dependencies.md). The key and its member's value type are separate dependencies. Selecting the correct key does not select a nominal constructor from the stored value, waive member admission, or make an ordinary object invariant typed storage.

## Requirements and decision

A valid solution must preserve source declaration identity, distinct activations and property paths, completed keys and written contracts, ordinary evaluation order and failed state. It must not replay Symbol creation or key conversion, enumerate a candidate object to choose its target, or read a reference to discover an identity. Autocomplete can describe the member under the stable key binding; equal descriptions never create interchangeable members.

Rust's declared field names are not runtime Symbol keys; its analogy is preservation of field contracts, not generative key identity. TypeScript erases its types and does not perform this proposal's runtime admission.

## Instantiation and contribution order

Checking retains the immutable source binding that establishes a fresh key. Aliases retain that declaration relationship. It does not initialize the binding or create the program's Symbol. Ordinary successful immutable initialization can retain its actual Symbol under the declaration and lexical environment. A failed initializer retains no initialized key; imported initialized keys retain the exporting binding's identity under the existing module rules.

At an inferred named-object boundary, complete a still-symbolic key independently at each property path. Prefer a matching selected contribution's actual key. This matters for recursion: the caller may have created its own Symbol from the same source declaration before forwarding a callee's differently keyed object. If no contribution supplies the dependency, an already initialized ordinary immutable binding in the applicable lexical environment can supply it. A same-spelled caller binding cannot. An actual key in a completed or written target is authoritative and is never retargeted from backing data.

Literal properties and methods retain keys already obtained by ordinary evaluation. Copies carry the corresponding source key dependency after their ordinary reads. Later literal definitions replace preceding contributions for the same key. A decorator mutation does not rewrite that source obligation: deleting the intended key and installing a different Symbol with the same description still fails admission. No new key evaluation, getter read or enumeration is performed to complete a target.

Key-only evidence supplies no value contract. In particular, an accessor's key must not erase the checked result of its later getter call by masquerading as a member typed `any`. Conversely, an actually checked member whose target is `any` remains authoritative. For fresh object inference, accessor exclusions use established computed keys as well as literal names, and a later data property or method replaces an earlier accessor exclusion. The declaration on a fresh accessor checks its result when called; inferring the fresh object must not call it. Ordinary admission of an existing object retains its existing member-read rules.

If admission fails, the destination remains uninitialized. Prior Symbol initialization, earlier object bindings and prior effects remain. The key does not confer reference liveness or change property mutability. A conforming plain object remains extensible and can be mutated through ordinary aliases; its established checked view still governs any subsequent receiving boundary.

## Bounded implementation

The interpreter retains declaration identities and checked key descriptions privately, records successful immutable Symbol initialization by environment, and carries key origins through the existing object contribution/completion machinery. Completion pairs the target and contributing view, preserving different keys and nominal identities at different nested paths. It does not rewrite shared symbolic publications or key caches globally by activation.

The focused cases cover fresh scalar and nominal members, aliases, same-description keys, nested paths, repeated and recursive activations, lexical shadows, method/accessor keys, copy/rest, decorators, failed state, direct eval and module imports/re-exports. Controls retain well-known and registry Symbols, ordinary annotations and ordinary mutable backing. Cases where the existing static rules establish no aggregate target test transport only; they do not prove additional static participation.

This resolves the fresh-Symbol admission issue recorded in the previous increment. Generic nominal leaves, unions and other composite kinds, index signatures, general mutable bindings and wrapper/resumable paths remain broader coverage tasks. The identity, convergence, checking-phase, budget/cache, specification-only and full-regression gates are not closed by this bounded repair.

The paired next probes retain a generic local class `P<T: type>` inside `make`, return a `P.<uint8>` from the resulting closure, then forward the selected closure result directly or through a named object property. Both currently fail with `ReferenceError: "P" is not defined`, including on the pulled base. They are desired-outcome probes, not passing conformance claims. The expected selected tag is `b:b`. The next task is to isolate where the captured family and specialization dependency is lost; these two observations need not be two separate bugs.
