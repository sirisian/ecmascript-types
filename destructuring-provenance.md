# Destructuring contribution provenance

Destructuring preserves evidence from the values it extracts. A typed sibling or computed key cannot annotate another extracted value. `function make() { const {x} = {seed: 1 := number, x: "s"}; return x; }` remains unparticipating, as does its direct-read equivalent. Giving `x` a String contract anchors that contribution. Renaming, nested patterns, established String or Symbol keys and finite key alternatives preserve the selected evidence, including distinct origins whose structural types compare equal.

Use the ordinary property contribution for an object pattern. Use the established iteration contribution for an array pattern, with the existing fresh-literal and immutable-position rules. A mutable array or tuple storage annotation does not establish the contract of its replaceable iterator. These rules describe extraction, not a new missing-key error or proof that a structural property is own and enumerable.

A default contributes only when the extracted value can be undefined. Remove undefined from the supplied contribution before joining surviving origins with the selected fallback. An annotation on an excluded undefined alternative cannot annotate a literal fallback; an unused typed fallback cannot annotate a supplied literal. Every written default still receives its required syntax and boundary checks. Later defaults may use earlier extracted bindings, and later binding names still shadow outer names without waiving temporal-dead-zone checks.

Rest retains evidence only from the collected values. For an object rest, retain a shape only where the existing copy judgment establishes own enumerable data properties and exclusions. Preserve the remaining members' individual evidence, and discard evidence belonging only to excluded members. Array rest follows the source iteration contribution, including established remaining positions. Neither the fresh rest container nor its syntax supplies an annotation.

An unchanged local binding can answer a contribution query without acquiring a storage contract. An unannotated `let` remains gradual, including when captured. An unannotated `const` infers a contract only when its selected contribution participates under the existing immutable-initializer rules; captured reads retain that admitted contract. Explicit element and enclosing-pattern annotations, including `any`, remain authoritative. Private callee approximations do not become independent captured contracts.

No source expression, getter or iterator runs to discover a type. Ordinary extraction order, skipped defaults, admission boundaries, iterator closing, failure state and reference permissions/liveness remain in force. Provenance supplies no stable-storage or borrowing proof.

## Decision

A valid direction must preserve selected declaration evidence, erasure, alternative origins, lexical identity and the storage/iteration distinction. It must keep contribution transparency separate from binding inference and leave runtime effects and reference rules intact.

| Direction | Ergonomics, autocomplete and wrong-guess cost | Prior art including Rust | Real-engine performance | Correctness and liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Give every extracted name the initializer's evidence | An unrelated field changes the selected name's editor contract and moves failures to an unexpected phase. | Rust selects fields from an already typed aggregate; it has no analogous gradual publication gate. | A single bit is cheap but loses necessary distinctions; it provides no shape/IC advantage. | Fabricates evidence and confuses storage with iteration. | Reject. |
| Infer from every known extracted type | Literal-only destructuring silently opts into typed storage, and a harmless rewrite changes receiving checks. | Rust infers ordinary bindings universally; that differs from this proposal's annotation-seeded inference. | More contracts and admission work, without a runtime-layout benefit. | Violates gradual binding rules and private-answer isolation. | Reject. |
| Erase all destructuring evidence, or support only simple names | Nested patterns and defaults unpredictably lose useful editor information and delay known errors. | Rust preserves component types through nested patterns; it does not motivate erasure. | Reduces analysis by omitting required information. | Disagrees with equivalent reads and existing typed bindings. | Reject. |
| Execute extraction/defaults to find the selected origin | Autocomplete/checking can invoke getters or iterators; wrong guesses have effects. | JavaScript destructuring is effectful; Rust's static patterns do not authorize executing arbitrary user code during checking. | Unbounded effects prevent predictable analysis and caching. | Violates checking phases and can observe invalid reference state. | Reject. |
| Project selected contributions, retaining provenance and distinct binding/capture contracts | Equivalent extraction preserves useful contracts; unrelated or skipped values do not affect the result. | Rust's component-pattern analogy supports selection; its ownership, static aggregates and lack of JavaScript defaults limit the analogy. | Compiler-owned metadata can share existing type/dependency graphs; no wrappers, new user-object shapes or IC keys are required. | Preserves all required distinctions, receiving checks, failure state and reference liveness. | Choose independently of implementation effort. |

This performance assessment is design reasoning, not a benchmark. [Rust patterns](https://doc.rust-lang.org/reference/patterns.html) describes component binding; [ECMAScript destructuring](https://tc39.es/ecma262/multipage/ecmascript-language-statements-and-declarations.html#sec-destructuring-binding-patterns) supplies the effectful property/iterator and undefined-default semantics. Neither independently defines this proposal's participation policy.
