# Tuple mutation plans

The [tuple admission audit](tuple-callable-admission.md) requires ordinary mutation to preserve backing location contracts. The next audit found a prerequisite failure even for fixed tuples: the interpreter used destination conversion to decide whether a move was allowed. That lets a `uint16` value move into a `uint8` position with conversion, although the existing design forbids moves between differently typed positions. An erased receiver can also reach a final length error after an intrinsic has already overwritten or removed elements.

An intrinsic mutation needs a pure plan after its ordinary receiver, length and argument processing, before its element work. The plan describes the final length, source/destination index pairs and any positions that must share one type. It consults backing contracts, not current element values. It neither reads elements nor tries conversions, invokes callbacks, writes, deletes or changes reference identity. An impossible plan throws TypeError at that point. A statically proved impossible plan remains a type error under the existing intrinsic-origin and effect proofs.

This does not make an admitted operation atomic. Getters, setters, species constructors and callbacks retain their ordinary effects after planning; subsequent conversions, writes, deletion and length changes retain their own checks. A later ordinary failure does not roll back earlier effects. A plan is not permission to use an invalid reference or overwrite backing established by an independent boundary.

## Decision: compatibility of movement

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art, including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
|---|---|---|---|---|---|
| Admit moves whenever the current value fits or converts | A rearrangement can silently narrow or specialize a value; the apparent positional signature does not describe the operation | Rust slice permutations operate within one element type; coercion sites do not make arbitrary tuple fields interchangeable | Requires value checks/conversions while moving, with effects and deoptimization | Contradicts the declared prohibition on moves across different types | Rejected |
| Admit a subtype-to-supertype move | Some intuitive widening works, but reverse and overlap direction become surprising | Rust assignment coercions are a partial analogy, not heterogeneous in-place permutation | Type relation checks and asymmetric movement guards | Changes the current same-contract rule; conversion/materialization obligations remain | Rejected for existing mutators |
| Require SameType for every planned source/destination pair | Indexed methods retain their promised types; a wrong range fails at the boundary | Rust's stable tuple field types and homogeneous slice operations support this distinction; runtime JS effects and liveness have no direct Rust equivalent | Shape-guarded type identity checks; skip homogeneous tail runs | Preserves backing promises and location identity without retyping | **Selected**, independently of implementation effort |

## Decision: scope of the plan

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art, including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
|---|---|---|---|---|---|
| Reject every mutator on a heterogeneous tuple | Autocomplete offers methods that fail even on an empty or same-type window | Rust lacks these tuple methods, so it does not require this blanket restriction | Cheap shape test | Safe but rejects operations that move no value across types | Rejected |
| Judge only the final values or the comparator's actual permutation | Data-dependent permission and callback effects precede discovering an impossible operation | Rust slice sort starts with one element type; it does not infer permission from comparator output | Whole-value scans, speculative callbacks and changing IC assumptions | Does not establish legal movement before effects; can bypass declared contracts | Rejected |
| Use the operation's actual index geometry, and all potential positions for arbitrary sort | A same-type window works; `[uint8, string, uint8]` can reverse because the middle stays in place | Rust sub-slices provide a useful range analogy, though these tuples use per-position types | Checks scale with declared prefix positions; a homogeneous tail needs one run check | Every possible move is authorized before element effects; no lifetime change | **Selected** |

`reverse` compares mirrored positions; `copyWithin` compares its normalized source and destination runs; `shift`, `unshift` and length-changing `splice` compare the positions actually moved. A `splice` replacing values without shifting does not acquire a movement obligation: each inserted value still crosses its own destination boundary. `sort` requires the same type throughout the occupied range, even with a comparator that happens to return zero. `fill` requires one type throughout the selected nonempty range because the same supplied value is used there. Empty ranges impose no movement or uniformity requirement. `push` and the inserted arguments of `unshift`/`splice` remain separate value boundaries.

The proposed final length must lie in the backing domain before a method reads, copies, removes or stores elements. This includes fixed-extent homogeneous arrays: a rejected `pop` must not first remove an element. For required fixed tuples and a single trailing unbounded homogeneous rest, the domain is exact arity or the required-prefix minimum respectively.

## Decision: failure timing and effects

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art, including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
|---|---|---|---|---|---|
| Discover an impossible plan at each store or final length assignment | A caught error can leave a tuple changed or a reference invalid although the operation was impossible from its types | Rust prevents incompatible field use before executing it | No initial plan, but redundant conversions and failed work | Does not enforce the movement prohibition; can delete before an inevitable arity error | Rejected |
| Plan before ordinary argument normalization | Fewer effects on failure, but argument coercion exceptions and effects disappear | Rust has no directly equivalent JS coercion stage | Cheap early check | Changes existing argument order and lacks the normalized index geometry | Rejected |
| Execute speculatively and roll back | Appears atomic but external effects remain visible | Rust exclusive mutation is not rollback of JS callbacks | Copies, logs and difficult deoptimization | Cannot undo arbitrary getter/setter/proxy effects or restore reference identity safely | Rejected |
| Plan after normalization, before element work; retain ordinary effects afterwards | A bad range/type plan fails before element access; earlier argument effects and later ordinary failures stay predictable | Rust validates operation domains before mutation; JS normalization/species effects remain specific to this proposal | Pure metadata checks, no value snapshot or wrapper shapes | Protects location contracts without inventing transactionality or borrow authority | **Selected** |

Existing comparator validation precedes the sort plan. For `splice`, the plan precedes species creation and reading the removed elements. A rejected plan does not call a getter or comparator merely to learn that its movement was forbidden. A valid plan preserves the ordinary algorithm's observation and write order. Replacement methods receive no intrinsic plan; calling the original intrinsic through `call` or another alias still executes its plan.

## Implementation boundary and next work

The interpreter now plans the existing backing positional/tail representation, and the established fixed primitive tuple proofs use SameType for movement and range uniformity. It does not replace the legacy first-rest representation for non-final/multiple rests, finite/nested rest operands or defaulted positions. A guard over that approximation does not make those forms correct. General-rest storage still needs the full contract and a mutation plan preserving surviving location contracts, as the previous note recommends. No implicit frozen partition or retyping operation is introduced.

Direct element stores and length assignments retain their existing checks. Copying methods retain their existing shape rules. Planning does not close proxy backing, array-like acquisition, reentrant adoption or general static-effect analysis. If an earlier ordinary argument effect establishes backing before the plan, the plan sees it; later effects remain subject to ordinary boundary checks.

Primary prior art: [Rust tuple fields](https://doc.rust-lang.org/reference/types/tuple.html), [Rust slice operations](https://doc.rust-lang.org/std/primitive.slice.html), [Rust coercion sites](https://doc.rust-lang.org/reference/type-coercions.html), and the [ECMAScript Array algorithms](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-array.prototype.splice). Rust's borrowing prevents incompatible aliasing statically; this proposal's references instead retain their established runtime relocation/removal rules.

The subsequent [suffix storage audit](tuple-suffix-storage.md) replaces the approximation for exactly one unbounded homogeneous rest surrounded by required positions. It extends these plans with exact length-derived contracts and a SameType check at every surviving index; the remaining general-rest and initialization gaps are recorded there.
