# Symbol binding identity in checking

The key a user creates remains the key used by metadata shapes, captures and reflected objects. A Symbol description is display text. An initialized immutable binding supplies its actual Symbol identity as computed-key evidence, including an immutable alias or an import followed to an immutable exporting binding. This evidence is independent of a `symbol` or `any` readable contract and creates no inferred contract or annotation-derived participation. Mutable targets, references, uninitialized bindings and opaque object-environment lookups supply no such evidence. A nearer declaration blocks outer fallback.

Use the environment of the consuming source. A Module recheck uses its module environment after the required dependency evaluation, not its realm's global environment. Console checking refreshes actual completed bindings after normal or abrupt evaluation; an unreached declaration remains uninitialized. Direct eval retains its lexical environment, and separate realms retain separate bindings. Reading this evidence executes no initializer, getter, helper or reference read.

A local immutable declaration known to receive a fresh Symbol can have a private checking key before initialization. Repeated passes within one checking unit and immutable aliases must agree on that key. Distinct declarations remain distinct even with equal descriptions. This private key is not the program's runtime Symbol: it cannot initialize storage, escape through reflection, replace the actual value, or identify a later activation. Unknown initializers and a shadowed `Symbol` name supply no intrinsic proof. Reconsider consumers once actual binding identity is available.

A meta declaration pending solely on an uninitialized direct local binding can retain its established shape keys as private ownership evidence. Detect two established pending claimants before body entry. Defer only the matching unclaimed-key judgment; no default, hook, registered claim or base-form waiver exists until preparation succeeds. Other unclaimed keys still fail. Failed declarations and unavailable imports are not pending local claimants. Actual runtime construction still requires a published owner. This keeps the publication transaction from [metadata publication](meta-publication.md).

A standalone specialization such as `function f<float32.<const D: M>>()` remains a specialization group when its flattened callable signature has no ordinary type parameters. Pending inputs are not proof that it is nongeneric and do not select a default or successful case. Resolve the actual key and pattern when available. A closed no-match and an ordinary nongeneric application keep their existing errors.

## Identity directions

| Direction | Ergonomics, autocomplete, wrong guesses | Prior art, including Rust | Real-engine performance, shapes and ICs | Correctness and reference liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Identify keys by name or description | Completion may show the expected spelling while a different key silently matches | ECMAScript Symbols contradict this; Rust paths resolve declarations, not equal display text | Small tables but invalid canonical/cache reuse; no valid IC advantage | Violates unique identity, shadowing and realm boundaries; establishes no liveness | Reject |
| Eagerly run/cache initializers or replace their values with checker tokens | Source-order effects and reflected identity surprise users; wrong guesses can change execution | Rust constant items are evaluated under a const regime and inlined; that is not a license to pre-run JS initializers | Speculative effects, cache invalidation and value substitution burden engines; no need to mutate user shapes | Violates TDZ, activation identity and evaluation order | Reject |
| Forget all Symbol evidence or ban local Symbol captures | Correct member suggestions become unusable and ordinary explicit specialization fails | Rust does not have JS Symbol keys; its field syntax does not justify this ban | Simple rejection offers no inherent shape/IC benefit | Avoids the question by removing supported programs | Reject |
| Preserve initialized binding identity and private declaration-bound checking evidence separately | Key completion, capture reads and reflection agree; a wrong Symbol does not alias | ECMAScript binding/value identity is direct prior art. Rust's path resolution is a limited declaration-scope analogy, not runtime Symbol semantics | Compiler-owned side tables or descriptors; identity lookups can be cached on actual environments, no fields added to user objects or IC churn | Keeps actual availability, identity and existing reference permissions/liveness independent | Recommend regardless of implementation effort |

| Direction | Ergonomics, autocomplete, wrong guesses | Prior art, including Rust | Real-engine performance, shapes and ICs | Correctness and reference liveness | Other / decision |

| Label a pending specialization nongeneric or ban Symbol cases | Declaration and application disagree; users receive an irrelevant diagnostic | Rust explicit generic arguments refer to declared generic structure; its stable trait system is not this overload design | Cheap refusal, no user-layout benefit | A flattened signature's representation cannot erase its case group | Reject |

## Verification boundary

Cover earlier-source and same-source fresh, registered and well-known Symbols, aliases, equal descriptions, shadowing, numeric capture domains, declaration conflicts, failed initialization/recovery, Module imports/re-exports and cycles, direct eval, console refresh and realms. A bounded source subset does not close generic activation identity, recursive inference, all effect-dependent availability or cache/resource accounting. The subsequent [metadata producer admission](metadata-producer-admission.md) repair addresses root Array admission and invalid written-leaf omission; it does not close those broader gates.

Primary prior art: [ECMAScript declarative binding reads](https://tc39.es/ecma262/2025/multipage/executable-code-and-execution-contexts.html#sec-declarative-environment-records-getbindingvalue-n-s), [Rust paths](https://doc.rust-lang.org/reference/paths.html), [Rust constant items](https://doc.rust-lang.org/reference/items/constant-items.html). Rust constants need not have one stable memory address; they are not direct analogues of a unique runtime Symbol.
