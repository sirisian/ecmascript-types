# Tuple element construction contexts

An array literal receiving a tuple context supplies each direct element with its own destination type. The created value must agree with the context used to check it. For example, the `U` below belongs to the generic alternative in either union order, and the resulting callable must accept both Number and String specializations:

```js
type Choice = { fn: (value: string) => string }
            | { fn: <U: type>(value: U) => U };
const items: [number, Choice] = [1, { fn(value: U): U { return value; } }];
```

The existing array element context did not cover tuple positions during evaluation. This refinement uses the declaration-proved fixed prefix, homogeneous rest and required suffix domain, including nested tuple rests and compact finite array runs. It carries the selected construction alternative through the array's existing live contribution paths to its receiving boundary. It does not change the array's declared storage contract.

## Decision: choose a construction context

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Provide no tuple context during evaluation | Checking and completion can promise an adopted generic declaration that the created function lacks. An ordinary first use then fails. | Rust tuple operands initialize distinct typed fields; TypeScript also models positional tuple types. Neither suggests ignoring an already available field type. | Cheap creation, but loses usable specialization information. | Disagrees with the existing positional context rule. | Rejected. |
| Use the first position or a union of all positions everywhere | Completion suggests unrelated neighbours' members and can select the wrong binder. The error may appear only at admission. | Rust fields retain their individual types; TypeScript's read unions are not construction destinations. | Simple metadata, but broad unions add checks and weaken specialization. | Conflates destination context with a possible-read approximation. | Rejected. |
| Inspect values, pre-run later spreads, or try admission to discover the partition | Context and errors depend on side effects that the user has not reached. Autocomplete cannot describe the same rule. | Rust tuple construction has no arbitrary JavaScript iterator effects; erased TypeScript typing cannot authorize them. | Extra iterator/getter calls, buffering and speculative conversions; potential shape and IC churn. | Changes evaluation order, failure precedence and liveness-sensitive effects. | Rejected. |
| Contextualize only spread-free fixed tuples | Predictable for a subset, but ordinary homogeneous rests and suffixes fail despite an unambiguous declaration. | Rust fixed tuples are only a partial analogy; this proposal explicitly has variable tuple rests. | Cheap, but discards declaration-sized proofs. | Safe omission of useful context, inconsistent with the broader known-position rule. | Rejected as the design endpoint. |
| Derive the destination from declarations and already completed evaluation; require one type across unresolved alignments | Completion can show the actual destination. A wrong length still fails under the ordinary rules; no guessed partition changes a callable. | Rust preserves positional field typing; TypeScript supports leading/middle rest elements. Their type models motivate positions, not this runtime mechanism. | Compact declaration runs and length guards; no public tag, wrapper, new object property or per-index shape. Known contexts can compile directly into construction. | Preserves adopted declaration identity, ordinary boundary timing, live contribution guards and reference liveness. | **Selected**, independently of implementation effort. |

For a supplied literal without spreads, every direct element and elision occupies one position. A trailing comma contributes none. Use that supplied length to anchor the required suffix; omitted trailing defaults are handled later by the existing default-completion rules. An elision is supplied `undefined`, not omission.

During evaluation, after the last source spread has completed, the actual accumulated count plus the number of remaining direct elements/elisions determines the final supplied length. This calculation does not evaluate those remaining expressions. It permits a direct suffix element after a dynamic spread to receive its own context while preserving ordinary iterator effects.

Before an unobserved spread, use the actual current index and the remaining fixed contributions as a lower bound. A fixed prefix has a stable destination. Beyond it, offer the homogeneous rest type only if every suffix position that can still reach that index has the same type. Enough following fixed contributions may exclude all suffix alignments. Otherwise compare only the reachable suffix runs, using SameType and their declared counts; never expand a large finite run or choose a partition from current values. If different types remain possible, provide no unique tuple position context. This does not excuse independently provable static errors or imply admission will succeed.

Static checking uses its own declared iteration information. Observing an iterator's actual count during ordinary evaluation does not retroactively make that count a static proof. Unknown-length indexed reads still have their possible-position union, even when the initializer happened to have a known length.

## Decision: carry the selected child to admission

Retain the existing operation-local contribution mechanism from [contextual union selection](contextual-union-selection.md). Eager admission would move getters and failures before later elements; a permanent value tag would leak a choice into ordinary reads and change object layout assumptions; an ambient preference would leak through reentrant getters. Each is rejected for those correctness and performance costs. Rust's nominal enum identity does not imply a persistent tag for this structural union. The recommended mechanism preserves the child result only through its original live data-property path, including every intervening array index or object property. Replacing a descriptor with the identical value ends that association. A literal's own selected contract still undergoes the ordinary check after decorators.

The receiving check validates the selected alternative and propagates its failure without trying another arm. It retains the original union as the storage contract, so a later valid replacement can use another arm. Later element effects precede admission; an abrupt later element prevents that admission. Ordinary reads and independent reentrant boundaries receive no pending choice. No reference identity or lifetime rule changes.

## Coverage and limits

Coverage exercises functions, arrows and methods in both arm orders; fixed, homogeneous rest, required suffix, nested/finite/zero runs, defaults and elisions; direct elements before, between and after spreads; equal reachable rest/suffix types; nested receiving contexts, captures and imported aliases; order, identity, descriptor replacement, reentrancy, failure recovery and closed diagnostics.

This is not a general context solver for heterogeneous multiple dynamic rests, unresolved extents, recursive tuple domains or alternative tuple shapes. Such forms retain their existing checking/admission rules. Spread operands and values obtained from ordinary iteration do not acquire a new construction context or a pending child choice under this refinement. Assignment writes, call spreads and collected rest parameters remain separate receiving-path work. Full body/default alternative applicability remains a separate gate.

Primary prior art: [Rust tuple expressions](https://doc.rust-lang.org/reference/expressions/tuple-expr.html), [TypeScript 4.2 tuple rest elements](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-2.html), and [ECMAScript array initialization](https://tc39.es/ecma262/multipage/ecmascript-language-expressions.html#sec-array-initializer). Rust's fixed arity and compile-time borrow discipline differ from runtime tuple admission and reference liveness here. TypeScript erases types and therefore does not settle runtime admission. The selected design is an inference from these analogies and this proposal's existing commitments.

## Regression repair: retain the scalar rest admission mode

The existing numeric-rest regression exposed a separate failure on the pulled baseline. `const raw: any = [decimal128(7)]; const values: [...[].<bigint>, ...[].<number>] = raw;` was accepted. The boundary rule requires TypeError: a proposal numeric value retains its type through `any`; unlike an ordinary Number or BigInt, it requires an explicit conversion to another numeric type. The explicit tuple cast remains available.

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art including Rust | Real-engine performance | Correctness and liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Change the expected result to permit this conversion | A rest silently permits what a scalar annotation refuses; completion hides the discrepancy. | Rust's explicit numeric conversion discipline does not justify an implicit aggregate exception. | Cheap, but preserves representation-dependent behaviour. | Contradicts the existing carried-type rule and makes decimal differ from float128. | Rejected. |
| Identify checked admission by the identity of its callback | A transparent receiving wrapper can change acceptance; users cannot predict this from the type. | Rust function values do not encode the caller's semantic conversion mode merely by identity. | Cheap equality test, but every wrapper needs special handling. | Already failed when a callback retained construction choices. It is not an adequate semantic guard. | Rejected. |
| Pass the required scalar admission operation explicitly | Scalar and rest boundaries enforce the same declared rule; explicit casts retain their distinct meaning. | Rust's distinction between an explicit conversion and type-preserving storage supports the principle; its lack of this gradual boundary limits the analogy. | An internal call parameter, with no value tag, wrapper object or shape/IC change required in a real engine. | Retains RequireType, construction-choice isolation, ordinary conversion effects and reference checks. | **Selected**, independently of implementation effort. |

Adjacent probes found the same missing carried-type guard at fixed tuple, homogeneous array and object-member boundaries. These are all receiving operations in the boundary table, so the engine now passes RequireType as their member operation, including the receiving construction choices. Scalar rest planning consumes that supplied operation without inferring its mode from callback identity. The explicit path keeps its explicit conversion callback. In particular, the explicit structural-object step of ConvertValue converts members explicitly in place; it reuses the ordinary observation/write/admission path with that operation rather than falling into checked member admission. The original failing requirement is unchanged; controls cover decimal32/64/128, rational64, float128 and uint8, alongside explicit fixed-tuple/array/object casts and the existing explicit-rest and class-operator tests. This is an application of the existing boundary rule, not a new numeric conversion policy.

For the numeric analogy specifically, Rust's [type cast expressions](https://doc.rust-lang.org/reference/expressions/operator-expr.html#type-cast-expressions) distinguish requested numeric conversions from storing a value at its existing type. Rust has no matching `any` boundary; its cast rules do not decide this proposal's representability or runtime failure phase.

## Regression fixture: imported nominal guards after effects

An existing value-class fixture required a static impossible-test diagnostic for `c instanceof C` after an effectful conversion and `await`, with `C` imported. The nominal annotation of `c` alone does not prove the identity and protocol of the right operand at that later expression. A control replacing `C[Symbol.hasInstance]` after construction makes the test false while `c` retains its nominal type. The protocol must execute normally when its stability is not proved.

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art including Rust | Real-engine performance | Correctness and reference liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Diagnose solely from the left operand's nominal annotation | Rejects a guard whose right operand's protocol can give a different answer; a type shown by completion is mistaken for a protocol guarantee. | Rust nominal identity has no corresponding replaceable JavaScript instance-test hook. | Cheap type comparison but unsound. | Ignores intervening effects and actual protocol selection. | Rejected. |
| Execute conversions or hooks while checking to settle the test | Results depend on effects occurring before their source position. | Rust compile-time evaluation does not authorize arbitrary JavaScript user code during type checking. | Speculative execution and invalidation costs. | Violates checking phase, effects and liveness rules. | Rejected. |
| Never diagnose nominal guards | Predictable, but discards independently established closed diagnostics. | Rust can use known nominal identity; it does not require blanket uncertainty. | Cheap deferral, fewer useful compile-time facts. | Weakens the existing proven-origin rule unnecessarily. | Rejected. |
| Require stable actual constructor/protocol evidence, retaining runtime behaviour when effects invalidate it | A nominal type remains useful without promising a mutable protocol's answer. Proven closed guards still diagnose. | Rust motivates nominal identity only; its lack of a replaceable constructor/protocol limits the analogy. | Reuses origin/effect facts; no ordinary execution or new object layout. | Preserves protocol order, unknown dependencies and reference liveness. | **Selected**. |

The old effectful fixture now requires successful evaluation, and replacement-hook and conversion-without-suspension controls preserve this distinction. The existing local closed-guard tests remain. A separate stable-import probe remains a required diagnostic follow-up for the origin-proof audit; accepting an effectful case is not a claim that every imported case must be deferred.
