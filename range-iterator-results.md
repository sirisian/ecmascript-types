# Static results of explicit range iteration

`step` and `reverse` expose a helper-bearing iterator with the protocol `Iterator.<I, undefined, any>`, where `I` is the item contribution below. Its own `Symbol.iterator` returns an iterator with the same item, completion and input contracts. `next()` produces `{value: I, done: false} | {value: undefined, done: true}`. Exhaustion is a value of `undefined`, not the no-values type `void`. Incoming `next` values are ignored by the numeric cursor. These contracts do not assert that acquisition succeeds or that the interval contains an item.

## Item contribution

The runtime item selection in [range-iteration.md](range-iteration.md) remains unchanged: a supported concrete stored numeric domain wins; otherwise the original typed start, typed end, then Number supply the carrier. Reversing does not reverse that priority. Endpoint reflection and yielded-item typing remain separate.

For a concrete range shape, a supported numeric domain contributes its complete type, including metadata. The supported bases are `number`, `bigint`, sized `int` and `uint`, and `float16`, `float32`, `float64`. A literal endpoint type contributes its widened numeric base; literal endpoint sets are not item sets (`ClosedRange.<1 | 3>` also yields `2`). A union contributes the canonical union of every arm's endpoint-fallback contribution. An unresolved, cyclic, erased or unsupported contribution is `any` and cannot be omitted.

Endpoint fallback preserves supported typed-numeric and BigInt carriers, including their metadata. A Number endpoint contributes ordinary `number`: it does not select a typed-number carrier. `RangeBounds.<T>` is an endpoint-reading view, so it uses this fallback upper bound even when `T` is a single numeric type; it cannot prove the hidden stored domain. In particular, `RangeBounds` of a Number metadata type contributes `number`, while a concrete shape with that exact stored domain retains the metadata. This is an upper bound on normal items, not a new numerical representation or a change to admission hooks. Generic parameters unresolved at the member judgment contribute `any`; no destination or callback context invents a stored domain.

| Direction | Ergonomics and autocomplete | Prior art | Real-engine performance | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Always use endpoint `T` | Attractive signature, but a literal union excludes intermediate items; wrong guesses become false static promises. | Rust ranges retain `Item`, but Rust does not have this erased/heterogeneous endpoint fallback. | Cheapest type query, no shape effect. | Unsound for literal and some metadata endpoint views. | **Reject.** |
| Always use Number | Familiar for small loops; loses sized integers, BigInt and metadata. | Neither Rust's associated `Item` nor ECMAScript's result protocol implies Number. | Loses numeric specialization and may demand conversions. | Disagrees with actual values. | **Reject.** |
| Leave every result unknown | Avoids false promises but autocomplete cannot describe `next`, completion or concrete items. | Unlike Rust's typed iterator contract. | No static work; missed specialization opportunities. | Safe but discards established facts. | **Reject.** |
| Read endpoints or invoke metadata during checking | Could sometimes predict a single carrier more precisely. | Rust trait selection is not execution of iterator state. | Effects and state dependence complicate caching and IC invalidation. | Violates phase separation and can consume state or affect references. | **Reject.** |
| Use the static upper bound above | Concrete numeric loops retain precision; uncertain domains remain visibly gradual. | Follows Rust's separation of `Item` from advancement; fallback is proposal-specific. | Bounded type traversal; no range/cursor shape change or numerical retagging. | Includes every possible carrier without evaluating endpoints or creating reference authority. | **Recommend.** Precision follows available type evidence. |

## Completion, input and receiving boundaries

| Direction | Ergonomics and autocomplete | Prior art | Real-engine performance | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Use `void` as the terminal value, or omit completion from `.value` | A bare item assignment looks safe until exhaustion. | Rust exposes `Option<Item>`; ECMAScript exposes a `done` discriminator and an actual value. | No benefit over the same two result shapes. | `void` has no values; the cursor actually returns `undefined`. | **Reject.** |
| Use `any` for the entire step result | Accepts mistakes even for a known concrete item type. | Discards the information both cited protocols expose. | Prevents useful checking with no runtime saving required. | Safe but needlessly weak. | **Reject.** |
| Use a discriminated result with `undefined` completion | Readers must account for exhaustion; tools expose both branches. | Close to Rust's `Option` role, with ECMAScript's existing object representation. | Existing result shapes and discriminant ICs; no extra cursor allocation. | Matches normal results and preserves failure timing. | **Recommend.** |
| Restrict resume input to `void`, `undefined` or the item type | Suggests an input obligation the numeric cursor never uses. | Rust `next` takes no sent value; that does not decide JavaScript's ignored extra arguments. | Adds an unnecessary admission. | Changes accepted calls without a numeric need. | **Reject.** Use optional `any` input. |
| Treat the internal helper carrier as a global nominal constructor | Chaining checks, but an inferred local can throw a ReferenceError for an unwritten name. | Rust's concrete adapter types are real types, not this implementation sentinel. | A global lookup and prototype walk prove the wrong thing. | No such global constructor exists. | **Reject.** |
| Trust the public method name and skip result admission | Replacement bugs pass until later use. | Rust's trait identity is not a mutable JavaScript property. | Fast but unsound; ignores property/IC invalidation. | Can publish an unchecked return or initialize a binding falsely. | **Reject.** |
| Retain the internal chaining carrier with a structural protocol boundary | Ordinary inferred locals and explicit protocol annotations work; malformed replacements fail at the receiving boundary. | Uses ECMAScript protocol objects; unlike Rust, replacement remains possible. | Existing structural admission and method views; engines can guard/elide proven cases without changing range shape. | No invented global, eager iteration, new reference authority or extended lifetime. | **Recommend.** |

`step(by: any = undefined)` preserves runtime difference validation: omission supplies `undefined` and fails numeric difference validation; a wider difference need not fit the item width, and unsupported inputs still fail at acquisition. `reverse()` keeps its origin and integral-endpoint requirements. Dot, established computed String keys, finite keys, optional calls and extracted method views use the same contracts. Extraction does not bind `this`. A replacement cannot bypass an inferred-initialization or return boundary; prior effects survive failure and an unsuccessfully initialized binding remains uninitialized.

The result remains helper-bearing under the existing iterator-helper rules. The default range `Symbol.iterator` contract and shared consumer rules are specified in [range-default-iterator.md](range-default-iterator.md). This explicit-cursor contract does not define general callback/bind/apply transport, stronger generic item inference, or a new control-flow narrowing rule. Ordinary Array indexed storage still does not prove the behavior of its replaceable iterator.

Primary references: [Rust Iterator](https://doc.rust-lang.org/std/iter/trait.Iterator.html) (`Item`, `next`, `step_by`, `rev`) and [ECMAScript iterator result objects](https://tc39.es/ecma262/multipage/abstract-operations.html#sec-createiterresultobject). Rust's `step_by` is count-based skipping; it does not establish this proposal's fractional numeric difference semantics or JavaScript method stability.
