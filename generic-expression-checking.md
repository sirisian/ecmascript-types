# Checking generic expressions

An expression such as `I.<uint8>` applies a generic declaration even when its result is discarded. If `I<T: type extends string>` is the established declaration, the application is invalid before execution, just as an annotation naming `I.<uint8>` is invalid. An unused function or an explicitly unreachable branch does not excuse a statically established invalid application.

This applies to interfaces, aliases and established class constructors. Positional, named and spread arguments use the same parameter assignment, constraints, kinds and defaults as other applications. A supplied but unresolved argument occupies its slot; it is not an omitted argument and cannot select a fallback default. Keep dependent obligations until their determining inputs are available, including through enclosing generic specialization.

The expression's value type and the type it denotes remain distinct. Checking `I.<string>` does not make the expression an instance of `I<string>`. Checking a class application does not construct an instance, materialize its constructor, run a static initializer or install a new object shape.

## Required properties

1. Reject known invalid argument binding at the existing checking boundary.
2. Preserve the applied declaration's lexical context and the caller's argument context.
3. Preserve pending inputs, bypassed defaults and enclosing specialization dependencies.
4. Establish the actual generic origin; a spelling, an erased value or a mutable producer binding alone is insufficient.
5. Preserve ordinary execution, module availability, identity, reference permissions and reference liveness.

## Prior art and analogy limits

[Rust's bounds](https://doc.rust-lang.org/reference/trait-bounds.html#bound.satisfaction) restrict uses of generic items and provide assumptions inside generic bodies. This supports checking a known application's bound even when its result is not consumed. Rust is not a model for executing this proposal's first-class Type Objects or JavaScript getters during checking, and its trait/lifetime system is not a substitute for this proposal's reference-liveness rules.

[TypeScript's generics](https://www.typescriptlang.org/docs/handbook/2/generics.html) use constraints and parameter defaults to guide argument checking. That is a useful tooling analogy. Its types are erased; this proposal retains runtime type identity, initialization, conversion and dynamic admission, so the phase and cache rules cannot simply be copied.

## Boundary and origin rules

Use source declarations and immutable origin information already established by ordinary checking. Parentheses and an eligible immutable alias preserve the original declaration. A class binding that can change, a class decorator that can replace it, an erased parameter, an arbitrary property read or a call result does not acquire that origin merely because its name or runtime value once matched it.

Purely static judgments retain their existing parsing/linking phase. Judgments requiring type computation retain the prescribed pre-body or specialization boundary, evaluability restrictions and budget. The checker does not execute a dependency body on demand, initialize a local binding to obtain an argument, or evaluate an unused default. A failed computation is not an unknown type or a successful cached application.

Runtime application still evaluates its base and performs the required admission. Static checks do not remove accessor/Proxy effects, class initialization, ordinary exceptions or dynamic reference checks. The selected design is independent of the size of the interpreter change.

## Imported alias origins

A named import of a generic alias keeps the exporting declaration's parameter list, constraints, defaults and retained obligations. Renaming the import or passing it through a re-export does not replace that declaration. The alias's expanded result is a separate fact: `type I<T: type> = T` remains transparent, and `I.<string>` still denotes `string`. The value of the alias itself has Static Type `type`, even when its expansion denotes a primitive or an unresolved parameter.

Argument expressions belong to the importing use site. Bounds and selected defaults belong to the exporting declaration. Module linking establishes the origin; it does not initialize the declaration's inputs. Computed checks wait for the prescribed consumer boundary after ordinary dependency evaluation. A dependency exception wins over those pending checks; an unavailable cyclic input remains unavailable. Known argument-list errors keep their earlier checking phase.

### Directions considered for crossing the module boundary

| Direction | Ergonomics | Prior art | Real-engine performance | Correctness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Export only the expanded type | Autocomplete loses parameters; a valid alias can be called nongeneric, and wrong arguments can survive until execution. | Rust aliases are transparent, but transparency does not imply losing their source declarations. TypeScript transports alias declarations through imports. | Small metadata, but repeated recovery and delayed admission; no shape advantage. | Expansion can erase constraints and generic capability. It confuses a Type Object's value type with its denotation. | Rejected: the existing language rules already require the declaration contract. |
| Make all aliases nominal to retain their declaration | Parameter names remain available, but equal structural types unexpectedly become distinct. | A Rust alias names an existing type; a newtype would be a different feature. TypeScript aliases do not introduce nominal identity either. | Adds identity distinctions and potentially more specialization/cache entries; wrappers could change object shapes and inline caches. | Changes alias equality and assignability merely to transport checking information. | Rejected independently of implementation cost. |
| Read or evaluate the imported runtime value during linking | Can recover a target, but makes a harmless import refactoring trigger initialization or a cycle failure sooner. | Neither Rust imports nor TypeScript's erased type imports justify running a JavaScript module to discover a contract. | Introduces eager execution, allocation and cache population; property-based recovery could affect shapes or invoke accessors. | Violates dependency order and initialization availability; runtime success is not proof of reference liveness. | Rejected: linking must not manufacture the needed runtime state. |
| Transport resolved declaration identity and source context separately | Autocomplete and argument errors remain stable through named imports, renames and re-exports; wrong guesses fail at the prescribed phase. | Matches declaration-based cross-module tooling while retaining transparent aliases. Rust's specific alias-bound limitation is noted below. | Internal per-module metadata can be shared; no public object properties, wrappers or inline-cache changes are needed. Existing runtime interning remains authoritative. | Preserves structural identity, caller/declaration contexts, pending inputs, default demand, dependency order and independent reference liveness. | **Recommended.** This meets the required properties regardless of interpreter implementation effort. |

Rust is an important but limited comparison here. The [Rust Reference](https://doc.rust-lang.org/reference/items/type-aliases.html) describes an alias as another name for an existing type. However, the [rustc `type_alias_bounds` documentation](https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html#type-alias-bounds) documents that ordinary alias parameter bounds and where clauses are not checked at use sites. That limitation is not the rule of this proposal, which already requires alias constraints to be checked. The earlier Rust generic-bound analogy therefore does not establish Rust alias-bound enforcement. [TypeScript's module reference](https://www.typescriptlang.org/docs/handbook/modules/reference.html#importing-and-exporting-typescript-specific-declarations) confirms that aliases can be exported and imported, but its erased type declarations do not model runtime Type Objects or module initialization requirements.

Expression applications splice tuple or stated-extent array spreads into the argument sequence before alias binding, just as type-reference applications do. The expanded entries keep their order and do not acquire a label from the spread. An erased target still performs this binding at runtime; an invalid spread does not become a single tuple argument.

## Dependencies of imported alias contracts

A declaration's environment crosses the module boundary with its contract. At the consumer's required checking boundary, a producer-local constant already initialized by ordinary dependency evaluation is available to that contract. Its name does not become a consumer-local read. Helper functions keep their actual producer closures, including imports used by those helpers. Evaluability remains a separate requirement: an initialized mutable binding is not thereby an admissible compile-time input.

Retain applications inside an alias body as obligations independently of the expanded result. If `Outer<T>` applies an imported `Inner<T>`, closing `Outer` must check `Inner` with the resulting arguments, even if `Inner` erases those arguments from its result. Each step follows its own resolved import, including renames and re-exports, and retains the source module of its bounds, selected defaults and predicates. An incomplete argument set is pending, not a closed successful predicate check.

This does not make local runtime inputs available before their initialization, execute an enclosing function to obtain its captures, or run an import cycle in a new order. A required computation that cannot complete because of an uninitialized producer input fails at the consumer's pre-body boundary. Ordinary handled exceptions and short-circuit evaluation keep their existing rules. Dependency exceptions still precede pending computations; purely static argument failures retain their earlier phase. Failed evaluation records no successful application.

### Directions considered for source dependencies and nested applications

| Direction | Ergonomics | Prior art | Real-engine performance | Correctness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Defer every imported dependency to runtime | Moving an alias behind an import changes when the same wrong argument is reported; unused code can hide it despite autocomplete showing the restriction. | Rust's ordinary alias-bound limitation exists, but adopting it would abandon this proposal's established checks. TypeScript's generic constraints support earlier feedback. | Small checking summaries but repeated runtime admission; no shape or inline-cache advantage. | Loses required pre-body checks and can discard inner obligations when expansion erases parameters. | Rejected: import placement must not weaken an established contract. |
| Copy or evaluate producer initializers in the consumer | Can make simple examples pass, but a name collision or cycle gives surprising values and effects. | Neither Rust's lexical alias declarations nor TypeScript's erased generics supplies a precedent for executing JavaScript initializers in another environment. | Duplicates closures and computations; eager allocation can change caches and object identity, with possible shape and inline-cache consequences. | Confuses declaration and activation identity, can initialize unavailable inputs, and violates module order. | Rejected independently of implementation effort. |
| Keep only the outer alias's contract after expansion | Straightforward autocomplete for the outer parameters hides restrictions imposed by its body; a wrong guess becomes a delayed inner failure. | Rust's transparent naming is relevant to equality, not a justification for erasing obligations this proposal promises. | Preserve each resolved source and retained application; use actual module environments | Imports, renames and wrappers preserve the restrictions tooling can explain. Wrong guesses fail at the prescribed boundary with the original clause's diagnostic. | Follows lexical declaration identity and transparent aliasing; Rust's alias-bound limitation and TypeScript's erasure remain explicit analogy limits. | Share internal declaration/dependency metadata and deduplicate equivalent inputs. No wrappers, public fields, shape changes or new inline-cache guards are required. | Keeps caller arguments separate from producer contracts, preserves initialization/evaluability, dependent checks, failure order and independent reference liveness. | **Recommended.** Satisfies the requirements without manufacturing runtime inputs, regardless of implementation cost. |

The Rust and TypeScript sources linked above apply to this comparison as well. Their module and generic models do not determine JavaScript initialization or exception semantics; those follow this proposal's own checking and module rules.
