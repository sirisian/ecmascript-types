# Type-checking diagnostics

The specification defines which programs are rejected. Diagnostic identifiers explain those rejections to people and tools; an identifier does not add a rejection rule. engine262 is a proof of concept against that specification, not its semantic authority.

`StaticTypeError` identifies a type violation found before the candidate source body executes. It inherits from `Error`, separately from `SyntaxError` and the dynamic `TypeError` boundary. Like other native errors it accepts a message and an optional cause, supports subclassing, and has a constructor in each realm. The formal definition is `sec-statictypeerror-objects`.

## Identity and applicability

The specification repository owns `diagnostics.json`. Each entry identifies a diagnostic family, a rule, its checked-code applicability, permitted phases and error class, an explanation, argument and related-location schemas, and the specification clauses that define its meaning. The generated rule index is informative: its links lead to the predicates; the JSON does not duplicate those predicates.

A family can contain several rules. For example, `RT_CONSTRUCTOR_REQUIRED` includes the checked-only inference rule for calling `new` on an ordinary nonconstructor and the always-applicable rule for a proposal Type Object that supports conversion but not construction. Renaming a message cannot change which rule applies.

The applicable source unit belongs to the obligation. Deferring a metadata judgment does not transfer ownership to the module or helper that resolves it. Declared contracts remain mandatory when a caller is unchecked or its argument type was inferred. Added contracts on existing built-ins and inference-based impossibility errors follow the checked-code boundary. Existing built-in contextual types and overload formation make this decision when creating obligations, before a final diagnostic exists.

An inapplicable diagnostic does not erase facts. In particular, an established empty meet stays empty when its error is suppressed. An unknown result, an empty domain, a hook failure and an abandoned evaluation are different outcomes. None creates a reference or extends reference liveness.

## Host records

An engine may expose an immutable host diagnostic record with a family, rule, phase, primary source location, owning unit, applicability, arguments and related locations. This proposal does not require a JavaScript-visible `error.code` property or a specific rendering order, number of secondary errors, wording, or language of the message.

engine262's `TypeDiagnosticOf(error)` supplies this host record for registered checker errors. It keeps records in a weak side table. It does not add bookkeeping properties to program objects or use diagnostic information in runtime inline caches. A constructor-created `new StaticTypeError()` is an ordinary error object; it need not have a host checker record.

The registry currently marks its identifiers **provisional**. An identifier becomes stable only when its meaning, applicable obligations and conformance witnesses are settled. A stable identifier is never reassigned. Retirement reserves the identifier; a split or replacement requires new identifiers and a migration explanation. Discovering another error is not a reason to delay useful provisional identities.

## Implicit protocol contracts

A typed return can expose a non-callable `Symbol.hasInstance` to an unchecked caller. That caller keeps the existing runtime callability error. When the hook is callable but its declared parameter or receiver contract cannot accept the implicit call, the declared contract still applies before execution. A union member that fails only the suppressed callability rule cannot establish an always-applicable failure.

| Direction | Ergonomics | Prior art | Performance | Correctness | Other and decision |
| --- | --- | --- | --- | --- | --- |
| Always reject every known protocol failure | More early feedback, but an unchecked caller loses its documented runtime behavior. | Rust checks trait obligations statically, but has no comparable legacy JavaScript boundary. | One combined proof; no shape or IC benefit. | Conflicts with the checked-only non-callability rule. | **Rejected.** A typed return does not activate its caller. |
| Suppress every protocol failure in unchecked code | A wrong declared argument appears valid until execution. | Rust, TypeScript and C# distinguish callable signatures from their invocation sites; none motivates dropping a declared contract here. | Avoids some diagnosis work, with the same runtime representation. | Loses always-applicable declared receiver and parameter obligations. | **Rejected.** The operator does not erase a hook's contract. |
| Separate operator eligibility and declared-call obligations | Predictable boundary and useful signature information for tools. | Retains Rust's emphasis on enforcing declared call obligations while respecting JavaScript's different participation policy. | At most two bounded contract queries; no required object metadata or IC changes. | Each alternative is checked under the rule that actually applies; liveness is unchanged. | **Selected.** Both rules may share a diagnostic family. |

## Conformance and implementation independence

Negative tests should identify the intended rule and error class and establish that the candidate body did not execute. A timeout, parse failure, or unrelated type error is not evidence for the intended rejection. A host-side observer is useful when inserting a source sentinel would itself invalidate an origin or effect proof. Module tests must separately observe dependency effects and candidate-body rejection; async evaluation must settle.

The independent Boolean-flow model in the specification repository enumerates a bounded domain and emits neutral source fixtures consumed by an engine adapter. Its coverage declaration excludes metadata, mutation, reference liveness, numeric domains and module scheduling. Its agreement is evidence within that domain, not a claim that every type judgment is independently validated.

Source classification can use node ownership and a downward inheritance traversal; it must not repeatedly scan every ancestor's subtree. Cached checking depends on source, strictness, inherited direct-eval status, declaration and module environments, and any realm state admitted by the relevant rule. Speculative runtime feedback cannot justify an additional mandatory rejection. Uncalled functions still require the checks applicable to their source.

A subsequent production implementation may choose different representations, traversal schedules and caches while preserving these outcomes. The future Deno V8 fork work has its own source, integration and performance validation; this document chooses no fork, build scripts or engine-specific integration points.

## Evaluation accounting and invalid recursive declarations

A computation's allowance covers user code reached inside it, including a builder, inverse, default, refinement predicate or metadata hook. Exhaustion remains a failure even if evaluated code catches an incidental exception. No value obtained after exhaustion may become a successful cached type or inverse proposal. GetTypeObject requests are charged before intern-table lookup, so a populated intern table does not make the same sequence of requests cheaper. Separate agents have separate active computation state.

This is part of the selected logical-accounting direction, not a claim that the fuel model is complete. Portable constants, a complete specification of evaluation-step charges, per-expression accounting, and replay of skipped evaluation costs remain necessary. engine262's host budget settings are development controls; they do not establish the finalized language's acceptance boundary. Its `TypeEvaluationBudget` host export exposes counters and scopes for validation and is not a JavaScript language API.

The following choices settle the narrower accounting and recovery questions. Rust's [long-running constant-evaluation lint](https://doc.rust-lang.org/stable/rustc/lints/listing/deny-by-default.html#long-running-const-eval) motivates termination safeguards but permits user configuration; it is not a portable browser acceptance contract. Rust's [E0072](https://doc.rust-lang.org/error_codes/E0072.html) is a close analogy for rejecting infinite inline layout, although the languages' reference and nullable representations differ.

| Direction | Ergonomics | Prior art | Performance | Correctness | Other and decision |
| --- | --- | --- | --- | --- | --- |
| Charge physical allocation and function entry alone | A warm cache can change acceptance; a looping inverse can hang tooling. | Rust's const-evaluation safeguard does not justify leaving function bodies unbounded. | Cheap counters, but no bound on work inside one call. | Depends on representation and misses nested computation. | **Rejected.** Neither charge measures the required logical work. |
| Charge logical requests and all evaluation reached by a type computation | Repeatable local boundary behavior; a wrong guess has an identifiable computation. | Shares Rust's termination motivation while requiring an eventual portable ECMAScript policy. | Counters or equivalent summaries; interning remains available; no program-object shape or IC changes. | Cached Type Objects receive the same request charge; nested calls cannot reset fuel; liveness is unchanged. | **Selected.** Complete fuel calibration is still required. |
| Count nesting only at explicitly type-positioned calls | A recursive ordinary helper can still crash an editor's evaluator. | Rust's termination safeguard motivates covering the work actually reached; it does not justify exempting helper calls. | Fewer counters but no bound on recursive body evaluation. | Recursion through ordinary calls or callbacks bypasses the nesting allowance. | **Rejected.** A type-position wrapper alone is insufficient. |
| Include ordinary function-body invocations while a type computation is active | Recursive helpers have an accountable failure; terminating recursion and ordinary JavaScript outside the computation remain available. | Retains the termination motivation of Rust const evaluation without copying its configurable lint policy. | A logical depth counter; optimized tail calls retain their specified charge; no shape or IC changes. | Shares sticky exhaustion through direct, mutual and callback recursion; it creates no reference and changes no liveness rule. | **Selected.** The portable numeric depth policy still requires calibration. |
| Catch a host stack overflow and report a type mismatch | Avoids a crash but points users at a supposed type error whose occurrence varies by machine. | Rust E0072 diagnoses layout, not available native stack space. | Defers work until resource failure and conflates implementation capacities. | A host failure proves neither infinite layout nor impossible narrowing. | **Rejected.** Keep host failure distinct from semantic proof. |
| Normalize an already invalid recursive declaration and recover with `any` or `never` | Can hide the real declaration error or invent downstream errors and autocomplete types. | Rust's diagnostic recovery is not a language rule admitting an invalid type. | Repeated graph traversal risks excessive work or overflow; no runtime IC advantage. | Recovery must not supply accepted contracts or reference facts. | **Rejected as language semantics.** Tooling recovery remains internal. |
| Reject established declaration cycles before downstream type analysis; preserve reference-bearing cycles | The declaration gets the diagnostic even when unused; valid linked structures keep their specified behavior. | Closely follows Rust E0072's need for indirection without importing Rust's exact layout rules. | Cycle validation can use graph algorithms; stops useless downstream work; no object-shape changes. | Applies existing layout predicates without changing type identity or reference liveness; unresolved inputs remain deferred. | **Selected.** Additional diagnostics are optional and cannot enable acceptance. |

Positive witnesses must accompany these failures: sufficient fuel, cold and populated intern tables, a subsequent independent computation, and admissible recursive reference positions. Exact-limit tests also distinguish spending the last permitted unit from requesting one more unit. These tests establish the stated boundaries; they do not certify all phase integration or general cache equivalence.

## Comparing legacy source under checking

Ordinary conformance tests must retain syntax-based checked-code applicability. engine262 also provides an explicit per-compilation `forceCheckedCode` host option for diagnostic probes of unchanged legacy Scripts. It requires the `runtime-types` feature, marks the Script and its descendants checked, and does not change parsing, strictness, declaration inference, or the source itself. Typed source needs no override. The option is not a language directive, a required host feature, or permission to reject legacy JavaScript by default. Direct eval retains the specified caller inheritance; indirect eval and dynamically constructed functions classify their own source.

The shared test observer records ScriptBody entry through a host callback and obtains a diagnostic record from the completion. Inserting an assignment before the candidate can disable a directive prologue, displace a hashbang or source span, and change effect analysis. A source-visible sentinel can also be overwritten by the candidate. Error class and body entry must be separate assertions: a program can throw `StaticTypeError` during execution, and an eval can fail before its own body after the caller has started.

The available testing directions are evaluated below. Rust's [UI-test guidance](https://rustc-dev-guide.rust-lang.org/tests/ui.html) separates compiler-error tests from execution expectations and supports explicit test configuration. That is an analogy for controlling the harness and asserting phases; Rust has no equivalent legacy-JavaScript participation boundary.

| Direction | Ergonomics | Prior art | Performance | Correctness | Other and decision |
| --- | --- | --- | --- | --- | --- |
| Wrap every legacy fixture in an annotated function | Convenient initially, but scope and strictness changes can hide the intended error and distort source locations. | Rust's separate compile/run expectations do not justify changing the program under test. | Extra parse structure; no useful production shape or IC effect. | The source is no longer the same Script; declarations and reference scopes can differ. | **Rejected for unchanged-source comparison.** Keep wrappers when function scope is the actual subject. |
| Add a new language directive or force checking globally | Easy activation, but can silently change unrelated legacy source and editor expectations. | Rust's test configuration is not precedent for a new JavaScript language opt-in. | A global setting complicates cache identity and isolation; no object-shape advantage. | Alters the agreed syntax-based boundary, including later compilations. | **Rejected.** A test convenience does not establish new language semantics. |
| Explicit per-compilation host override, automatic classification by default | Tests compare identical source and locations; typed fixtures stay simple. | Follows the separation between harness configuration and language outcomes in Rust UI testing. | Reuses classification and existing checking; no new program-object properties or IC dependencies. | Propagates through the same ownership graph without new references, lifetime changes or inferred contracts. | **Selected for optional checker probes.** Default-mode tests remain mandatory conformance evidence. |
| Prepend a source sentinel and inspect only the error name | Short assertions, but a wrong guess can pass for the wrong phase or error. | Rust distinguishes compiler failures and runtime outcomes rather than conflating every failure. | Cheap, but changes the analyzed source and its effects. | Can destroy directives or hashbang placement and can be reset by the program; names can be misleading. | **Rejected.** Instrumentation must not change the proposition under test. |
| Observe body entry from the host and assert the native error plus rule | Preserves source, diagnostic spans and meaningful failures. | Retains Rust's distinction between rejection and execution expectations. | One optional observer hook; no runtime object-shape or IC change. | Leaves effect/origin and liveness proofs unchanged; distinguishes runtime-thrown errors. | **Selected.** Nested source, modules and asynchronous settlement need their own boundary observations. |


## Declaration preparation and binding identity

Type declaration preparation must not depend on previously checked source. A type alias named `T` in an earlier realm cannot make a later value binding named `T` eligible for recursive type resolution. Each checking invocation owns temporary preparation evidence. Nested invocations suspend it and every exit restores or discards it, including rejection, exhaustion and host interruption. Eligibility depends on the actual uninitialized binding read and its declaration in the active group; it never depends on exception wording. See the specification's `sec-declaration-preparation-state`.

For example, after `type T = string;` was evaluated in one realm, engine262 previously accepted the following in a separate realm. Without that earlier source it threw a runtime `TypeError`:

```js
function make() { return 5; }
const T = make();
interface I { value: T; }
```

The selected correction preserves the runtime error for this runtime-dependent example. It does not introduce a new early-error family or broaden compile-time evaluation. Valid recursive interfaces still undergo the existing structural and default checks; a temporary unresolved reference is not an accepted `any` contract. Autocomplete must derive members from the resolved declaration, never from historical name matches or recovery placeholders.

Rust's [namespace rules](https://doc.rust-lang.org/reference/names/namespaces.html) distinguish type and value namespaces. That reinforces the need to identify what a name denotes, but it is not a direct implementation model for this proposal: Type Objects participate in this proposal's lexical binding and runtime evaluation rules. The choice therefore follows those rules rather than introducing Rust's namespaces.

| Direction | Ergonomics | Prior art | Performance | Correctness | Other and decision |
| --- | --- | --- | --- | --- | --- |
| Keep process-wide declaration spellings and recognize error text | The same file changes behavior with editor or realm history; inferred members may silently become permissive. | Rust's namespace distinction gives no support for matching unrelated bindings by text. | Cheap lookup but growing historical state; no useful shape or IC benefit. | Cross-scope contamination and wording-dependent acceptance violate binding identity. | **Rejected.** Diagnostic rendering cannot supply semantic evidence. |
| Clear a set of spellings at each checking entry | Removes some history dependence, but shadows still look identical and nested checking can erase outer evidence. | Still loses the declaration identity that Rust's resolution distinguishes. | Small set; restoring a stack is cheap; no IC advantage over identities. | Even a stack of names cannot distinguish same-spelled bindings or an actual read from a forged exception. | **Rejected.** Scope cleanup alone is insufficient. |
| Track opaque binding identities in activation-local groups and preserve read provenance internally | Predictable resolution and autocomplete; a wrong value binding keeps its existing error and phase. | Preserves the useful declaration-resolution principle from Rust while respecting this proposal's shared lexical rules. | Linear group setup, constant-time membership and weak side metadata on failed reads; no new program-object properties, shapes or IC dependencies. | Separates scopes, binding recreation and import targets; nesting restores prior state. Tokens need not retain bindings or values and create no references or lifetime extensions. | **Selected.** This is an abstract semantic requirement, not a mandated production-engine data structure. |
| Treat every unresolved type reference as `any` | Fewer immediate errors, but wrong annotations and misleading completion lists survive. | Rust rejects unresolved type obligations; its recovery does not make an invalid program valid. | Cheap recovery can cause later unsound assumptions; no relevant IC benefit. | Converts lack of evidence into a successful contract and can invent narrowing or liveness facts. | **Rejected as language semantics.** Tools may recover only without admitting the program. |
| Reject every uninitialized type read and remove recursive preparation | Simple errors, but valid recursive interfaces stop working. | Rust permits recursive structures through suitable indirection; its exact layout rules differ. | Simpler preparation; no program-shape advantage. | Contradicts the proposal's admitted recursive types. | **Rejected.** Preserve structural recursion checks and distinguish unrelated bindings. |

This correction isolates temporary recursion evidence. It does not establish transactional rollback of all declarations, caches or metadata, and it does not complete the specification's broader phase-integration and resource-policy work. Conformance evidence should pair cold and warm executions, successful and failed prior checks, ordinary and indirect binding reads, lexical shadows, nested checking, and valid recursive declarations.

## Module checking order and completion

Computed module checking follows the ordinary module evaluation order and completes before the candidate module body. Parsing and linking retain their earlier judgments. Asynchronous dependencies can delay this boundary even when the candidate has no top-level `await`. A failure rejects the module through the ordinary module rejection paths, preserves effects already produced by dependencies, and prevents dependent bodies from starting. The specification's `sec-module-type-checking-order` and `EvaluateModuleBodyWithTypeChecking` identify the synchronous and asynchronous entry points. This supersedes the conflicting statement that all computed type checking finishes before any module in a graph evaluates.

The checking pass is a logical obligation, not a mandated number of physical AST traversals. A cache or earlier internal computation must preserve inputs, acceptance, failure timing and effects. It cannot report success while evaluation remains pending or move a required pre-body error into execution.

In a cycle, preparation that requires an uninitialized imported binding fails at the candidate module's pre-body boundary with the existing type-evaluation diagnostic. The actual resolved binding matters, including through a re-export. This creates no implicit retry, cycle-wide scheduler, fallback type or reference lifetime extension. Explicit generic deferral and genuinely runtime-dependent checks keep their existing rules. This scheduling decision does not itself complete every imported-builder or declaration-preparation implementation path.

Rust's [constant-evaluation rules](https://doc.rust-lang.org/reference/const_eval.html) provide a useful distinction between restricted compile-time computation and ordinary execution. Rust does not supply an equivalent JavaScript module-evaluation graph with top-level await, so the scheduling analogy is limited. The closer ordering contract is the proposal's pinned [ECMAScript module evaluation machinery](https://tc39.es/ecma262/2025/multipage/ecmascript-language-scripts-and-modules.html#sec-source-text-module-record-execute-module).

| --- | --- | --- | --- | --- | --- |

| Execute imported bodies on demand while resolving a type | Some unavailable values appear to work, but dependency effects become difficult to predict. | Neither Rust const evaluation nor ECMAScript linking authorizes arbitrary runtime effects during type resolution. | Reentrancy, duplicated work and cache complications; no shape benefit. | Violates the evaluable fragment and ordinary module ordering. | **Rejected.** Loading declarations is not permission to execute a body. |
| Follow existing module prerequisites and check before each reached body | Stable error timing; uncalled invalid code is still checked and completed dependencies keep their effects. | Combines Rust's restricted computation principle with ECMAScript's actual module ordering. | One logical gate at an existing execution boundary; reusable summaries are possible; no ordinary object or IC changes. | Preserves participation, dependency failures, cycles, asynchronous ordering and reference liveness. | **Selected.** The specification patches both synchronous and asynchronous body entry. |
| Wait for every body in a cycle before checking any member | Cycles can cease making progress and editor diagnostics become scheduling-dependent. | Rust's module system is not a precedent for cyclic JavaScript initialization. | Requires a new barrier and cannot generally make progress. | A member may require its own check before it can supply the binding another member needs. | **Rejected.** Use the ordinary cycle traversal and binding availability. |
| Retry failed imported-binding reads after executing more bodies | A wrong guess can run code before a supposedly early error; repeated computations confuse diagnostics. | Rust's compile-time model does not justify a runtime retry scheduler. | Adds invalidation, replay and termination obligations; no IC advantage. | Changes effects and failure precedence, and can turn unavailable evidence into unsound acceptance. | **Rejected.** Required unavailable imports receive the defined type-evaluation failure. |

## Imported builders and lexical values

A checking environment must distinguish facts about a binding from the value that binding holds. An imported builder's function type describes its contract; the function itself remains the value called. The same distinction applies to imported constants, Type Objects and namespace objects. Temporarily binding an import to a Type Object made from its static type can silently replace the callee or its arguments. Follow the ordinary live binding instead, including re-exports and namespaces, and retain the original closure environment and function identity.

Imported code remains subject to compile-time evaluability. A locally immutable import of an exported `let` is still a read of mutable state. Inspect the original declaration and its lexical dependencies, including helper functions, before executing the builder; reparsing a detached function body loses this information. Valid local mutation within the builder remains admitted. Ordinary parameter, generic, receiver and return contracts remain in force, and the result must be a Type Object. An available function declaration can be called in a module cycle without executing its module body; unavailable captured values still fail under the existing module-checking boundary. See `sec-imported-builder-bindings`, `sec-iscompiletimeevaluable` and `sec-evaluatebuildercall`.

The closest binding precedent is [ECMAScript's indirect module bindings](https://tc39.es/ecma262/2025/multipage/executable-code-and-execution-contexts.html#sec-module-environment-records). Rust's [constant-evaluation rules](https://doc.rust-lang.org/reference/const_eval.html) likewise restrict computations and mutable state, but its `const fn` system does not supply JavaScript's live imports or closure semantics. Import syntax alone is therefore neither a purity proof nor a reason to reject an otherwise valid computation.

The engine correction and its module corpus establish named imports, direct namespace members, re-exports, lexical captures and representative specialization paths. They do not certify every higher-order callable, dynamically computed namespace access, cache policy or declaration-preparation form. Those remain part of the broader implementability and conformance review.

## Exported type declarations

Adding `export` to a type alias or interface must preserve its declaration-preparation scope, source order, recursive group and checking phase. A module should not accept a recursive interface through `interface I { next: I | null } export {I}` but fail when it is written `export interface I { next: I | null }`. An exported metadata shape must likewise be available to its governing `meta` declaration before the source's metadata judgments. Otherwise valid narrowing and intersection programs can fail, and an unrelated unclaimed-key diagnostic can hide the actual impossible test or missing default.

`sec-exported-declaration-preparation` makes export wrappers transparent to every existing preparation stage for these two declaration forms. Preserve the original declaration and binding: the body evaluator, recursive-resolution evidence, deferred checks and diagnostics must identify that same declaration. Named export lists and re-exports do not add local declarations. Keep the existing required-import failure, runtime-dependent resolution and generic deferral rules; this is not permission to execute ordinary export initializers or decorators early. No new diagnostic code is needed: the existing rule determines the failure.

[ECMAScript's export evaluation](https://tc39.es/ecma262/2025/multipage/ecmascript-language-scripts-and-modules.html#sec-exports-runtime-semantics-evaluation) delegates an exported declaration to its declaration evaluation; export lists do not evaluate another local declaration. [Rust visibility and re-exports](https://doc.rust-lang.org/reference/visibility-and-privacy.html) offer the limited analogy that making an item publicly accessible preserves the underlying item. Rust does not supply this proposal's runtime Type Objects, JavaScript temporal dead zones or asynchronous module schedule.

| Direction | Ergonomics | Prior art | Performance | Correctness | Other and decision |
| --- | --- | --- | --- | --- | --- |
| Leave declarations inside export wrappers to runtime | Publishing a type can break otherwise valid code; autocomplete and the checker can disagree about recursive members. A wrong guess costs a module initialization failure. | ECMAScript delegates exported declarations; Rust public access is not a distinct type-formation regime. | A smaller preparation walk, but missed metadata facts and inconsistent work later; no shape or IC benefit. | Changes recursive-group membership and required failure timing merely because a name is exported. | **Rejected.** Syntax placement cannot defeat an existing checking obligation. |
| Evaluate every export wrapper during preparation | Some declarations work, but value initializers and decorators can run before the programmer expects. | Neither ECMAScript exports nor Rust visibility authorizes arbitrary JavaScript effects during type preparation. | Executes extra user code and potentially constructs classes or objects early; can change initialization and IC observations. | Violates runtime effect order and the restricted evaluable fragment, with possible liveness consequences. | **Rejected.** Selection of type declarations is not Evaluation of export syntax. |
| Clone or reparse exported declarations into a synthetic scope | A simple example may work while diagnostics, captures or duplicate processing become confusing. | ECMAScript exports retain the declaration and its module binding; Rust re-exports retain the underlying item. | Additional nodes, environments and identity bookkeeping, without an object-shape or IC advantage. | Requires reconstructing source locations, lexical bindings and processing identity, and risks changing reference provenance. | **Rejected.** No synthetic declaration or scope is required. |
| Select the admitted exported type alias or interface at its original position, retaining its declaration identity | Local and exported spellings get the same type facts and diagnostics; autocomplete retains the same members. Invalid inputs fail at the established phase. | Follows ECMAScript declaration delegation and Rust's separation of access from item identity, while keeping this proposal's own runtime rules. | A linear declaration selection usable during binding; no new program-object properties, shapes or IC constraints. A production engine may integrate it with an existing traversal. | Preserves lexical scope, recursive groups, deferred resolution, source spans, processing identity, module order and reference liveness. | **Selected.** Apply the selection consistently to all preparation stages. |
| Introduce separate preparation or diagnostic rules for each export spelling | More special cases for authors and tools, with no useful difference in the underlying error. | ECMAScript export names do not create a second local declaration; Rust re-exports likewise preserve the item. | Duplicated checking paths and maintenance costs; no shape or IC improvement. | Can be made equivalent only by continually synchronizing the duplicated rules. | **Rejected.** Reuse the declaration's existing judgments and diagnostic identities. |

The portable module corpus covers exported recursive interfaces, cyclic imported inputs, metadata defaults and intersections, impossible tests in several control constructs, inhabited branches, and runtime-order controls. It observes original module body identities rather than inserting a source sentinel. This establishes the export boundary; it does not complete nested declaration preparation, rollback semantics, every metadata-shape form or the full checking-phase review.

## Generic alias constraint obligations

An alias's `where` clause belongs to the declaration selected by lexical resolution. It is checked over the bindings produced by the ordinary generic binder, including named arguments, defaults, empty or omitted argument lists, and packs. A separate scan keyed by the alias's name can reject valid shadowing, miss nested declarations, reverse named arguments, and lose obligations below a traversal depth limit. Reuse the resolved declaration and bindings instead. The rule is specified in `sec-generic-where`.

Retain an unresolved constraint when an enclosing generic parameter has not been bound, even if the alias's result type erases that parameter. Closing the enclosing application must close the constraint as well. A successful check belongs to the clause and its semantic inputs; a display string is not a cache key. In particular, same-spelled nominal types and signed zero must remain distinguishable. No new diagnostic family is required: a false specialization predicate still uses `RT_WHERE_UNSATISFIED` at the clause's source.

Rust's [scope rules](https://doc.rust-lang.org/reference/names/scopes.html) and [generic parameter rules](https://doc.rust-lang.org/reference/items/generics.html) support declaration-based resolution and the distinction between a generic declaration and its bound arguments. The analogy is limited: Rust's namespaces, inner-item restrictions and trait bounds differ from this proposal's JavaScript scopes, runtime Type Objects and executable Boolean predicates. These rules preserve this proposal's semantics rather than importing Rust's scope restrictions.

| Direction | Ergonomics | Prior art | Performance | Correctness | Other and decision |
| --- | --- | --- | --- | --- | --- |
| Keep a separate scan of top-level alias names | A harmless local rename can change rejection; autocomplete can show the inner alias while the error describes the outer one. Named/defaulted uses become surprising. | Rust resolves the actual declaration; spelling alone does not identify a generic item. | Simple initial scan, but duplicated traversal and argument interpretation; no shape or IC advantage. | Misses nested declarations and can apply the wrong clause or bindings. | **Rejected.** The normal resolver already owns declaration identity. |
| Repair the scan with another scope resolver and binder | Can match the intended behavior if both implementations remain synchronized; later syntax additions can drift. | Rust's declaration-based model motivates one semantic resolution rule, not two independent interpretations. | Duplicate scopes, argument handling and repeated syntax walks; no object-layout benefit. | Correctness depends on preserving identical defaults, named arguments, packs and deferral behavior in two paths. | **Rejected.** Do not duplicate the language's binding semantics. |
| Record obligations from ordinary generic resolution and binding | Local, exported and nested forms use the same facts as autocomplete. Invalid closed applications fail before execution and point to the actual clause. | Uses Rust's declaration/argument distinction without adopting its different namespaces or restrictions on inner items. | Obligations attach to existing resolution work; deduplicate equivalent bound inputs and reuse verified results. No new ordinary-object properties or IC dependence. | Preserves lexical identity, parameter kinds, named/defaulted/packed arguments, source locations and reference lifetimes. Retains dependence until substitution closes it. | **Selected.** This is the specification's semantic contract; representations remain implementation choices. |
| Defer every nested constraint until runtime use | Uncalled invalid code appears valid, and failure moves to whichever call first executes. | Rust does not generally excuse invalid generic uses because an enclosing function is uncalled; its exact validation model is different. | Less checking work initially, but repeated runtime work and later failures. | Violates the existing requirement to reject closed, determinable type errors before source-body entry. | **Rejected.** Deferral needs an unresolved semantic input. |
| Stop scanning at a fixed AST depth and accept the rest | Moving code into more blocks can silently disable a constraint. | Rust resource limits are not evidence that an unchecked obligation is satisfied. | Caps one traversal cheaply but changes the accepted language; no shape or IC benefit. | Confuses incomplete work with successful checking and bypasses the resource-failure rule. | **Rejected.** Resource failure must remain explicit. |
| Cache success by declaration name and displayed arguments | Diagnostics look stable while two different inputs can inherit one verdict. | Rust distinguishes items and const arguments semantically; textual display is not an identity rule. | Cheap strings, but formatting allocations and unsound reuse; no IC benefit. | Can merge shadowed declarations, nominal identities or signed zero; cannot justify reference facts. | **Rejected.** Reuse the existing clause and semantic-input identity machinery. |

The engine records alias obligations alongside function generic constraints, retaining multiple argument sets for one application node when enclosing specializations differ. Its portable cases establish nested and shadowed aliases, argument binding, representative enclosing specialization, module/eval/dynamic-function boundaries and runtime controls. They do not certify every external capture, imported alias, higher-order case, abrupt predicate or preparation form; the remaining checking-phase and cache review is still required.

## Specialization predicate completions

A closed `where` check has more outcomes than true and false. Once its inputs are available and its evaluation is required, an escaping throw is a type-evaluation failure before source-body entry. For example, `function F<T:type>():void where T.missing() {} function unused(){ F.<uint8>(); }` cannot pass checking because the invalid application is uncalled. The same rule applies to an alias constraint. A predicate that evaluates normally to false remains an unsatisfied constraint. A caught throw that produces a normal result is judged by that result; a skipped operand is not evaluated. Budget exhaustion takes precedence over either outcome and cannot be caught into success.

`sec-specialization-predicate-completion` specifies the ordered judgments: establish inputs and dependencies, apply an explicit deferral rule when required, evaluate in the original environment, check resource exhaustion, distinguish abrupt completion from normal failure, and record success only for a predicate that holds. This gives another implementation a completion rule to reproduce rather than a list of engine exception messages. Tests exercise that rule; they do not supply missing normative semantics.

Availability must be established before using a helper's result. For example, a helper that catches a premature read of an uninitialized external `const` and returns false has not proved that the real predicate fails. Returning true from the catch is equally unsafe: caching it could bypass a later runtime failure. A class's nominal type likewise does not supply static methods or final layout before its constructor and decorators have been evaluated. Preserve original declarations and environments, including transitive helper captures; do not run ordinary initializers or reconstruct closures to make an input appear available. Required imported inputs follow the existing module boundary and cycle-failure rule. A helper's own local temporal-dead-zone error during a legitimately started evaluation is a real evaluation failure.

[The Rust Reference's constant-evaluation rules](https://doc.rust-lang.org/reference/const_eval.html) make failures such as out-of-bounds indexing compilation errors in required const contexts. That supports distinguishing a failed required computation from a deferred one. The analogy stops short of this proposal's executable JavaScript predicates, catch/finally semantics, runtime Type Objects and live module imports. [ECMAScript's try-statement evaluation](https://tc39.es/ecma262/2025/multipage/ecmascript-language-statements-and-declarations.html#sec-try-statement-runtime-semantics-evaluation) supplies the completion rules within the evaluation; the proposal specifies how an escaping completion affects source checking.

| Direction | Ergonomics | Prior art | Performance | Correctness | Other and decision |
| --- | --- | --- | --- | --- | --- |
| Silently defer every thrown predicate | An invalid closed application appears usable until execution happens to reach it; editor acceptance is unreliable. | Unlike a required Rust const computation, failure is treated as permission to postpone judgment. | Less failure processing initially, with later repeated work; no shape or IC advantage. | An exception proves neither an unavailable input nor a satisfied constraint. It defeats pre-body rejection. | **Rejected.** Deferral needs a semantic reason established independently of the throw. |
| Convert every throw into false and report an unsatisfied constraint | The location is useful, but users are told their arguments failed a predicate that never produced an answer. | Rust distinguishes evaluation failures; ECMAScript distinguishes normal and abrupt completions. | Similar cost to preserving the completion kind; no layout benefit. | Loses the difference between a Boolean rejection and a broken computation; can conceal the actual failure. | **Rejected.** Preserve the completion category. |
| Propagate the original exception out of checking | Error names depend on whether the predicate throws an Error, a primitive or another value; tools cannot reliably classify a source-checking failure. | Ordinary ECMAScript runtime propagation is appropriate at runtime; Rust const checking supplies the closer phase analogy here. | Avoids a diagnostic wrapper but changes no steady-state object shapes or ICs. | Violates the source-checking `StaticTypeError` contract for a required type computation. | **Rejected.** Original runtime exceptions remain appropriate only on deferred runtime paths. |
| Establish eligibility first, then distinguish normal success, false, abrupt failure and exhaustion | Closed failures are reported at the clause before execution. Editors can point to the failing obligation; wrong inputs and broken predicates remain distinguishable. | Combines the required-evaluation distinction illustrated by Rust with ECMAScript's actual completion semantics. | Dependency summaries and internal readiness facts can be reused. Evaluation uses existing interpreter/compiler machinery; no new properties on program objects or IC assumptions. | Preserves lexical identity, runtime order, budget priority and reference liveness. Only completed success can justify reuse. | **Selected.** The normative result is independent of the implementation's traversal or representation. |
| Infer unavailability from `ReferenceError`, error text or Error-shaped properties | A user-thrown lookalike changes rejection timing; message localization can alter checking. | ECMAScript permits arbitrary thrown values. Rust const contexts do not justify interpreting error strings as readiness evidence. | Cheap string/class tests but unstable semantics; no IC benefit. | Confuses real local TDZ failures, missing names and unavailable external environments; caught premature reads still yield false facts. | **Rejected.** Use declaration/environment provenance before evaluation. |
| Execute surrounding statements or build substitute closures to obtain missing inputs | Some examples work, but effects, initialization timing and captures change unexpectedly. | Neither Rust const evaluation nor ECMAScript lexical environments authorizes arbitrary early JavaScript effects. | Extra execution, allocations and potentially different class shapes and IC observations. | Changes TDZ behavior, binding identity, decorator order and possibly reference lifetimes. | **Rejected.** Preserve explicit deferral and module-boundary rules. |
| Add a dedicated `RT_WHERE_EVALUATION` family | Makes predicate failures directly filterable, but gives users two codes for the same required-computation failure depending on its syntactic position. Clause locations already identify the predicate. | Rust illustrates the required-evaluation distinction; it does not dictate JavaScript diagnostic family granularity. | Equivalent checking and object-layout cost; one more public diagnostic category. | Sound if specified separately, but duplicates the general evaluation-failure category without a different completion rule. | **Rejected.** Keep the semantic failure category shared; the clause location supplies the more specific context. |
| Reuse `RT_TYPE_EVALUATION` and retain `RT_WHERE_UNSATISFIED` and `RT_TYPE_EVALUATION_LIMIT` | Tools keep three meaningful distinctions and the original clause location. Users can investigate a failed computation separately from rejected arguments. | Follows the broad distinction between compilation/evaluation failure and an unsatisfied constraint; exact identifiers are this proposal's own convention. | Existing diagnostic machinery and generated catalog; no runtime object-layout changes. | Matches the existing checking wrapper's general type-evaluation category without changing runtime exceptions or making the registry normative. | **Selected.** Clarify the provisional family's explanation and normative reference now; no need to await every future error. |

The engine implementation uses the existing lexical evaluability traversal with an availability predicate and lexically resolved free references, defers unevaluated class inputs recursively through compound type records, and reports an escaping closed-predicate throw at the clause. Error constructors are admitted for this predicate path as for type builders. The portable corpus records original sources, body-entry observations, completion class and diagnostic identity/location. Additional host tests check exhaustion precedence and environment restoration. This work does not certify every higher-order call, imported alias declaration, captured binding, nested preparation path or cache dependency; those remain part of the broader independent-implementation and conformance review.

## Recursive interface formation

A recursive interface must describe the same member contract in a block or function as it does at top level. Previously, the engine's source-level preparation could swallow an uninitialized recursive member reference and replace its type with `any` or an empty function signature. Nested declarations, without that preparation context, instead threw a native `ReferenceError`. Neither result implements the declared contract. For `interface N { next: N | null }`, a value whose `next.next` is `5` is not an `N`; successfully forming the declaration must not erase that fact.

`sec-recursive-interface-resolution` specifies declaration-based graph formation in the declaration's actual environment. The temporary node represents a recursive edge, not a permissive type. Complete the graph before publishing a successful result, preserve generic arguments and all member positions, and discard pending evidence on failure. A forward type reference does not initialize an ordinary value binding or execute the enclosing scope. Lexical resolution still distinguishes an interface from a same-spelled value or parameter. Existing closed-cycle Early Errors, runtime-dependent exceptions, import availability and reference-liveness rules remain applicable.

[Rust's recursive-type rules](https://doc.rust-lang.org/reference/types.html#recursive-types) permit recursive nominal types subject to finite-size restrictions; they do not erase recursive fields. The analogy is limited: Rust requires nominal participation in recursion and does not provide this proposal's structural aliases, JavaScript runtime Type Objects or dynamic lexical initialization. [ECMAScript's declarative binding read](https://tc39.es/ecma262/2025/multipage/executable-code-and-execution-contexts.html#sec-declarative-environment-records-getbindingvalue-n-s) retains the uninitialized-binding error for ordinary value reads. Type-graph formation must coexist with that behavior.

| Direction | Ergonomics | Prior art | Performance | Correctness | Other and decision |
| --- | --- | --- | --- | --- | --- |
| Reject every uninitialized interface reference | Nesting or reordering a valid declaration breaks it; autocomplete can describe a contract the runtime refuses to form. | Rust permits eligible recursive nominal declarations. | Minimal formation machinery; no shape or IC benefit beyond omitting required work. | Confuses a known declaration's recursive type edge with an ordinary value read. | **Rejected.** Recursion is part of the admitted type language. |
| Replace unresolved members with `any`, missing contracts or empty signatures | Declarations appear to work, but invalid deep values pass and editor facts overpromise enforcement. | Rust recursion retains its field types. | Less graph construction initially, but weaker contracts cannot support the intended optimizations. | Loses properties, parameter/result contracts and generic dependence; supplies false evidence to typed boundaries. | **Rejected.** An incomplete graph is not a successful permissive type. |
| Put every nested declaration into the enclosing source's preparation group | Some recursion works, but captures and shadowing can resolve to the wrong activation; errors occur before required values exist. | Rust's static items do not justify flattening JavaScript environments. | Larger eager traversal and startup work; can force unnecessary computation and allocations. | Conflates binding identities and crosses runtime/environment boundaries, potentially changing liveness. | **Rejected.** A declaration retains its own lexical scope and formation prerequisites. |
| Initialize all forward interface value bindings immediately | Forward type references work, but ordinary expression reads silently lose their TDZ behavior. | ECMAScript separates declaration instantiation from initialization; Rust supplies no matching dynamic value-binding rule. | Can reduce later resolution work, but changes observable initialization and cache assumptions; no object-layout requirement warrants it. | Converts type resolution into value hoisting and can change effects and failure order. | **Rejected.** Existing source preparation is the only authority for its own early initialization. |
| Retain a graph keyed by declaration and actual binding identity, with ordinary generic binding | Recursive members remain visible to autocomplete and enforced at every depth. Wrong values fail at the existing boundary. | Preserves the recursive-type distinction illustrated by Rust and JavaScript's separate value initialization. | Shared internal graph nodes bound work by the declarations/edges visited. A production engine can use binding handles and compiled summaries; no program-object fields, shapes or new IC assumptions are needed. | Preserves scope, argument identity, complete member contracts, failure cleanup and reference lifetimes. | **Selected.** Required semantics do not depend on copying this interpreter's traversal. |
| Cache pending resolution by identifier spelling or parsed declaration alone | Repeated calls or same-spelled declarations can inherit another environment's partially formed result. | Rust's declaration model does not supply JavaScript activation identity. | Smaller keys, but invalid reuse; no shape or IC advantage. | Ignores captured inputs, actual binding identity and failed formation. | **Rejected.** Temporary formation evidence belongs to the active resolution and its environment. |
| Add separate errors for recursion in blocks, loops, functions and modules | More error codes without a new language violation; users must learn arbitrary placement restrictions. | Rust's finite-size rule concerns a type, not a diagnostic for every syntax container. | More rule paths and maintenance, with no runtime layout benefit. | Duplicates or contradicts existing type-validity and phase rules. | **Rejected.** Reuse the existing failure categories and fix formation itself. |

The engine forms interface graphs without interning incomplete member shapes, uses binding identity for active recursive resolutions, and evaluates a forward declaration in its own environment. It retains native failures for unrelated value bindings and leaves expression-position TDZ behavior intact. The portable cases cover nested scopes, recursive members and signatures, generic/alias edges, valid and invalid values, source/module boundaries and failure cleanup. This does not complete the broader questions of runtime captures across repeated instantiations, arbitrary computed declarations, imported alias obligations, phase precedence, failure commit or resource/cache portability.

## Interface identity across activations

Forming complete recursive graphs is insufficient if the completed Type Object is interned by a source Parse Node alone. A local `interface N { value: T }` can capture a different `T` on each call. Reusing the first call's Type Object can accept invalid values, reject valid ones, conflate reflection and Map keys, and apply partial members to the wrong declaration. This is a type-identity defect, not a new early-error category.

The selected rule is generative interface declaration identity: one identity per actual primary binding instance, retained by forward/recursive resolution, preparation, generic applications, aliases, imports and reflection. A new activation creates a distinct interface even when its captures happen to be equal. This is an intentional clarification of nominal identity, including the observable `===` result. It does not make structurally identical aliases distinct, hoist ordinary value bindings, execute an uncalled scope or grant reference liveness. Ordinary membership can remain structural while nominal interface-to-interface relations distinguish declarations. The normative rule is `sec-interface-declaration-identity`; SameType compares the identity as well as the Parse Node and generic arguments.

[Rust items](https://doc.rust-lang.org/reference/items.html#itemsstatic-def) are determined at compile time and generally fixed during execution. That supports a declaration-based nominal distinction but is not an analogy for a JavaScript declaration evaluated repeatedly with runtime captures. [ECMAScript declarative environments](https://tc39.es/ecma262/2025/multipage/executable-code-and-execution-contexts.html#sec-declarative-environment-records) supply the closer binding model. The selection below is this proposal's design judgment, rather than a claim that Rust has this runtime identity rule.

| Direction | Ergonomics | Prior art | Performance | Correctness | Other and decision |
| --- | --- | --- | --- | --- | --- |
| Intern only by Parse Node and explicit arguments | A second invocation silently keeps the first contract; autocomplete can describe fields that enforcement misreads. | Rust's static items cannot justify ignoring dynamic JavaScript captures. | Few Type Objects, but stale contracts cannot support sound optimization. | Conflates activations, partial contributions and failed/successful results. | **Rejected.** Source identity alone is insufficient. |
| Mutate one shared Type Object to the most recently formed contract | Old variables, reflection and registry keys change meaning after an unrelated call. | Neither Rust nominal items nor ECMAScript binding identity implies last-call-wins contracts. | Requires invalidating every dependent shape/IC assumption on each formation. | Changes previously published typed boundaries and caches. | **Rejected.** A later activation cannot rewrite an earlier declaration. |
| Reject local interfaces or all captured inputs | Predictable restriction, but moving valid code into a helper breaks it and costs users manual generic plumbing. | Rust's compile-time item restrictions are a limited analogy; this proposal admits runtime type values and nested declarations. | Simplifies formation and caching, at the cost of the admitted language. | Avoids conflation by withdrawing supported behavior and does not specify repeated closed declarations. | **Rejected.** No such restriction is needed for correctness. |
| Treat interfaces as structural aliases | Equal shapes share Type Objects, but nominal relationships and type-keyed registries lose the declaration distinction. | Rust nominal types are not merged solely by shape; erased structural systems have different runtime commitments. | Shares shapes effectively, but requires recursive contract comparison to decide identity. | Contradicts the specification's nominal interface kind and declaration-based relations. | **Rejected.** Structural membership does not imply structural nominal identity. |
| Intern by a computed capture vector or completed member shape | Equal-looking factories can share an identity, but hidden dependencies, closures, defaults and future partial members affect the result. | Rust generic argument identity is useful only for explicit complete inputs, not arbitrary JavaScript lexical dependencies. | Requires dependency discovery, snapshots and invalidation beyond ordinary generic binding; object identity and mutable captures complicate cache keys. | A partial capture/shape key can merge different obligations; partial contributions would still need an activation owner. | **Rejected as nominal identity.** Such summaries may optimize work only when they preserve the specified distinct identities. |
| One interface identity per actual primary binding instance | Users can rely on a declaration keeping its own captured contract. Autocomplete retains the source declaration and fields; a registry intentionally sharing a nominal interface can hoist its primary binding. | Fits ECMAScript lexical activations and the existing distinction between nested declaration instances; Rust's nominal model supports declaration distinction but has no identical runtime rule. | Opaque constant-size handles; code and immutable shape summaries can still be shared. No extra program-object properties or IC layout changes are required. | Preserves captures, forward references, generic arguments, aliases, imports, reflection, failure separation and partial ownership without comparing closure state. | **Selected.** The language result is independent of cache strategy and implementation effort. |
| Create a fresh identity on every resolution or specialization request | Two reads of one type compare unequal and Map keys stop being reusable. | Neither Rust type equality nor ECMAScript binding reads imply freshness on lookup. | Repeated allocations and missed caches; no semantic benefit. | Breaks Type Object interning, recursive edges and equal applications of one binding. | **Rejected.** Freshness belongs to binding creation, not a read or rebuild. |

The engine carries the existing opaque binding token into formed interface records, compares it in nominal identity/family relations, and keys runtime partial contributions by that token. Runtime class publication resolves its actual `implements` targets in the class environment and keeps inherited and self-referential contracts, instead of treating a checker's symbolic interface record as a match for every activation. Concrete constructors retain their own resolved contracts. It does not add observable fields to program objects or retain an environment through the token. Portable tests distinguish same-binding reuse from separate activations, captured members and recursive edges, generic applications, typed boundaries, partial members, reflection, aliases and modules. This does not complete every captured default, bound or predicate path, nor the corresponding identity audit for other declaration kinds, failure-commit semantics or portable resource/cache accounting.
