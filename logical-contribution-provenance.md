# Logical result contribution provenance

`&&`, `||` and `??` return an operand value. Their result's declaration evidence follows the operands that can supply that value under the existing static result rules. A known result type alone is not an annotation, and an annotation used only to decide whether another operand executes does not annotate that operand.

For example, `function make() { return true && { x: "s" }; }` remains unparticipating. Writing `const flag: true = true; return flag && { x: "s" };` in the body does not change that: `flag` cannot supply the expression's result. By contrast, `return true && { x: "s" := string };` retains the surviving member's annotation and anchors the object contribution. An unchanged local naming any of these expressions retains the same result evidence.

The short-circuit contribution is the left operand's falsy part for `&&`, truthy part for `||`, and non-nullish part for `??`. The right operand contributes only when the left can permit its evaluation. Filter alternative origins by that same selection before combining their evidence. If an alternative's values cannot contribute, neither can its annotations. A selected singleton annotation still counts, including an explicit conversion to a singleton or `null` type. Explicit `any` erasure remains erased.

This matters inside a nested expression. In `(flag ? { x: "s" := string } : false) && "s"`, the object's annotation supplies no result evidence: the object only causes evaluation of the literal right operand. For `(flag ? null : { x: "s" }) ?? { x: "s" := string }`, both object alternatives can supply the result; a subsequent `.x` retains both origins even though the structural types may be equal. An unrelated annotation on `flag` supplies no additional evidence.

Preserve these distinctions through conditional arms, nested logical expressions, unchanged aliases, inferred bindings, imports, generic contexts and subsequent member reads. Keep each operand's applicable guarded and contextual environment. A declared or participating published aggregate/callable contract remains independently authoritative; a private inference answer supplies no independent contract. An inferred immutable initializer's participation and a return contribution's anchoring use their existing rules on the surviving operands, rather than treating every syntactic child as a value producer.

The expression's Static Type still comes from the existing logical-result and contextual-adaptation rules. Origin projection determines evidence, not a narrower array element domain or a new literal conversion. Preserve existing unreachable-operand and impossible-test diagnostics, including their precedence. This work does not make previously prohibited dead tests valid.

Checking executes no operand, getter, iterator or function body to discover a type. Runtime short-circuit order, effects, object identity, receiving checks, failed binding state and reference liveness are unchanged.

## Requirements and decision

A valid direction must preserve operand-value derivation, singleton annotations, erasure, guarded contexts, surviving alternative origins and ordinary expression types. It must distinguish independent published contracts from private answers and must not execute source code during checking.

| Direction | Ergonomics, autocomplete and wrong-guess cost | Prior art including Rust | Real-engine performance | Correctness and liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Anchor every logical expression with a known result | Adding `true &&` to a literal unexpectedly publishes a contract, changes editor information and moves failures before evaluation. | Rust's lazy operators produce Boolean values from Boolean operands; they do not justify this JavaScript publication gate. TypeScript's static inference is erased. | Cheap classification, but adds unnecessary inference and admission. No object-shape or IC benefit. | Confuses type knowledge with annotation provenance. | Reject. |
| Combine evidence from every syntactic operand | A control annotation or an excluded alternative changes an unrelated value's contract. A refactor can introduce new early errors. | Rust guarantees lazy evaluation, not provenance from unselected JavaScript operand values. | A single aggregate bit is cheap but loses information needed for selection. No runtime layout advantage. | Violates value derivation and loses erasure/alternative distinctions. | Reject. |
| Erase evidence at every logical operator | Useful contracts disappear behind a common conditional idiom; known mistakes move to runtime. | Rust preserves established types through expressions; TypeScript preserves narrowed operand information. Neither recommends blanket erasure. | Avoids analysis by discarding required information; does not improve IC stability. | Loses declared and participating result contracts. | Reject. |
| Execute operands or inspect current values to choose evidence | Editor answers and checking depend on effects and initialization order; a wrong guess can run user code. | Rust's lazy operators describe runtime control flow, not permission to execute arbitrary bodies during type analysis. | Unbounded effects obstruct predictable caching and engine optimisation. | Violates checking phases and can observe stale or non-live references. | Reject. |
| Project each available origin through the existing logical selection, then combine surviving evidence separately from the result type | Equivalent aliases and operand spellings retain useful contracts without inventing annotations. Known errors keep their specified phase. | Rust provides a close analogy for conditional evaluation, but its Boolean-only operators and ownership model do not determine JavaScript's gradual inference gate. TypeScript provides a comparison for truthiness narrowing, without runtime enforcement. | Compiler-owned provenance can share the existing expression/dependency graph. No public object fields, wrappers, new shapes or IC keys are required. | Preserves declaration identity, contextual typing, erasure, impossible alternatives, private answers and reference rules. | Choose independently of implementation effort. |

These performance statements are design analysis, not measurements. [Rust lazy Boolean operators](https://doc.rust-lang.org/reference/expressions/operator-expr.html#lazy-boolean-operators) specify Boolean operands and conditional right-operand evaluation. [TypeScript truthiness narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#truthiness-narrowing) illustrates narrowing across JavaScript truthiness tests. Neither defines this proposal's annotation-seeded runtime publication policy.
