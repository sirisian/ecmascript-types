# Optional-chain contribution provenance

An optional chain retains declaration evidence from the member read or call that supplies its live result. `?.` does not itself annotate that result. For example, `function make() { return ({ x: "s" })?.x; }` remains unparticipating; giving `x` a String contract anchors the contribution. An unrelated typed member, computed key or call argument supplies no evidence to the selected value.

At each optional boundary, remove nullish receiver alternatives under the existing typing rule while retaining the surviving origins for subsequent reads and calls. Equal structural types may carry different evidence. A conditional receiver must not gain or lose an anchor merely because narrowing selects one canonical representation. The existing receiver and result types remain authoritative; origin retention does not narrow an array's uniform element or member domain.

Where the chain may short-circuit, its generated `undefined` alternative supplies no declaration evidence. This is distinct from a live member or call with an explicitly declared `undefined` result, which retains its annotation. A nullish receiver annotation is control evidence, not an annotation on the generated result. A private callee answer remains private; a declared or participating published result retains its independent contract.

Preserve these distinctions through nested chains, unchanged local aliases, inferred immutable bindings, capture, imports, namespace selection, generic specialization and subsequent logical selection. Apply each live member/call's existing return-anchoring and immutable-initializer participation rules separately. The chain's keys, arguments and nested syntax still undergo their required checks. Parentheses end a chain, and optional calls preserve a property receiver only where ordinary evaluation preserves that reference.

The specification already permits redundant optional access on a known non-nullish receiver. That receiver makes the guard redundant but leaves the written continuation reachable. An always-nullish receiver instead makes the written chain unreachable and retains the existing dead-chain error. Apply the distinction consistently in value positions, conditions, equality tests and switches. Computing the result type of an always-nullish chain does not waive its diagnostic. Nullishness is not truthiness: `0`, `false` and the empty String are present values.

These judgments execute no getter, function, initializer or argument to discover a type. They do not change ordinary evaluation order, skipped effects, identity, receiving checks, failed-state behaviour, reference permissions or reference liveness.

## Contribution decision

A valid solution must preserve live value derivation, independent contracts, erasure, generated absence, alternative origins and existing types. It must not borrow control evidence or execute source code during checking.

| Direction | Ergonomics, autocomplete and wrong-guess cost | Prior art including Rust | Real-engine performance | Correctness and liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Anchor every known optional result | Adding a defensive `?.` publishes a contract and can turn a runtime failure into an unexpected early error. | Rust's `Option` carries an established payload type; its wrapper is not evidence for this JavaScript annotation gate. TypeScript's checks are erased. | Cheap classification, but unnecessary publication and admission; no shape or IC benefit. | Confuses known type/absence with declaration evidence. | Reject. |
| Inherit every receiver/key/argument annotation | An unrelated annotation changes the selected value's contract and editor information. | Rust `Option::map` derives its successful output from the mapping operation, not from another unrelated input. | An aggregate bit discards the distinctions needed by member selection; no runtime layout advantage. | Violates value derivation and gives skipped paths evidence they do not supply. | Reject. |
| Erase every optional result | Useful declared and published contracts vanish behind common optional access, delaying known failures. | Rust preserves the output type of `map`/`and_then`; TypeScript preserves optional member/result information. | Avoids analysis by dropping required information, without improving IC stability. | Loses live contracts and conflicts with ordinary member/call rules. | Reject. |
| Execute the receiver, getters or calls to select evidence | Checking and autocomplete depend on effects and initialization timing. Wrong guesses may run user code. | Rust's Option combinators describe runtime operations, not permission to execute arbitrary code during type analysis. | Unbounded effects obstruct predictable compilation and caching. | Violates phases and can observe stale or non-live references. | Reject. |
| Retain live origins and add a separate unanchored absence alternative | Defensive spelling and equivalent aliases preserve the selected contract; known mistakes retain their required phase. | Rust's `Option::map` and `and_then` distinguish successful transformation from absence. Their explicit sum types and ownership rules differ from this proposal's gradual publication policy. TypeScript supplies an optional-chain analogy without runtime admission. | Compiler-owned origin metadata can share existing expression/dependency graphs. No wrappers, public fields, new shapes or IC keys are required. | Preserves declaration identity, erasure, private answers, actual types, effects and reference rules. | Choose independently of work required. |

## Redundant-access diagnostic decision

| Direction | Ergonomics, autocomplete and wrong-guess cost | Prior art including Rust | Real-engine performance | Correctness and liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Reject every statically settled optional guard | Tightening a receiver type breaks an otherwise useful defensive chain; no written continuation is dead on a non-nullish receiver. | Rust can apply Option transformations to a known `Some` value. It does not justify this mandatory rejection. | Rejecting earlier saves no necessary runtime work; an engine can remove a proved redundant guard. | Contradicts the specification's explicit permission for non-nullish receivers. | Reject. |
| Permit both known-present and always-nullish chains | Uniform permissiveness, but the latter silently retains a written continuation that cannot execute. | Rust's `None.map(...)` is valid, but Rust does not share this proposal's mandatory unreachable-code rules. | Both can be folded without changing shapes/ICs. | Reopens the established always-nullish dead-chain rule and its diagnostics. | Reject for this proposal. |
| Permit known-present redundancy; retain the always-nullish diagnostic | Preserves useful defensive access while reporting an unreachable written continuation. The two cases have distinct reasons visible in an editor. | Rust and JavaScript optional operations support present/absent reasoning; the dead-chain diagnostic is specific to this proposal. | The existing nullish-domain judgment suffices; no runtime layout change. | Satisfies both existing specification commitments, consistently across expression contexts, without changing liveness. | Choose. |

The performance discussion is design analysis, not a benchmark. [Rust Option](https://doc.rust-lang.org/std/option/enum.Option.html) documents `map` and `and_then`; [TypeScript 3.7](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html) describes optional property, element and call operations and their nullish short-circuiting. Neither defines this proposal's annotation-seeded publication policy.
