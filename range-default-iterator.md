# Default range iteration

A built-in range's `[Symbol.iterator]()` returns a fresh forward numeric cursor. Its static result uses the same contract as `step` and `reverse`: a helper-bearing synchronous iterator with cursor item `I`, completion `undefined`, and optional `any` input to `next`. Its self-iteration returns an iterator with those same three protocol arguments. The source range remains reusable; the cursor is stateful and returns itself from self-iteration.

Derive `I` by [range-iterator-results.md](range-iterator-results.md). In particular, the endpoints of `ClosedRange.<1 | 3>` do not restrict its items to that union: it also yields `2`. A supported concrete domain preserves its complete type; an endpoint-reading `RangeBounds` view uses the documented fallback upper bound. Unsupported, erased or unresolved domains remain gradual. The static result does not guarantee successful acquisition, a first item or termination. Default iteration still needs a forward origin, validates its numeric domain and preserves fused completion and failure state.

`next()` returns `{ value: I, done: false } | { value: undefined, done: true }`. A direct `.value` read includes exhaustion. The cursor ignores sent values. This does not make the range itself an iterator, give it a `next` method, or bind `this` when its iterator method is extracted.

|---|---|---|---|---|---|
| Keep the default method gradual while explicit cursors are typed | The common spelling loses useful completion and item information; wrong guesses evade checking. | Rust `IntoIterator` associates both `Item` and `IntoIter`; leaving the conversion untyped loses that relationship. | No necessary runtime saving; discards specialization opportunities. | Conservative but inconsistent with established cursor facts. No liveness benefit. | **Reject.** |
| Use endpoint `T`, or always Number | Simple autocomplete, but falsely excludes interior literals or loses typed numeric/BigInt carriers. | Rust's associated `Item` is not this proposal's endpoint-reading view. | Cheap but creates invalid representation assumptions. | Disagrees with the runtime cursor; no reference argument repairs it. | **Reject.** |
| Make the range its own cursor | Fewer objects, but a second traversal unexpectedly resumes or exhausts shared state. | Some Rust ranges are iterators themselves; that does not determine this proposal's reusable range semantics. | Could save a cursor allocation but changes state/shape and observable identity. | Violates existing fresh-cursor behavior and risks conflating cursor state with source/reference lifetime. | **Reject.** |
| Reuse the established cursor item/completion/input contract | Autocomplete describes the usual traversal and exhaustion accurately; known wrong uses fail early. | Follows Rust's association between iterable conversion and item type, using ECMAScript's mutable Symbol hook and result objects. Rust ownership/borrowing is not JavaScript property lookup. | Reuses type queries and cursor/result shapes. Engines can specialize with existing property and call IC guards. | Matches existing numeric acquisition and item admission without granting reference authority or extending lifetimes. | **Recommend.** Chosen independently of implementation effort. |

## One read contract, ordinary property effects

The well-known Symbol must be established, including the ordinary dot/computed spelling on the unshadowed `Symbol` intrinsic, a known constant key and computed object-pattern extraction. An unrelated Symbol or shadowed `Symbol` name does not select this contract. Optional access keeps its normal short circuit and diagnostics. Whole `any` receivers remain gradual. Mutable extracted callees keep the ordinary stability rules.

The member query supplies the same default protocol to existing static iteration, flattening and delegation consumers. Stored literal-endpoint ranges therefore contribute the cursor domain to loop variables, typed spread destinations and pattern consumers. `yield*` derives yielded items separately from `undefined` completion. Existing literal-loop counter facts remain separate, and consumers with unresolved protocol alternatives retain their usual uncertainty. Inferring a protocol contribution does not promote an ordinary Array literal to typed storage; `const xs = [...r]` retains the existing gradual Array policy. An explicit typed destination still checks known spread items. Ordinary Array indexed storage does not prove its replaceable iterator's behavior.

| Direction | Ergonomics / autocomplete / wrong guesses | Prior art | Real-engine performance | Correctness / reference liveness | Other / decision |
|---|---|---|---|---|---|
| Add the method as permanent readonly range storage | Convenient structural shape, but users lose existing replacement behavior. | Rust trait selection is not mutable ECMAScript method storage. | Could simplify guards only by changing object shape/semantics. | A static read contract does not authorize freezing or closing range objects. | **Reject.** |
| Duplicate endpoint/item rules in every consumer | May look consistent until one consumer infers a different carrier or completion. | Loses the shared associated-item principle. | Duplicated type work and inconsistent caches; no runtime gain. | Encourages drift; no extra reference capability is justified. | **Reject.** |
| Share the read/protocol query and retain ordinary lookup and receiving checks | Equivalent established reads agree; replaced hooks remain observable, and bad values fail at the typed destination. | ECMAScript GetIterator performs property lookup; Rust supplies only the analogy of a shared item association. | No new public fields, wrappers or shapes. Guarded elision remains possible. | Preserves getter/call order, abrupt completion, failed-initialization TDZ and liveness. | **Recommend.** No hook, callback or next call executes during static checking. |

## Literal fit, unknown endpoints and metadata effects

The default protocol does not replace a fresh range literal's established produced-element fit judgment. A literal spread into an array, tuple rest or function rest with a bounded numeric destination retains that judgment, including empty intervals and excluded sentinels. A stored range continues to contribute its established cursor domain. When a written endpoint is unknown, a different known Number endpoint does not prove Number items: the unknown endpoint can select a typed numeric carrier at runtime. Preserve uncertainty unless a receiving context independently establishes the obligation. For uncertain spread routing to fixed numeric parameters, the broad literal protocol alone cannot prove every argument count impossible: distinct positions may have different numeric domains. Retain their runtime receiving checks; do not apply one position's bound to the whole source interval.

| Direction | Ergonomics / autocomplete / wrong guesses | Prior art | Real-engine performance | Correctness / reference liveness | Other / decision |
|---|---|---|---|---|---|
| Compare every literal's broad protocol type to its destination | Rejects established fitting byte spreads and empty intervals. | Rust uses concrete iterator item types, but does not have this proposal's contextual numeric literal admission. | Cheap but defeats existing fit analysis; no shape benefit. | Contradicts the produced-element fit rule. | **Reject.** |
| Retain fit for fresh literal consumers and uncertainty for unknown endpoints | Existing literal idioms work; autocomplete makes no unsupported carrier claim. | Rust supports context-directed numeric literals; ECMAScript dynamic endpoint values limit the analogy. | Reuses static bounds analysis and existing receiving checks; no wrappers or new shapes. | Keeps endpoint storage, item fit and carrier evidence separate; liveness unchanged. | **Recommend.** |
| Infer Number from one known endpoint when the other is unknown | Attractive precision, but valid typed carriers fail an invented Number boundary. | Rust's statically fixed endpoint types do not justify this inference from an unknown JavaScript value. | Unsound specialization can require deoptimization or reject valid values. | The missing endpoint evidence cannot prove a carrier. | **Reject.** |

Receiving admission of an inferred metadata-bearing item may invoke validation after the cursor's `next` call has returned. That is outside the cursor's active reentry guard. The cursor reentry test therefore uses an explicit `any` receiving binding to isolate validation during item production; a separate test preserves the observable effects of subsequent inferred receiving admission.

The available directions are: (1) elide receiving metadata validation based only on the intrinsic-looking method name; reject because replacement prevents that identity proof, wrong guesses become unsound, and any performance gain would require independent guards; (2) keep the cursor guarded through later receiving operations; reject because it changes the guard's lifetime and ordinary call/effect order without a reference-liveness basis, adds state management, and makes autocomplete unable to explain when a cursor becomes available; (3) retain both established boundaries and test them independently; **recommend**. The third direction keeps ordinary metadata hooks and receiving obligations, needs no new public shapes or wrappers, and has no extra reference authority. Rust borrowing constrains aliasing while an iterator is borrowed; it does not justify holding a JavaScript reentry guard after `next` returns. Test setup must expose which boundary it intends to observe, rather than suppressing required validation globally.

## Loop entry admission

A simple loop binding whose type is inferred from its source protocol has an initialization boundary, just as an ordinary inferred binding does. Apply the established inferred type before the loop body and retain it for later stores. Resolve captured generic parameters in the current type context. An explicit annotation keeps its own admission; explicit `any` remains gradual. Destructured bindings continue through their existing extraction/admission path. Reference iteration keeps its existing location and liveness rules.

The implementation previously published this inferred type during checking but enforced only the separate numeric type inferred from body uses. A replaced iterator could therefore put a String into a variable checked as `uint8`, and a later typed initialization could incorrectly elide its check. The repair reuses ordinary inferred-binding admission at simple loop entry. Failure follows the existing loop path: skip the body, restore the environment and close the iterator, preserving earlier effects.

| Direction | Ergonomics / autocomplete / wrong guesses | Prior art | Real-engine performance | Correctness / reference liveness | Other / decision |
|---|---|---|---|---|---|
| Keep the inferred type only in the checker | Tools promise numeric operations that can receive other values after replacement. | Rust's inferred loop type is an actual contract, not a suggestion. | Cheapest entry but makes downstream elision/optimization unsound. | Allows invalid values into checked code. | **Reject.** |
| Wrap every iterator or freeze the hook | Adds identity changes or removes existing mutation; errors can move to acquisition. | Neither Rust nor ECMAScript implies a mandatory wrapper for this boundary. | Extra allocation, shapes and call IC variants, or changed object semantics. | Does not belong to reference-liveness rules and changes effects unnecessarily. | **Reject.** |
| Admit the inferred loop binding at its existing initialization boundary | Known loop types remain dependable; explicit gradual bindings retain their intended behavior. | Closest to an inferred Rust loop variable, with this proposal's dynamic admission and JavaScript closing semantics. | Reuses binding machinery; engines may elide checks with an independent source proof. No new object shape or wrapper. | Prevents body entry on failed admission, substitutes generic captures and keeps subsequent stores constrained. | **Recommend.** |

Primary references: [Rust IntoIterator](https://doc.rust-lang.org/std/iter/trait.IntoIterator.html) and [ECMAScript GetIterator](https://tc39.es/ecma262/multipage/abstract-operations.html#sec-getiterator). Performance evaluations are design analysis, not benchmarks. General nominal-to-structural admission, unresolved protocol-union precision, arbitrary callback/bind/apply transport, named intrinsic routing and explicit generic intrinsic invocation remain separate audits.

## Inferred generator completion and the remaining explicit-void issue

An inferred generator completion carries an actual value in its `done: true` result. Keep an established `undefined` contribution as `undefined`, including `return yield* range`, fallthrough and generator do-expressions. The ordinary-function rule that collapses a wholly valueless result to `void` does not apply to this protocol component. Written generator shorthand and explicit `R = void` annotations are unchanged by this inference repair.

| Direction | Ergonomics / autocomplete / wrong guesses | Prior art | Real-engine performance | Correctness / reference liveness | Other / decision |
|---|---|---|---|---|---|
| Collapse inferred completion to `void` | Makes a valid completed result fail structural admission; tools lose the actual terminal value. | Rust's ordinary Iterator ends with `None`; ECMAScript exposes an actual terminal value. Neither requires an uninhabitable property. | No representation saving; causes unnecessary failed checks. | Confuses discarded function results with protocol values. | **Reject.** |
| Make every inferred completion `any` | Avoids failures but loses known absence and accepts wrong guesses. | Weaker than either language's established result information. | No necessary runtime saving. | Conservative but discards a known contribution; liveness unchanged. | **Reject.** |
| Preserve inferred `undefined` as a value component | Completion narrowing is usable and required receiving checks agree with runtime. | Uses the ECMAScript result protocol, while Rust supplies only the discriminated-completion analogy. | Same result shapes and existing admission; no wrappers. | Matches the established contribution and does not extend reference lifetime. | **Recommend and implement.** |

A broader baseline failure remains for an explicitly annotated `AsyncGenerator.<any, void, void>`: admitting its completed result through a typed Promise handler encounters the uninhabitable `value: void` member. The original failing test is retained unchanged. This is not repaired by changing inference or by rewriting that test's annotation.

For the next design cycle, the available directions are: (1) keep the existing uninhabitable result and accept runtime rejection; reject because ordinary completion becomes unusable with no ergonomic, performance or liveness benefit; (2) reinterpret explicit void as undefined; reject because a void callable contract can conceal an actual non-undefined value, so that is false precision; (3) introduce a special discarded-property type/admission exception; reject as the initial direction because it adds a new structural exception, reflection rules and engine checking cost solely for this protocol; (4) represent the completed value contribution as gradual when an explicit void contract intentionally discards it. **Recommend evaluating direction 4 as the next implementation task**, with the written generator's return obligation kept separate. It preserves actual completion and uses existing shapes/admission and downstream typed receiving checks, but autocomplete loses completed-value precision by design. Rust's `Option<Item>` does not expose JavaScript's arbitrary terminal value, so its absence representation is only a partial analogy. This change must specify `next`, `return`, `yield*`, synchronous/asynchronous contracts, inference and reference liveness together; the current increment does not implement it.
