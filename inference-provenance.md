# Return inference, declaration provenance and captured contracts

The result type of a contribution and its declaration provenance answer different questions. A singleton type may come from an annotation. Conversely, widening a literal to `string` does not create an annotation. Preserve these facts separately, and read captured storage through its declared or inferred binding contract when establishing a published return.

This specifies the binding-read cases of `sec-anchored-contributions` and preserves `sec-published-return-types`: publication affects result checking and typed consumers, while signature identity and overload ranking remain declared-only. It neither infers types for ordinary unannotated `let` bindings nor changes which units are checked.

## Required outcomes

- `let s: string = "s"; function g(){ return s; } const n: number = g();` has an early return-contract error, including in a nested scope or uncalled body.
- A declared singleton, `null` or `undefined` can anchor a contribution. Parentheses do not change that result.
- `function g(){ const s = "s"; return s; }` has no annotation-derived anchor. Widening or naming the initializer alone does not activate publication.
- An untyped shadowing parameter or local cannot borrow the outer binding's annotation.
- A captured `string | number` contributes that contract. A valid later Number store must not violate a published `string` contract fabricated from the declaration-time value.
- A narrowing comparison on a union-typed parameter remains useful. The same comparison immediately after a singleton initialization remains subject to the existing impossible-test rule.

## Signed-literal regression expectation

There are three directions: remove initialization-derived impossibility checks; exempt signed literals; or retain the rule and test subtraction using an input with both alternatives possible. The first two make results less predictable, lose existing correctness guarantees, and add exceptions with no capture, reference-liveness, shape or inline-cache benefit. TypeScript's separation of declared and observed types supports retaining the distinction; Rust and C# do not supply a close analogue for this proposal's JavaScript numeric-literal union rule. Their absence is no reason to invent an exemption.

Choose the third direction. Use a `uint64 | -1` parameter to test equality and inequality narrowing. Separately test that the same comparison after `let r: uint64 | -1 = -1` is rejected with `RT_IMPOSSIBLE_TEST`. This makes both useful behavior and mandatory rejection explicit without weakening either rule.

## Publication order and lexical dependencies

A consumer must use the result required by the inference rules, even if its declaration is encountered before the declarations that establish that result. Dependency computations resolve names in each contributing function's declaration environment. A caller's same-spelled parameter cannot turn an unknown captured binding into an annotated one, or replace a known captured contract with another type.

Typed constants and explicit inferred bindings can supply dependencies through their initializer's Static Type. Preparing this contract executes neither the initializer nor the function. A compatible forward use still has its ordinary temporal-dead-zone behavior. An incompatible typed consumer is rejected before that ordinary execution begins. Reading a provisional result from a function with no annotation-derived anchor does not manufacture participation for either the callee or its wrapper.

An initializer may depend on incoming flow: in a branch that narrows `u` to `string`, `const s = u` keeps that information. Preparing `s` as the broader declared union of `u` would change its contract and can invent an error. The dependency therefore includes the required initializer flow; a compiler may prepare flow-independent contracts earlier but must not guess a broader substitute for unresolved flow-sensitive information. Memoization must preserve the same dependency distinction.

The specification states these dependencies and the required checking boundary rather than copying the interpreter's traversal. The dependency graph includes the declaration environment and the participation result as well as the type. A provisional type alone cannot serve as either a published contract or an annotation-derived anchor. Recursive convergence and resource exhaustion remain separate judgments; a declaration-order workaround must not redefine them.

## Dependencies across function forms

Use one declaration dependency relation for ordinary, async and generator results, with the contribution operation selected by function form. Complete the callee's required contributions in its declaration environment before a dependent consumer becomes final. Keep yield, completion and async fulfillment distinct, and retain participation separately from the protocol type. This is the chosen design for the finalized specification; an interpreter's traversal or temporary recursion guard is not an acceptance rule.

An unannotated literal-only async callee may contribute privately to a participating caller without becoming typed at ordinary call sites. The same distinction applies to generator protocols: knowing that a call produces an iterator does not identify a declared yield or completion contract. An inferred generator completion must come from its return contributions, including ordinary fallthrough, rather than from the default used by a written yield-type shorthand.

The proof of concept may cache a completed query for one inference wave. Such a cache must not prevent a later query after declaration inputs become available. True recursive convergence, resource failure, and initializer-flow dependency replay remain separate implementation obligations; supporting acyclic cross-form chains is not a claim that those wider obligations are complete.

## Completing initializer-dependent checks

The final specification requires dependency-complete judgments at the source-checking boundary. An inferred binding depends on its initializer's incoming flow and its declaration environment. Its consumer may have a different source position, receiver, contextual type and generic environment. Preserve both identities. An unfinished type query is not a completed unknown type; an intermediate mismatch based on that unfinished query is not a final error.

A producer with a completed unknown type follows the existing gradual rules. A producer with unfinished prerequisites remains unfinished, even if an intermediate pass produced a broad type. In particular, completing a callee used by an earlier assignment or test does not retroactively complete that transfer: recompute it and any affected initializer facts before finalizing a consumer. Existing recursive inference and resource-failure judgments remain separate.

The current proof of concept rechecks simple non-reference lexical and variable initializer compatibility after captured binding contracts complete in ordinary flow analysis. It retains the consumer's original contexts and invalidates dependent ordinary, async and generator results. It also records unfinished flow transfers so they cannot justify new speculative errors. General flow-transfer replay and the complete recursive solver remain implementation gaps; the conservative guard is not a new normative permission to skip those judgments. Reference binding checks remain outside this bounded recheck queue. The default and field consumers added below use the same dependency requirements.

## Dependent inferred bindings

An initializer's result can be a prerequisite of another inferred binding, not only of an annotated consumer. Complete those contracts in dependency order and wake affected consumers. Preserve the distinction between the producer's computation and the consumer's eventual use. A completed unknown producer is still completed work; it can allow downstream computation to finish without supplying a typed contract or an annotation-derived anchor. Explicit `:=` validates its completed result and does not confuse scheduling state with `any`.

The proof of concept now completes acyclic chains of prepared inferred bindings after their required normal-flow inputs are established. Reverse dependency edges release waiting binding computations; dependent function publications are invalidated, then initializer consumers are reconsidered. Only the declaration contract is updated: a later flow fact and the ordinary value binding's initialization state are not overwritten. Compatible chains of explicit inferred declarations can now complete before the non-`any` validation is finalized.

General flow-transfer replay, additional consumer forms and recursive binding/function components remain incomplete. Where those prerequisites prevent this bounded query from completing, the interpreter retains its existing `:=` validation diagnostics; removing an old error solely because it was deferred would silently discharge an unproved requirement. That fallback is an implementation limitation, not the finalized specification's resolution of an unfinished input. The finalized direction remains completion of the required dependency and fixpoint judgments.

## Default and field consumers

Apply dependency completion wherever an existing compatibility check consumes an initializer: simple parameter defaults, contextual defaults for whole binding patterns, annotated defaults inside patterns, and annotated instance/static fields. The target contract remains the one required at the original source position. The source can become known after a producer completes; that must not change which bindings a default refers to or which receiver a field initializer uses.

The relevant alternatives are about completing the required judgment. They do not reopen whether JavaScript defaults execute on invocation or whether class field initializers execute during class evaluation or construction.

The proof of concept adds these four consumer sites to its existing dependency queue. It retains a parameter scope before later body declarations modify the interpreter's shared frame, preserves that frame's binding identity and metadata during rechecking, and restores displaced state afterward. This is an implementation accommodation; a compiler with separate parameter/body scopes need not copy frames. Existing diagnostic families are retained, and initializer diagnostics identify the consuming expression.

The bounded change does not complete general flow-transfer replay, recursive binding/function components, all reference obligations, or repeated unannotated field-contract checks. The lexical mutation analysis described below addresses unrelated same-spelled writes for the integrated callee and initializer-alias queries. Other spelling-based flow and intrinsic-effect screens remain to be integrated. None of these limitations is permission for a finalized implementation to skip a required judgment.

## Lexical mutation identity

A write invalidates the binding it reaches. It does not invalidate every same-spelled binding in the source. This matters before execution: suppressing an established callee result because an unrelated parameter is assigned can hide an otherwise required early error. It also matters in the opposite direction: ignoring a captured write or a defaulted destructuring target can incorrectly trust a replaced callee.

The proof of concept builds a lexical scope graph before resolving mutation targets and integrates its facts into callee-result stability and unchanged initializer-alias contributions. It includes plain, parenthesized and destructuring assignments, updates, iteration targets and initialized `var` declarations. A `var` declaration without an initializer only declares the binding. The checker also gives a class static block its own variable/lexical frame and static receiver; otherwise that block's local `var` could overwrite an enclosing checker binding even with a correct mutation graph.

This remains a bounded integration. The old conservative screen is retained for direct `eval`, `with`, reference syntax, unresolved identities, path-dependent match/capture names, Annex B block-function copies and Script-global object bindings. Other spelling-based narrowing and intrinsic-origin screens are unchanged. Their remaining imprecision is an implementation limitation, not a new permission for a finalized engine to omit a required judgment. A completed inferred return still cannot license check elision.

## Contribution environments

Return, resolution and yield inference must resolve each contribution in its source scope. An inner same-named declaration cannot overwrite an outer alias's type or anchoring provenance. Conversely, a later unknown local shadows the outer declaration throughout its scope. This is specified in `sec-contribution-environments` alongside `sec-anchored-contributions` and the binding-identity requirements of `sec-elision-stability`.

```js
function f(x: string) {
  let g = x;
  { let g; g = 1; }
  return g;
}
const q: number = f("s"); // Early Error: the result is string.
```

The inner `g` does not change the outer alias. An unknown local also has an identity: in `{ return g; let g; }`, the return cannot borrow an outer `g` annotation. Establishing a static name or contract leaves runtime initialization and TDZ behavior intact.

## Local function dependencies and capture contracts

A local function declaration determines the binding throughout its owning scope. Build all sibling signatures before following a contribution dependency. In the following source, `f` returns a Number, even though an outer function-valued parameter happens to have the same name as the local function:

```js
function outer(g: () => string) {
  function f(x: number) {
    return g();
    function g() { return 1; }
  }
  const q: string = f(1); // Early Error: f contributes number.
}
```

`g`'s literal-only result remains provisional. It can answer participating `f` without publishing a result for `g` or inventing an anchor. The same query is available to a function literal at a contextual result position. Ordinary signature construction, overload identity and ranking remain declared-only; inferred results do not change which overload wins.

A separate distinction is necessary for captured locals. `let s = x; return s` can follow an unchanged initializer within that function's contribution computation. Replacing the return with `return g(); function g() { return s; }` does not annotate `s`: the nested function reads a captured binding contract. A typed constant initialized from a typed parameter can supply that contract, while a constant initialized from the contract-free mutable alias cannot manufacture one. Explicit annotations and reference referent contracts retain their existing meaning.

## Captured initializer dependencies

A required local capture contract is a dependency of the nested function's result, even when its initializer follows the return that first requests that result:

```js
function f(x: string) {
  return g();
  function g() { return s; }
  const s = x;
}
const q: number = f("s");
```

The parameter of `f` establishes the initializer contract. The Number consumer is incompatible before evaluation. Changing its annotation to String removes that incompatibility; execution still encounters the ordinary temporal dead zone. Preparation does not run `g`, initialize `s`, or make the initializer reachable.

The initializer belongs to its own source environment, including its receiver. Giving `g` a Number parameter also named `x` cannot change the type of `s`. Likewise, an initializer using an enclosing arrow's lexical `this` does not use the receiver of the ordinary local function that asks for its contract. A binding chain can cross several local function results without changing these ownership rules.

The exact initializer judgment matters. In `function f(x: string | number) { x = "s"; const s = x; return g(); function g() { return s; } }`, `s` uses the flow at its initializer. Substituting the wider parameter annotation would falsely reject a compatible String consumer. A computation may be prepared before its flow is available only if that computation is proved independent of the missing flow. An unresolved dependency is not the same as a completed unknown result.

## Flow at a captured initializer

A guard can determine the contract of a new constant without determining the future value of its source parameter:

```js
function f(x: string | number) {
  if (typeof x !== "string") return "s";
  const s = x;
  return g();
  function g() { return s; }
}
```

The normal path reaching `s` supplies String. `g` therefore reads the String contract of `s`; a String consumer of `f` is compatible, and a Number consumer is rejected in checked code. A subsequent store to `x` cannot change `s`. Returning `x` directly from `g` instead reads the captured parameter's union contract: the point at which the checker asks about `g` is not proof of its future invocation state. A reference to `x` likewise retains its location contract, not the type of a copied value.

The source judgment applies the existing flow rules, including normal versus abrupt predecessors, branch joins, loop back edges, targeted breaks and continues, switch fallthrough, exception and finally paths, and effect invalidation. Initializers in a multi-binding declaration occur in order. An earlier call, write, accessor or suspension can invalidate a fact before the next initializer. A nested contribution computation has a separate completion state. Its return must not end the enclosing path, and inspecting unreachable source must not revive that path.

## Stored domains in contribution flow

A successful typed store can establish the input of a later captured initializer just as a guard can:

```js
function f(x: string | number) {
  x = "s";
  const s = x;
  return g();
  function g() { return s; }
}
```

The assignment checks the declared union destination and establishes a String current value. The new constant has that String contract, so `g` contributes String. Its contract does not change if `x` is subsequently overwritten. The same rule applies to `let x: string | number = "s"` before the capture.

Use the domain after the required storage conversion. With `x: uint8 | string`, the store `x = 1` establishes Uint8, not Number. Preserve a destination's declared structural and callable view: assigning `{ v: "s" }` to `{ v: string | number }` does not make the mutable property permanently String. Source, conversion and store effects occur before the destination fact becomes available to the next expression or binding. Alias invalidation applies even when no new fact is established. A reference remains a location with its existing contract and lifetime, not a copied value.

## Switch contributions, selection and fallthrough

Contribution inference uses the switch flow specified in `sec-narrowing-flow`; it does not get a separate rule that starts each clause from the switch's original entry. Label selection and clause execution have different predecessor relations. A selected entry is saved while later labels are examined. A clause body receives that entry joined with preceding normal fallthrough. The default's selection follows all failed labels, including labels after the default in source text. Only breaks targeting this switch join its successor.

An empty clause has an empty statement list for declaration discovery, but still has its label and flow edges. Removing the entire clause can discard an evaluated expression or an entry that falls through into a later body. Case-block declarations share their existing lexical scope; preparing them executes no initializer and does not bypass a temporal dead zone.

```js
function f(x: string | number | boolean) {
  switch (typeof x) {
    case "number": return "s";
    default:
      return g();
      function g() { return s; }
      const s = x;
    case "boolean": return "s";
  }
}
```

Here the default selection has excluded both Number and Boolean. The captured constant has a String contract, and a Number consumer of `f` is incompatible. Executing `g` before `s` is initialized still fails at runtime. If an earlier clause instead falls through into the default, its normal flow must also join that entry; the default's selected residual alone is not the body's complete input.

## Captured switch expression results

The switch flow judgment retains the relation between a captured discriminant result and the source facts that produced it. A Boolean expression such as `x is string` has distinct result environments. An optional chain has evaluated and skipped alternatives; the evaluated result can itself be `undefined`. Applying `typeof` transforms their result values without erasing their source relations. Contribution inference and an initializer contract consumed by a contribution use these same environments at the source position, as required by `sec-initializer-inference-obligations` and `sec-narrowing-flow`.

```js
function outer() {
  function f(x: string | number) {
    switch (x is string) {
      case true:
        return g();
        function g() { return s; }
        const s = x;
      default: return "s";
    }
  }
  const q: string = f("s");
}
```

The selected `true` environment gives `s` a String contract. This makes the String consumer compatible and a Number consumer incompatible. Runtime initialization remains separate: executing the early call to `g` still reads `s` in its temporal dead zone. Reading captured mutable `x` directly in `g` does not acquire the immutable constant's contract.

For optional switch selection, failed singleton labels also remove their matching result alternatives in order:

```js
function f(o: { tag: "a" | "b" } | null) {
  switch (o?.tag) {
    case "a": break;
    case "b": break;
    default:
      if (o is null) {} // The test is always true: a type error.
      break;
  }
}
```

The two failed labels exhaust the evaluated result's domain. Only the skipped alternative reaches the default selection, and neither preceding body falls through. In contrast, one label of type `"a" | "b"` need not match the captured value: its failure cannot exclude both values. A member typed `string` likewise retains values after a failed literal label. If the evaluated property can itself be `undefined`, selecting or retaining `undefined` does not prove receiver absence.

Use the admitted built-in strict equality relation for exclusion. Within one numeric type, `0` and `-0` match the same label, while NaN never matches itself. A type identity or assignment relation alone is insufficient. Existing literal adoption and operator-admission rules still establish which value domains can be compared. Label effects can invalidate a relation to the original receiver or binding without changing the discriminant value already captured. Do not repeat a getter, call or discriminant evaluation to recover that relation.

## Immutable predicate aliases and contribution contexts

An immutable Boolean alias retains the established implications of the value captured by its initializer. Copying that alias or composing it with recognized Boolean operations preserves implications about the original source places while their identities survive. The rule is stated in `sec-narrowing-flow`; contribution inference consumes the same result environments under `sec-initializer-inference-obligations`.

```js
function f(x: string | number) {
  const text = x is string;
  const selected = text;
  return selected ? x : "";
}
```

The result is String. Moving the test into one or several immutable Boolean bindings does not discard the source relation when querying a return, yield or dependent constant initializer. The ordinary checker also retains the relation: inside `if (selected)`, another deciding `x is string` test is always true and is a type error under the existing impossible-test rule. These use the existing diagnostic identities.

The relation belongs to a source binding and captured value, not just its spelling. Source replacement, calls with relevant unknown effects, reference-origin invalidation and loop widening retain their existing invalidation rules. An open object property contract does not establish a repeatable data read. Copying a Boolean after its original relation has been invalidated cannot reconstruct that relation. An explicit `any` view, mutable Boolean or reference alias does not become an immutable Boolean copy. A nested function reading mutable `x` retains its storage contract; capturing the predicate does not freeze `x`. A constant initialized from a correctly narrowed read can retain its own separate contract.

Deferred expression queries also need the normal-completion state from their source position. A collector can visit a return before requesting the type of its operand. At that later scheduling point, the enclosing path may already be marked as returned. Using that state to query `selected ? x : ""` loses both arms' incoming flow. ## Deferred stores and lexical call effects

A store can depend on a result whose initializer flow has not yet been completed. Its pending answer must remain a dependency on that store's value and source environment. Treating all following flow as permanently unknown loses required early errors; using a later environment can invent incompatible contracts. `sec-deferred-store-flow` specifies completion, conversion order, captured value identity, joins and invalidation independently of the engine's scheduling mechanism.

```js
function outer(u: string | number) {
  u = f();
  const q: number = g();
  function f() { return t; }
  function g() { return s; }
  const s = u;
  let v: string | number = "s";
  const t = v;
}
```

The store supplies String to `s` and hence to `g`. The Number consumer is incompatible; a String consumer is compatible. This inference neither evaluates `f` nor removes its runtime temporal-dead-zone failure. A write to `u` before `s` captures its value changes that capture; a write after the capture does not. Completing an old store must not revive facts invalidated by subsequent effects.

## Completing downstream flow judgments

A completed return contract must reach every source judgment that consumed its unfinished answer. Completing the first test's diagnostic alone is insufficient: its outgoing environments may feed another test, a switch label, an inferred constant and another callable result. `sec-dependent-flow-completion` now states the transitive completion rule and identifies the outputs required for the control-structure families.

```js
function outer(u: string | number) {
  u = f();
  if (u) {}
  const q: number = g();
  function f() { return t; }
  function g() { return s; }
  const s = u;
  let v: string | number = "s";
  const t = v;
}
```

The independent initialization establishes the contract of `t`; `f` publishes String. The assignment and the open truthiness test leave String at the declaration of `s`, so `g` publishes String and the Number consumer is incompatible. A String consumer is compatible. Replacing that consumer with `if (typeof u === "number") {}` or an impossible `switch (typeof u)` label requires the existing impossible-test error. These are static judgments in an uncalled function, not execution of its initializers.

An annotated initialization also has two distinct outputs. `let u: string | number = f()` establishes the destination contract, but an unfinished result of `f` leaves its stored-value domain unfinished. Using the declared union as a completed initializer value can permanently infer too broad a contract for `const s = u`, both hiding errors and rejecting valid String consumers. Keep the value dependency attached to this initialization; it does not make an unrelated binding or stable callable declaration depend on that pending value.

## Independent flow inputs and connected value relations

A deciding test does not consume every fact held by its checker. Its domain, operands, applicable effects and retained value relations determine its actual dependencies. Revisiting an unrelated unfinished copy while narrowing a completed String can manufacture a cycle in an otherwise acyclic sequence of captures and function results. Conversely, completing that String does not complete every other fact in the environment.

`sec-dependent-flow-completion` now states these distinctions explicitly. An effect-free test preserves a completed input and its justified refinements on its admitted outcomes; each later join still needs every admitted predecessor. Copy/equality propagation follows retained relations between the affected places, including transitive relations and lexical ownership. Writes, calls, accessors and other specified effects still invalidate proofs. A stable function declaration's binding contract is independent of unfinished current values, while an unfinished inferred return remains a real dependency. Suspending a judgment to query another producer must also suspend its local proofs, even if that producer uses the same lexical binding.

## Applying a generic function versus instantiating its returned type

A call to `outer<T>` binds that declaration's parameter. If its result is a function `inner<T>`, the inner declaration remains generic. Its spelling does not identify it with the outer declaration. Returning, storing or reflecting it substitutes captured free parameters; invoking or explicitly specializing it later applies its own parameter list. This distinction applies recursively to declared and inferred results, receiver and narrowing contracts, and effective constraints. An unbound inner parameter can keep its identity while a constraint referring to an outer parameter becomes concrete. Default and constraint source nodes remain in their original environments and are evaluated only at the prescribed application.

The specification's `SubstituteType` already uses declaration identities. `sec-generic-specialization` now makes the recursive constraint and graph traversal requirements explicit, and `sec-dependent-result-instantiation` describes the two distinct uses and gives executable source. The engine uses separate entry points for signature application and free-parameter substitution. A scoped traversal shares its memo across the signature's fields, preserving recursive graphs and repeated parameter records; it does not reset a nested result to an application root. Explicit specialization retains the already-substituted inferred result. Runtime result enforcement and reflection use the free-parameter operation. This repairs the existing implementation paths without claiming that every name-keyed engine binding map has been replaced with declaration keys.

## Correction: replacement does not create a required inferred boundary

The earlier remaining-evidence report expected the following unannotated chain to throw:

```javascript
function bad(): any { return "s"; }
function id<T: type>(x: T) {
  function typed(): T { return x; }
  function produce() { return typed(); }
  let replacement: any = bad;
  typed = replacement;
  return produce();
}
id(1);
```

That expectation is superseded. Under `sec-elision-stability`, the replaceable callee cannot supply its original result to this contribution query. The contribution is unknown, so there is no published `T` result for `produce` or `id` to enforce. The shallow callable admission does not wrap the replacement, and the original annotated function never runs. Returning `"s"` is therefore correct. A mutable binding explicitly annotated `() => T` has the same limitation: it does not guarantee that an admitted callback dynamically checks its results.

Adding `: T` to `produce` or to `id` establishes a real declared boundary, which rejects the String at runtime even for an untyped caller. An independently established inferred contract also remains enforced. Compatible dynamic values pass these boundaries. The spec now spells out this distinction and example at `sec-elision-stability`. This clarifies the existing policy rather than introducing deep callable wrappers.

## Retaining generic defaults and complete inference environments

A default belongs to the signature that declares it. A returned `inner<U: type extends T = T>` from `outer(1)` retains Number in both its bound and its default. Publishing that returned signature substitutes the free enclosing parameter in a symbolic default description; applying `inner` later supplies its own omitted arguments in order. The default can occur inside an array, tuple or function type. A generic function type used as a default keeps its own binders. A higher-kinded default supplies a constructor; a bare alias in that position is not an empty application. Separate Number and String closures remain independent, and defaulted and explicitly equivalent arguments identify the same specialization.

The checker retains symbolic default descriptions alongside source, traverses them during free-parameter substitution, and consumes them when completing an application. Describing a default must not schedule its computed type for ordinary closed-annotation evaluation. The application owns that computation, including a computation nested in a tuple default. An unused default and a default bypassed by an explicit argument are not executed. Structural well-formedness, compile-time evaluability and the existing ordered-binding rules still apply; this is no exemption from checking a default when it is required.

A declaration-local alias also retains its lexical dependency. `type Limit = T` within `outer<T>` remains dependent on that enclosing parameter. The checker follows nongeneric alias declarations transitively when identifying an unresolved type's dependencies, with a visited-node set for cycles. It no longer treats the alias as a closed computation that attempts to look up an unbound global `T`. Wrong calls remain statically invalid after the captured constraint becomes known. Applied generic aliases keep their existing argument-binding path; blindly traversing their bodies without those bindings would falsely classify a closed application as open.

Queued return inference must retain the complete generic scope already established for the declaration, including bounds, value-parameter domains and declaration identities. Recreating that scope from names dropped the array bound in `outer<T: type extends [].<any>>`, so its nested `function f(...a: T, ...b: [].<uint8>) {}` was wrongly rejected even when specialized with `[].<uint8>`. Retaining the same scope repairs ordinary, async, generator and async generator forms. Supplying `[].<any>` remains invalid under the adjacent-rest rule. A discarded signature candidate also restores its pushed generic scope before checking another declaration.

The specification connects these requirements through `sec-dependent-result-instantiation`, `sec-generic-constraint-contexts` and Type Parameter Records. It specifies binding identity, dependency propagation, substitution and evaluation ownership rather than requiring the POC's maps, weak maps or inference queues. No new diagnostic family is needed.

## Completing stored applications and contextual completions

The stored-application and carried-completion discrepancies recorded above are resolved by the following rules. A stored generic application is checked under its declaration-owned explicit arguments and ordered defaults. While a required checking-time default is pending, its signature is unavailable; it must not become either the original generic signature or `any`. Consumers retain the dependency and are checked again when the default completes. This includes `const g := f.<16>`, aliases of `g`, and argument checks on later calls. Missing required arguments still fail; an evaluated default that violates a constraint still fails. Runtime specialization identity continues to depend on the original function and completed bindings.

A contextual type on an ordinary `do` reaches the expressions that actually provide its normal completion values. Read each producer in its lexical and flow environment. Labelled breaks carry values; normal finally preserves the incoming captured value; abrupt finally replaces it. Switch coverage belongs to the switch's discriminant environment, including a local enum scope, rather than a later merged environment. Speculative type queries restore their incoming state. The ordinary source walk remains responsible for actual flow effects, loop invalidation and escaping completions.

The disjoint strict-comparison obligation uses source provenance to decide the literal-name exception. A flow-literal record for an annotated binding is evidence about possible values, not permission to act as a written literal. The obligation applies to a comparison whose result is discarded as well as stored. Written literals, eligible immutable literal names, overlap, gradual operands and loose equality retain their respective existing rules. This does not turn a pure `is` query into a deciding test.

## Recursive unknown results and publication replacement

An inference task has three distinct states: no contribution answer yet, a known provisional result (which can be `never`), and a computed unknown join. Unfinished binding or evaluation dependencies remain recorded separately. The initial `never` contribution breaks a recursive dependency while its first answer is unavailable. It must not replace an unknown answer already computed for that dependency.

```javascript
globalThis.seed = "s";
function first(n: uint32) {
  return n > 0 ? second(n) : globalThis.seed;
}
function second(n: uint32) { return first(n); }
const value: string = second(0);
value;
```

`first` has an unknown result. That answer must reach `second`, replacing an earlier provisional `never`. Keeping `never` in either the callable signature or the runtime return contract rejects the actual String even though the source has no incompatible return annotation. In engine262, both declaration orders exhibited this failure. An async version also rejected its promise with the obsolete `never` contract.

Recomputation replaces the provisional answer, including when the new answer is unknown. Publication is then reconsidered from the current result and its provenance. An unknown join publishes no inferred result; losing the only declaration-derived anchor also removes publication. Clear the superseded signature result, inferred return boundary and anchoring provenance together. Explicit return annotations remain authoritative. A generator retains its independently specified protocol shape, and unknown protocol components remain unknown under the existing component rules.

The distinction is visible to consumers. An explicitly annotated String binding in the example succeeds; `const value := second(0);` is a static declaration-inference error because no Static Type is established; a Number binding reaches its runtime boundary and rejects the String. Unknown information supplies no proof of an always-true or always-false narrowing test. A private provisional answer can change even when neither the old nor new answer is published, so publication alone is not the convergence state.

## Finite recursive propagation and private answers

Finite return dependencies must settle regardless of declaration order or the number of functions in a cycle. The former eight whole-scope passes treated a `uint32` contribution moving through a cycle as construction of an ever-growing type. Forward-order chains of 8, 12, 20 and 40 functions could fail where the reversed declarations succeeded. The required result is the same canonical contract in every order, and dependent impossible tests must be judged from that result.

The checker now records result dependencies and schedules affected consumers. Its canonical member vocabulary distinguishes copying an established type, or forming a union of established members, from creating a new member. Dependencies are retained through function-value reads, generic applications and temporary local queries. Completed private answers are reused while their inputs remain valid; a required captured-binding change still invalidates them. Unknown answers and `never` retain the distinct meanings specified by the preceding section.

Conditional provenance must follow the arms in their source environments. Joining a literal-only arm with a private recursive answer does not create an annotation. Otherwise a cycle that should remain private can advertise an inferred String result, turning a Number consumer's runtime boundary failure into an early error. A participating wrapper can still infer String from the same private cycle. The implementation now separates those cases, including reuse of private answers so that an unanchored cycle does not repeatedly expand on every query.
