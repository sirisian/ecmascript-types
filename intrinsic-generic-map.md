# Explicit generic mapping

The intrinsic Range and synchronous Iterator `map` functions accept one output type parameter, `U`. `r.map.<string>(callback:f)` and `it.map.<U:string>(f)` have the same explicit-output obligation as their positional spelling. The existing item/input context remains receiver-dependent; explicit output arguments do not rewrite the source item type. Named value arguments follow [named-intrinsic-routing.md](named-intrinsic-routing.md).

## Application and callable identity

Resolve the actual callee by ordinary lookup, then resolve and bind the written type arguments once, before evaluating value arguments. An invalid application fails before those value arguments run. Use the ordinary type-argument rules, including names, fixed-extent spreads, arity and lexical type resolution. The intrinsic has no default for `U`; a stored application must bind it.

A specialization is a callable value interned by the original intrinsic function object and the completed output type. Equivalent positional, named, alias and spread applications have the same identity; different nominal declarations remain different even if their display names agree. Realm-specific original functions remain distinct. The specialization captures no receiver. An immediate member call keeps the already selected receiver without reading its getter again; extraction needs the receiver supplied by an ordinary method/reflective call. Public `name`/`length` properties and the caller's member spelling do not confer or revoke generic capability. A replacement callee uses its own declaration.

Reflection and the runtime callable type of a stored intrinsic specialization describe its completed callback/output contract. The receiver-independent specialization does not capture a particular range's item domain. Static member checking can still supply the established `I` to `(value:I,index:uint64)=>U`. Internal alpha-renaming that avoids capturing an outer `U` must not rename the public type-argument label: the mapper's declared label remains `U`. Named argument selection and reflected parameter names read that declaration spelling; substitution retains its distinct internal binding identity.

## Lazy output admission

Creating the helper does not invoke its mapper or inspect future items. Each reached intrinsic Iterator mapping step calls the original callback once, then admits its normal result to the captured `U` using the ordinary value boundary before yielding it. This includes the proposal's permitted conversions, for example a gradual numeric result admitted to `string`. The callback keeps its identity and its own declaration; it is neither wrapped nor retroactively annotated. The helper's output boundary remains after erasure, storage, borrowing and exit from the producer's generic scope.

If the callback throws, preserve its original abrupt completion. If output admission throws, use the same native `IfAbruptCloseIterator` path as a callback failure. The source closes under the existing precedence rules, the helper completes, and a later resume does not retry the failed item or callback. Argument effects, iterator acquisition and native callback validation retain their existing positions. No rollback or new closing flag is introduced.

`any` admits the normal result unchanged. `void` retains the proposal's discard interpretation for a callback result: it does not prove that the actual value is undefined and does not manufacture one. `never` admits no normal result. An empty source produces no callback result to admit. Promise and thenable results are items; synchronous mapping introduces no Await. All ordinary reference decay, suspension and liveness rules remain in force.

## Range forwarding and replacement

An explicit Range mapping acquires its ordinary fresh cursor, looks up that cursor's `map`, and forwards the completed `U` as an explicit type argument to the function actually selected. It passes the original callback and the already mapped positional value arguments. The selected intrinsic Iterator mapper creates the lazy boundary above. A user generic replacement receives the same explicit argument through ordinary generic selection, constraints, `where` clauses and parameter/body admission. A nongeneric replacement cannot silently consume and ignore this explicit application; it fails before its body. Plain inferred Range mapping keeps its ordinary forwarding path.

The Range method admits the delegated normal result against its helper-bearing `U` protocol. This is the ordinary structural/callable receiving boundary; it does not execute a replacement's `next` to prove future results, wrap a replacement's returned object, or strengthen a gradual user declaration beyond the proposal's existing callable contracts. The intrinsic Iterator implementation's per-item backstop is guaranteed when that intrinsic is the selected delegate. General enforcement through arbitrary gradual protocol replacements remains part of callable/protocol boundary work.

## Decision: establish real generic capability

| Direction | Ergonomics / wrong guesses / autocomplete | Prior art, including Rust | Real-engine performance | Correctness / references | Other / decision |
|---|---|---|---|---|---|
| Permanently reject explicit native application | Contradicts the generic output shown by completion and forces inference even when the author wants a constraint | Rust permits explicit generic arguments; its map also quantifies the closure type, unlike this proposal's one public output parameter | No specialization work, but no useful optimization benefit | Leaves static and runtime capabilities inconsistent; no liveness benefit | Rejected |
| Register the native and ignore type arguments | Appears successful until an incompatible item escapes | Rust's output type argument imposes an obligation; ECMAScript has no type arguments to justify ignoring one | Cheap but cannot justify output-type optimization | Unsound claim of a completed output type; does not enforce gradual results | Rejected |
| Specialize by caller spelling or bind the current receiver into the function value | Convenient direct call, surprising alias/extraction identity and accidental receiver retention | Rust method selection is not mutable JavaScript lookup; this proposal explicitly has receiver-independent specialization values | Extra receiver-dependent cache keys or closures; complicates IC guards | Replacements and borrowing diverge from ordinary lookup; can retain references longer | Rejected |
| Identity-owned, receiver-independent specialization with captured U and a real native output boundary | Direct/stored/named forms agree; wrong outputs fail at a predictable lazy boundary | Rust supplies the explicit output constraint and lazy adapter analogy; ECMAScript supplies receiver lookup and helper lifecycle | One cached callable per intrinsic/type; one output check at the existing mapping step, removable where statically proven; no result facade | Preserves actual selection and U across scope exit; adds no reference authority | **Selected** |

## Decision: where to admit mapped results

| Direction | Ergonomics | Prior art, including Rust | Real-engine performance | Correctness | Other / decision |
|---|---|---|---|---|---|
| Execute mapper during application/helper creation | Failures happen early but iterator use becomes eager and effectful | Neither Rust's lazy map nor ECMAScript map creation invokes the callback to discover output | Forces work for unused/empty/endless sources; obstructs optimization | Breaks laziness, effects and input availability | Rejected |
| Check only a later receiving variable or reflection result | Erased consumers can observe values contradicting explicit U | Weaker than Rust's map output obligation; typed receiving boundaries are separate | Saves a check only by losing the contract | No output backstop after erasure; signature metadata alone is insufficient | Rejected |
| Wrap or mutate the user's callback | Can enforce results but changes visible callback identity or unrelated later calls | Rust owns a closure in its adapter; that does not justify mutating a shared JS callable | Extra closure/call target or mutable function contract; additional IC pressure | Replacement helpers can observe wrapper identity; mutation conflates invocations and can retain captures | Rejected |
| Capture U in the native mapping closure and admit immediately before Yield | Preserves laziness, original callback identity and error locality | Matches Rust's item constraint conceptually; ECMAScript's callback/close/yield stages are the precise runtime analogy | Captured immutable type alongside existing closure state; no extra iterator wrapper | Uses native close precedence and state; references cross their existing value boundaries | **Selected**; void keeps its existing discard policy |

## Decision: explicit Range delegation

| Direction | Ergonomics | Prior art, including Rust | Real-engine performance | Correctness | Other / decision |
|---|---|---|---|---|---|
| Bypass the selected Iterator method and call the native implementation directly | Replacement behavior differs only for explicit syntax | Rust's statically selected methods do not model replaceable JS properties | Easy inlining but based on a false identity assumption | Violates existing ordinary lookup | Rejected |
| Call any selected method without forwarding U | Maximally permissive replacement, but explicit constraints disappear | Unlike forwarding an explicit generic obligation in Rust; ECMAScript alone has no such obligation | Avoids specialization but offers no sound type fact | A nongeneric replacement silently ignores explicit U | Rejected |
| Wrap every returned iterator with a new output facade | Can enforce arbitrary gradual delegates but changes result identity/prototype and adds another closing layer | Neither existing proposal forwarding nor ECMAScript helper identity promises such a facade; Rust adapters have different ownership | Extra object, next-call indirection and shape/IC effects | Requires a new protocol-wide wrapper policy, including borrowed methods and closing | Rejected for this contract |
| Forward U through ordinary generic selection and retain receiving admission | Generic replacement authors see the actual output argument and original callback; nongeneric replacements fail explicitly | Closest to ordinary generic forwarding; Rust does not settle dynamic JS replacement behavior | Identity-guarded cached specialization on the intrinsic path; ordinary generic dispatch otherwise | Preserves lookup, constraints, body checks and reference rules; does not claim to solve gradual protocol enforcement | **Selected** |

## Decision: public U versus an internal hygienic name

| Direction | Ergonomics | Prior art, including Rust | Real-engine performance | Correctness | Other / decision |
|---|---|---|---|---|---|
| Expose the hygienic internal name (`U_`) publicly | Named calls and autocomplete vary with unrelated receiver parameter spelling | Rust preserves the name of a declaration while resolving its scope; it has no named type-argument syntax here | No runtime cost, but no optimization benefit over a stable label | Avoids capture internally but makes the same intrinsic's public declaration inconsistent | Rejected |
| Use an undifferentiated U for both receiver and mapper bindings | Stable display, but a plausible call can silently substitute the wrong parameter | Unlike Rust's declaration-bound generic identity | Static substitution is superficially simpler; invalid type facts cannot justify optimized code | Captures the receiver's same-spelled parameter and violates declaration identity | Rejected |
| Select and reflect by declaration spelling, substitute by the distinct internal binding | Stable public U with correct receiver input context | Closest to declaration-bound generics; named syntax remains this proposal's choice | Static metadata work, no public object-shape or IC cost | Preserves separate bindings and adds no reference authority | **Selected**; existing source declaration names remain unchanged |

Primary references: [Rust Iterator::map](https://doc.rust-lang.org/std/iter/trait.Iterator.html#method.map), [Rust expression paths and generic arguments](https://doc.rust-lang.org/reference/paths.html#paths-in-expressions), and [ECMAScript Iterator.prototype.map](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-iterator.prototype.map). Rust's iterator ownership and static typing are not analogies for JavaScript prototype mutation, gradual boundaries or native failure precedence. Performance statements here are design analysis, not benchmark results.

## Boundaries still open

This increment implements explicit `map` application, not all generic standard-library intrinsics. Range `intersect` and the generic-looking scale sketch need their own capability audit. Concrete callable-boundary specialization, arbitrary bound/proxy/adopted generic transport and general callback context propagation remain separate; a bare native passed through a concrete callable view is not made explicitly specialized by this implementation. The previously observed `step()`/undefined default contract is unchanged. These limitations do not permit explicit mapper applications to ignore U.
