# Symbol keys in canonical metadata

Metadata record keys are ECMAScript property keys: Strings and Symbols. Symbol descriptions are diagnostic text, not identity. Preserve the same Symbol through every producer, canonical comparison, claimed portion, typed capture, computed result and reflected description. An own enumerable Symbol field participates like a String field. A nonenumerable or inherited record field does not participate. Lists still use indexed elements; a Symbol property on an Array is not an element.

Two records are equivalent exactly when their key sets agree and corresponding values are equivalent, independently of insertion order. The same rules apply inside lists and nested records. Distinct Symbols with identical descriptions remain distinct; registered and well-known Symbols retain their ordinary identities. The Symbol value rule is separate from the property-key rule, and both must hold. Canonical ordering must distinguish different Symbol identities using the existing per-agent first-interning order, rather than allowing equal display text to tie.

Constraint-shape lookup, global key ownership, default completion, normalization and hook projection all use actual property-key identity. The same-description key owned by another meta type cannot satisfy a required field. Default and supplied fields are merged by identity. Unclaimed keys are errors at construction, including reflected construction; the existing exemption for a base with a successfully published base-form meta declaration remains. Static failures use the established source-check phase; reflective calls reached during evaluation fail at that runtime boundary. This repair supplies no new rule for establishing a computed key whose initializer is still unavailable during checking.

The engine262 implementation currently keeps immutable host records, using opaque host Symbol tokens in a per-Agent side table to represent engine Symbol keys. Object spread and ordinary record merging retain those tokens. Shared enumeration and reverse lookup restore engine Symbol values at materialization. This is a proof-of-concept representation, not required spec behavior. The table lifetime is the Agent lifetime; it is not a claim of bounded cache retention or complete portable resource accounting. A production implementation may use weakly retained identifiers, interned descriptors or another representation satisfying the same identities.

## Verification boundary

Test identity, permutations, reflection round trips, enumerable getter order, unsupported Symbol-keyed leaves, numeric domains, typed captures, computed operators, declaration cleanup and the unclaimed/base-form distinction. Keep native error class, diagnostic phase and source-body entry assertions. Seed externally established Symbol bindings in an earlier source when testing canonical handling: same-source binding availability is an independent declaration-identity question, not permission to assert a later failure phase.

Top-level Array admission and omission of invalid written leaves remain separate producer defects. Deep downstream recursion, complete cost/cache accounting, structural Symbol-key ordering outside metadata, and computed-key availability require their own evidence.

The focused audit retains two concrete failures outside the passing corpus. A same-source `const k = Symbol(...)` followed by a meta declaration and a written parameterization can use inconsistent key identities during checking. A standalone function specialization capturing a non-default Symbol-keyed portion is rejected as nongeneric, while its String-key equivalent and the plain-base Symbol default case succeed. Neither failure is an accepted outcome; test sources and paired observations accompany the implementation handoff.
