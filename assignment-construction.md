# Construction at assignment stores

A fresh right operand has the construction context of its declared destination. Its selected union alternative must reach the existing store admission, just as a fresh initializer's choice reaches binding initialization. For example, assigning `{ fn(value: U): U { return value; } }` to `{ fn: (value: string) => string } | { fn: <U: type>(value: U) => U }` must preserve the generic alternative selected to make the literal well formed. Reordering the union does not change that result.

The choice is a request for checking the source occurrence, not a successful check or a permanent property of its value. Evaluate the destination once, evaluate the selected right operand once, and carry its producing completion to the actual store. Admit where the destination already checks. Keep the declared union as the destination's storage contract. Failure of the chosen alternative propagates without retrying an overlapping alternative.

## Required properties

A valid direction must preserve declaration identities and captured arguments; retain source and target evaluation order; perform no speculative getter, key conversion, setter or Proxy operation; keep reference and view liveness checks; preserve failure precedence, already performed effects and publication rules; isolate reentry; and avoid public properties, wrappers or shape changes. A right operand skipped by logical assignment contributes nothing. Checking an assignment expression's result must still supply its own destination context before checking its fresh right operand; the outer receiving context cannot replace that destination.

## Operation and boundary rules

1. Obtain a construction context from the actual destination's existing declaration metadata, without reading its value. Numeric primitive index keys can be recognized without effects. Do not convert an object key early or invoke an accessor to discover a destination. A `super` store uses the actual receiver's storage. A reference alias or Array span forwards to its storage while retaining the ordinary liveness check at use.
2. Preserve the RHS completion through ordinary value extraction. Named function evaluation has the same target context. Simple assignment and the evaluated RHS of `&&=`, `||=` and `??=` use this rule; skipped logical branches do no construction or admission.
3. Pass eligible choices explicitly through internal environment, reference, property, private-field, Array and tuple storage operations. Transparent internal forwarding preserves the operation. Array growth retains its existing initialization and publication plan. Nested source descriptors remain live until the associated admission; replacement by the identical value still ends that contribution.
4. Preserve the existing ordering of Proxy trap lookup, incoming checks, trap invocation and invariants. An existing typed Proxy incoming check can consume the operation's choice. A user callback, accessor invocation, reflection call or unrelated nested write does not inherit it. A later explicit operation in a trap receives an ordinary value. This does not authorize extra key conversions or change Proxy invariants.
5. Completing or failing the store ends this pending association. Ordinary later reads and an assignment expression used as another boundary's input gain no pending choice. Independent successful-admission facts and valid check elision remain applicable. Consequently, absence of a pending choice does not itself require specialization to another union arm. The assignment expression continues to return its captured RHS value; it does not reread the destination or substitute a numeric value converted only for storage.

### Forwarding alternatives

| Direction | Ergonomics | Prior art | Performance | Correctness | Disposition |
| --- | --- | --- | --- | --- | --- |
| Internal forwarding retains the operation; callback code starts independent operations | Ref aliases, spans and ordinary storage agree; user-written forwarding has ordinary value semantics. | ECMAScript distinguishes internal forwarding from `Call`; Rust borrows support access to the same location but lack Proxy callbacks. | Optional internal inputs; no value tags or callback instrumentation. | Keeps operation ownership and reference liveness explicit. | Recommend. |
| Forward through callbacks whenever the same value reappears | Identity equality looks sufficient until a callback independently stores the value. | Rust value identity is not evidence of a JavaScript evaluation occurrence. | Requires ambient/value lookups and effect tracking. | Conflates unrelated operations and lets replaced contributions regain a choice. | Reject. |
| Drop choices at every internal indirection | Similar source assignments vary by storage mechanism. | Rust reference assignment is still a destination-context operation; the analogy does not erase runtime liveness checks. | Less transport code, but forces repeated unselected admission. | Loses the original receiving operation through refs, Array definitions and Proxy fallthrough. | Reject. |

## Coverage and limits

The implementation covers simple and evaluated logical assignment to declared bindings, ordinary typed properties, public/private/static/inherited fields, `super` receivers, owned Array/tuple positions, reference aliases and returned locations, and owned Array spans. It carries choices through ordinary storage forwarding and the existing Proxy checks. Tests distinguish selected failures, failed publication, nested descriptor replacement, reentry, numeric conversion, captured targets, skipped branches and stale storage references.

This increment does not claim a general solution for contextual construction into setter parameters, user index operators, destructuring extraction, unknown destination/key alternatives, arbitrary callback forwarding or representation-specific buffer/SoA stores. Those need their own destination and source-correspondence proof. Existing write judgments still check every known destination separately; a union of possible read types is not an assignment context.

The dynamic construction-association rule is this proposal's design, not a claim that either reference specifies it.
