# Deciding tests of reference reads

A `ref` binding names a location. A test can establish a fact about the value read from that location, but the fact is neither a permanent value contract nor a liveness proof. Subsequent tests use the facts justified at their own evaluation positions.

This distinction resolves the four diagnostics carried from the module-reference audit:

| Witness | Required result | Reason |
| --- | --- | --- |
| Test `r !== 1`, store `x = 2` where `r` aliases `x`, then test `r !== 2` | Accept | The store revokes the earlier fact about the live referent. |
| Copy a returned reference into `const y: E`, then guard with `!(y instanceof E)` | Reject before the module body | The admitted copy has the stable nominal contract `E`; the guarded test cannot succeed. |
| Establish a counter fact, read a reference to a getter that writes that counter, then test the counter | Accept | Reading the reference has the getter's ordinary effects. The earlier counter fact no longer applies. |
| `r !== undefined || typeof r !== "undefined"`, where `r` directly aliases an unchanged ordinary local | Reject before the module body | The right operand is reached only when the same stable referent was found to be `undefined`. That deciding comparison cannot succeed. |

The last verdict depends on the stable location and absence of intervening effects. A reference to an accessor may return different values on successive reads. An untested, unannotated local does not acquire an `undefined` contract merely because its initializer is absent. A stored nominal membership query remains permitted: `const answer = y instanceof E` decides no branch. For a logical expression stored as a value, its left operand still decides whether the right operand runs; its final operand does not acquire a deciding role merely because its answer is constant.

Reference constness fixes rebinding permission, not the referent's current value. A direct store, compound assignment, update, alias store or rebinding must invalidate affected value facts. A chain that refers to another reference binding continues to follow that binding after rebinding. An unrelated local or a same-spelled shadowing declaration is not a write to the referent. An immutable ordinary copy keeps its own contract when the original location changes.

Forming or forwarding a reference does not read its referent. Reading one can invoke an accessor or proxy, throw, or fail a liveness check. Type checking executes none of those operations to discover a type. Retained contracts, current-value facts, selected locations, initialized state and reference liveness remain separate inputs.

## Decision

A valid repair must preserve required constant-test diagnostics, invalidate facts affected by writes or changed origins, account for accessor effects at value reads, preserve unrelated proved facts, distinguish lexical declarations, and keep ordinary evaluation and liveness checks. These requirements apply to scripts, functions, modules and imported bindings.

| Direction | Ergonomics and autocomplete | Prior art and limits | Real-engine performance | Correctness and liveness | Other / disposition |
| --- | --- | --- | --- | --- | --- |
| Keep all four rejections | Completion can advertise a value that a later live read no longer holds; correct programs fail | Neither Rust's borrow rules nor TypeScript's assignment flow justifies stale facts | No added analysis cost | Contradicts reference updates and getter effects | Rejected: two witnesses are false positives |
| Exempt reference tests or assertion-shaped branches | Hides useful mistakes; a wrong guess about a declared nominal type stops being diagnosed | Rust does not generally prohibit constant Boolean conditions, but that is a different language rule; TypeScript does not implement this proposal's whole impossible-test policy | Cheap special case | Removes required decisions, including the stable undefined witness, without repairing stale inputs | Rejected: changes the diagnostic policy to mask invalidation defects |
| Discard every flow fact at every reference operation or store | Avoids some false positives but loses completion precision for unrelated locals and stable direct cells | Conservative alias analysis is familiar; neither comparison requires erasing facts proved unaffected | Simple transfer, potentially more runtime checks and less optimization; no required shape change | Loses required preserved-fact judgments and confuses formation with reads | Rejected: excessive invalidation is observable in required diagnostics |
| Snapshot the referent or prohibit aliases to mutable cells/accessors | Simple value reasoning, but explicit `ref` stops following the location; wrong guesses become behavioural changes | Rust restricts competing accesses to borrowed memory; this proposal intentionally permits different aliasing and accessor behaviour | Snapshots can invoke user code and require extra storage; restrictions could aid optimization | Violates established read-through, rebinding, effects and liveness semantics | Rejected: incompatible language redesign |
| Execute source to discover aliases or getter outcomes | Results depend on effects during checking; completion becomes execution-dependent | Neither Rust's borrow checking nor TypeScript's control-flow analysis executes ordinary source for this purpose | User-code execution dominates checking cost and can change shapes/IC state | Breaks checking phases, TDZ, effects and failure precedence | Rejected: inadmissible checking strategy |
| Apply origin-aware invalidation and ordinary read effects within the bounded flow analysis | Completion reflects the established current domain; stale tests stop rejecting valid code while stable redundant tests remain errors | TypeScript's distinction between declared and observed types is relevant; Rust separates a reference from its referent and enforces stronger alias restrictions | Compiler-owned declaration/location dependencies and effect summaries; no required runtime wrapper, per-instance field, object-shape or IC-key change | Writes/rebinding revoke affected facts, uncertain origins supply no preservation proof, and every actual read retains ordinary liveness/admission | Recommended independently of implementation effort |

The recommendation requires sufficient origin evidence to preserve a fact, not whole-program points-to analysis or execution of arbitrary callees. A production engine may use sparse dependency sets or versions; a proof-of-concept may recompute bounded judgments. Precision cannot be chosen opportunistically when it changes a required diagnostic. The formal rules determine which proof survives; the representation does not.

Rust's shared references normally prohibit direct mutation of their referents, with interior-mutability exceptions; its mutable references provide exclusive access under its borrow rules. Those guarantees are not available merely because this proposal spells a binding `ref`, and Rust's restrictions do not license returning this proposal's getter value as a snapshot. TypeScript documents flow-sensitive observations while checking assignments against the declared type. It supplies a useful contract/current-value distinction, but its erased types and lack of these reference bindings make it an incomplete analogy.

Sources: [Rust reference types](https://doc.rust-lang.org/reference/types/pointer.html), [TypeScript narrowing and assignments](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#assignments).

## Reference location flow

An initialized alias of a lexical binding retains that binding cell as its source, not the value or terminal location it happened to reach during initialization. For `let ref a = x; let ref r = a;`, the edge from `r` continues through `a`. Rebinding `a` changes the location reached by both aliases, whereas rebinding `r` alone does not change `a` or `x`.

Keep this location information at each source position alongside the value-flow environment. A store through a known lexical chain invalidates facts about the cells it may overwrite and aliases that may reach those cells. An ordinary direct store must invalidate those aliases too. A rebinding invalidates dependent alias facts and replaces that binding's location edge; it does not store to the old referent. Prefix/postfix updates, compound/logical assignments and destructuring stores obey the same rule. This information supplies no new singleton inference through aliases.

Join location alternatives at the same admitted predecessors as value facts. A missing location proof is unknown, not an absent predecessor. Loop widening accounts for writes and rebinding on later iterations. Exceptional entry includes possible stores and rebinding before an implicit exception; finalizers transfer their location changes as well as value changes. Deferred checks restore the saved source-position location environment, and nested checks restore the suspended environment afterward. A captured reference's declaration-time location is not the location of an arbitrary later invocation. Calls that can execute a captured rebinding revoke its old location proof.

This flow information is limited evidence for preserving facts. A property location, reference parameter, returned reference or unsupported location expression need not identify a lexical cell. Such uncertainty retains conservative invalidation and runtime checks. A property getter can read a lexical cell or reference binding, so a property origin alone does not prove that its value is independent of a lexical store or rebinding. In particular, property stores can invoke setters, and conversions retain their existing effects. A successful type or location judgment does not establish initialization or extend a borrow's lifetime.

The implementation choice was evaluated separately from the semantic decision above:

| Representation | Ergonomics | Prior art | Engine performance | Correctness | Disposition |
| --- | --- | --- | --- | --- | --- |
| Remember only the initializer's terminal referent | Completion becomes stale after chained rebinding | Copies a pointer snapshot, which is not this proposal's reference-to-binding semantics; Rust's exclusive borrowing does not justify it | Cheap lookup | Loses binding indirection and later rebinding | Rejected |
| Union every syntactically possible source for the whole declaration | Earlier tests lose precision because of future rebinding; unrelated stores can erase facts | Resembles a flow-insensitive may-alias analysis; weaker than the source-position control flow this proposal already uses | Compact, but unnecessary invalidations can increase later checks | Cannot preserve required facts at positions before a different source is selected | Rejected |
| Treat a property origin as independent of lexical stores and rebinding | Completion can retain an outdated getter result; valid later guards reject | Rust's disjoint storage reasoning does not make an accessor independent of captured state | Cheap classification, but gives optimizers a false preservation proof | A getter can read the changed lexical cell or reference binding | Rejected: property identity alone is insufficient evidence |
| Maintain a separate location pass and merge its answers into type flow | Useful only if both passes agree on admitted predecessors; otherwise wrong completion or diagnostics | A separate alias analysis is common, but Rust and TypeScript do not provide this proposal's exact transfer rules | Can be efficient with a shared graph, but duplicated joins/replay need synchronization | Must retain identical lexical, completion and deferred-input contexts | Viable architecture, not selected for this interpreter because its existing flow environment already carries those contexts |
| Carry immutable location edges with existing source-flow snapshots | Precise direct-cell invalidation; unrelated and shadowed cells retain completion facts | Follows the established contract/current-value distinction; does not import Rust's alias exclusivity | Compiler-owned sparse edges or versions in a production engine; no user-object shape or IC-key change | Shares source positions, admitted joins, abrupt completions and replay restoration | Recommended and implemented for lexical aliases |

## Audit status

Lexical reference-alias invalidation is repaired in the engine implementation. The subsequent read-effects audit also corrected one earlier witness classification, described below. Direct and chained stores, updates, rebinding, loops, exception paths and destructuring share the affected-location judgment. Independent cells and the required nominal/stable-undefined diagnostics remain covered.

Reference reads of accessors use the read-effects transfer described below. Construction now includes instance-initializer writes in its captured effects, and initializer checking is isolated from declaration-time mutable facts. The former construction-counter failures and the checked-code classification correction are documented in [Instance initializer flow](construction-flow.md). Neither repair weakens the nominal or stable-undefined diagnostics.

Permanent regression tests cover the repaired alias transfers, preservation controls and required diagnostics. The audit artifacts separately record unresolved witnesses and their required outcomes; these failures are not encoded as accepted conformance behaviour.

## Reference read effects and receiving boundaries

Classify reads at their source position. A chain proved to reach ordinary lexical cells is a data read. An unknown location, property reference, reference parameter or unresolved imported reference can invoke user code when its value is consumed. Apply the ordinary captured-write and alias invalidation then; retain unaffected facts and the declared read contract. Do not save a getter result as a fact about the next getter read, including via a saved predicate or copy. A copied value still has its own contract.

Selecting a location is distinct from consuming its value. `let ref r = holder.base[key]` evaluates `holder.base` and `key`, including any getters those evaluations invoke, without reading the selected element. A skipped logical/conditional arm contributes no read effect. Loop, catch and finalizer transfers include possible evaluated reads; creating a callable does not execute its body. Imports and re-exports carry symbolic reference-binding evidence, without executing the producer.

The earlier `accessor-function-read` audit expected zero reads on entry to an ordinary function with a reference parameter. That expectation was wrong: when the function creates its `arguments` object, the proposal requires reference values to decay into ordinary values in that object. The original witness must throw its explicit runtime `Error` at its zero-read assertion. A pre-body `StaticTypeError` remains incorrect. An arrow-function control has no own arguments snapshot. A written reference-return annotation also retains its receiving membership check, which can read the referent. Location formation does not cancel either boundary.

| Available direction | Ergonomics / autocomplete | Prior art, including Rust | Real-engine performance | Correctness / liveness | Other and decision |
| --- | --- | --- | --- | --- | --- |
| Treat every reference read as a stable data load | Completion can advertise a stale value and reject valid guards; a wrong purity guess changes diagnostics | Rust's ordinary references have stronger alias guarantees; those guarantees do not cover this proposal's JavaScript getters | Cheap, but permits invalid load reuse | Unsound for accessors and captured writes | Rejected |
| Erase all facts at formation and every read | Unrelated locals lose completion precision and required diagnostics | A conservative fallback is familiar, but Rust does not require blanket loss of unrelated facts | More checks and fewer optimization opportunities; no shape benefit | Conflates formation with consumption and loses proved data-cell precision | Rejected |
| Inspect or execute getters while checking | Completion and diagnostics depend on user effects during analysis | Rust's checking does not run ordinary accessors to learn their outcome | Arbitrary execution cost and shape/inline-cache disturbance | Breaks phase separation and may alter liveness/state | Rejected |
| Remove or lazily defer arguments snapshots and reference-return admission | Makes the old zero-read assertion pass, but changes observable counters, throws and receiving checks | Rust has no JavaScript arguments object; its analogy cannot remove that boundary | Could save reads but changes semantics, including observable getter effects | Contradicts existing receiving rules and failure order | Rejected; correct the audit expectation instead |
| Apply possible read effects at consumption, preserve proved data-cell facts, retain receiving boundaries | Completion uses surviving facts; wrong guesses remain diagnosed where the contract proves them wrong | Rust distinguishes references from referents and offers interior mutability, but its borrowing rules are not this proposal's rules; ECMAScript provides the arguments-object boundary | Compiler-owned origin/effect sets; existing getter calls and IC guards remain; no required user-object fields, shape changes or IC-key changes | Preserves aliasing, source order, admission, initialization and liveness | Recommended independently of work required |

Production engines may lower these effects to dependency invalidation or versions; this interpreter uses its existing flow snapshots. None of this requires invoking a getter during checking or adding runtime reference wrappers.
