# Registered primitive operator signatures across sources

A primitive block registered by an earlier source remains a declaration the checker can use. A later source does not recover the built-in operation merely because its own syntax tree lacks that block. For example, after evaluating `primitive string { operator +(n:uint8):uint8 { return 7; } }`, a later `function f(s:string,n:uint8):string { return s+n; }` has a known incompatible return even if `f` is unused. An untyped operand can still leave dispatch unresolved and retain the existing runtime String conversion.

Retain the defining block and operator identities, fixed operand/result descriptors, declaration environment, private environment and captured enclosing generic substitutions. Instantiate component and metadata captures from the operands, retaining their parameter kinds: a numeric width capture is a value when passed to a builder. A same-spelled alias, builder or generic parameter in the consumer cannot replace an input belonging to the producer. Definitions without value bodies need the same declaration context as definitions with bodies. Registration and activation identity are separate from textual names; this increment does not certify every repeated activation of one declaration.

Use the existing dispatch order: protected plain pairs, receiver block precedence, operand admission and specificity, then built-in fallback. Consider declared operations before numeric-family exclusions. A definition accepting only part of a static operand domain prevents pretending that a broader definition or fallback necessarily wins. An established mismatch of known metadata remains a non-match; it is not a partial literal-domain alternative. An unresolved dependent operand requirement remains unknown. A bare primitive annotation does not establish absent metadata. Keep every possible successful result, and leave a genuinely unresolved result unknown with its runtime checks.

Resolve fixed signatures from their stored descriptors. A required dependent result may run in the existing bounded pre-evaluation fragment, with the producer's environment and the selected capture substitutions. Do not replay the earlier source, execute an ordinary operator body, or borrow the consumer's bindings. Select a uniquely established value definition before requesting its result builder: a losing overload's throwing builder is not a failure of the selected expression. Applicable bodyless contributions retain their existing composition obligations.

A deferred query belongs to the consumer site, registered definition and capture substitutions, with the captured declaration context belonging to that definition. Different determining inputs cannot share a completed answer. Unknown metadata cannot be replaced by defaults to make a query executable. Existing fragment limits apply; this is not completion of the wider portable accounting or cache-validity audit.

A known fixed failure is static; a failure established by required fragment evaluation precedes consumer source-body entry. Deferred evaluation failure and subsequent result assignability failure remain distinct diagnostics. Both successful and abrupt signature evaluation restore lexical, private and generic context. Recovering a type proves no reference permission or liveness, and does not roll back ordinary effects from an earlier source.

## Decision matrix

Required properties: cross-source and same-source contracts agree when inputs are established; producer identity survives shadows; plain-pair and partial-domain alternatives remain possible; only required fragment work runs; failure precedes consumer effects when decidable; runtime boundaries and reference liveness remain independent.

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Production performance, shapes and inline caches | Correctness and liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Ignore registered blocks absent from local syntax | Completion advertises the built-in result although execution selects another; wrong guesses fail downstream | Rust's operator Output belongs to the applicable implementation, not whichever declarations are textually nearby | Cheap local traversal but invalid result assumptions undermine optimized consumers | Contradicts existing dispatch and cross-source checking obligations | Reject |
| Resolve copied annotations in the consumer's environment | Aliases and builders silently change meaning when a caller introduces a name | Rust item/path identity is a limited analogy against textual rebinding; its trait coherence differs from this registry | Cheap lookup; wrong cache sharing across contexts; no shape advantage | Loses declaration and captured generic identity; cannot establish liveness | Reject |
| Replay the producer source or operator body to reconstruct its result | A tooling/type query repeats effects or registration and may throw for unrelated work | Rust const evaluation does not authorize arbitrary JavaScript source replay | Repeated allocation, user calls, shape changes and IC invalidation | Violates phase, availability and effect rules | Reject |
| Leave every registered result permanently unknown | Avoids a false positive but loses useful completion and accepts known bad unused consumers | Rust uses declared RHS/Output contracts; unknown is not a substitute for an available signature | Avoids reconstruction but leaves avoidable runtime checks | Fails required decided judgments; reference checks still needed | Reject |
| Evaluate every matching result builder before ranking | An unused throwing overload breaks a valid operation; adding an overload changes unrelated failures | Rust separates applicable implementation selection from its associated result; exact mechanisms differ | Wasted fragment work and cache entries; no object-layout benefit | Gives losing candidates an observable failure and resource cost | Reject |
| Preserve registered descriptors and producer context; select established candidates and evaluate only required dependent results | Completion describes the selected contract; wrong destinations fail at their source boundary; shadows do not alter meaning | Rust Add's RHS/Output and lexical item paths are useful contract/identity analogies, not adoption of trait coherence or Rust const syntax | Compiler-owned descriptors and dependency-keyed queries; no added user-object fields or shape transitions; ordinary operator lookup invalidation still required | Preserves identity, partial alternatives, phase, restoration and independent liveness | **Choose independently of effort** |

Primary references: [Rust Add](https://doc.rust-lang.org/std/ops/trait.Add.html) and [Rust paths](https://doc.rust-lang.org/reference/paths.html). Rust's statically selected trait implementations are not an open ECMAScript runtime registry.

## Bounded implementation evidence

The focused corpus covers fixed aliases, enclosing generic capture, component-dependent builders, caller shadows, specificity in both declaration orders, ambiguity, mixed numeric operations, bodyless metadata results, failure before consumer effects, losing builders, partial literal alternatives, and protected plain pairs. Script-to-Script, earlier-Script-to-Module and generated Function consumers are covered, with an agent-isolation control.

A prior String conversion test now uses untyped parameters so that it continues to reach the runtime conversion boundary. Its original typed source is retained as a separate required early-error witness; its error is not hidden by changing only an expected value.

This is not full coverage of module dependency registration before graph checking, repeated generic activation of one block declaration, mutable captured inputs, all deferred operand patterns, conversion-dependent metadata composition, or inference publication and resource accounting. Preserve those boundaries and the broader regression backlog.
