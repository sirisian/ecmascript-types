# Composing implicit casts at a bare numeric boundary

A crossing from a bare numeric value into a type constrained by several meta types must select all the required casts before invoking any of them. Each selected body receives the preceding body's admitted raw result. Attach the requested metadata only after the sequence completes, then perform the receiving boundary's validation. A cast for Dimensions alone cannot grant a NumberBounds constraint merely because both occur in the requested type.

```js
type D = { m: int32 };
meta D { default = { m: 0 }; subtype(a, b) { return a.m === b.m; } }
type B = { lo: int32 };
meta B { default = { lo: 0 }; subtype(a, b) { return a.lo === b.lo; } }
primitive float32 {
  operator float32.<D>() { return Number(this) + 1; }
  operator float32.<B>() { return Number(this) * 2; }
}
const source: float32 = 3;
const result: float32.<{ m: 1, lo: 2 }> = source; // 8
```

The old implementation returned after the first body and attached the entire destination, producing 4 here and skipping the second body's effects. The specification's `ConvertParameterization` already advances a single value through its selected casts. This decision makes the bare crossing follow that value-flow model and specifies its selection and ordering. It does not replace the separate subtype, conversion-factor, quantization or source-portion transport rules for crossings between parameterizations.

## Required properties

Every constrained destination owner needs coverage; a completed default portion requires no owner cast. Selection cannot manufacture a different owner's authority. Each selected declaration runs once, including a declaration for the entire concrete destination. The sequence must be deterministic independently of metadata property order and dictionary layout. Every intermediate result must satisfy the actual target base. Destination captures still read the requested destination, receiver captures still read the original source, and closures retain their own invocation bindings. Failure restores temporary state, publishes no result, and preserves effects already performed. Conversion grants no writable location, reference permission or liveness proof.

## Selection and ordering

| Direction | Ergonomics and autocomplete | Prior art, including Rust | Real-engine performance, shapes and inline caches | Correctness and liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Choose greedily while invoking bodies | A missing later cast is discovered after avoidable effects; one matching declaration can conceal an uncovered owner. | Rust and C# determine the conversion before executing its body. | Avoids a small plan but complicates partial failure and specialization. | Cannot establish complete coverage before effects. | Reject. |
| Run every applicable declaration, including overlaps | Adding a specialized declaration applies the conversion twice. Tooling cannot identify one provider for a portion. | Rust coherence and C# best-operator selection favor a determined conversion, not all candidates. | Redundant calls; registry size changes observable cost. | Violates one selected provider per owner. | Reject. |
| Resolve ties by declaration order | A library import can silently switch the chosen provider. | Neither Rust's coherence model nor C# ambiguity rules justifies arbitrary ties. | Cheap, but hides contradictory registrations. | Makes ambiguous coverage appear established. | Reject. |
| Require one unique best provider per owner, then deduplicate selected declarations | A concrete specialization wins predictably; a genuine tie is an error before bodies. Tooling can show each provider and missing owner. | Rust's unique conversion implementation and C#'s most-specific operator are limited analogies. Neither has this proposal's owner decomposition. | Pure descriptor comparisons; a real engine can cache the selected list with declaration-registry guards. No object layout change. | Establishes full coverage without body execution, preserves atomic exact-target coverage and reference rules. | **Choose.** |
| Order selected bodies by destination keys, hash iteration, or lookup buckets | Reordering equivalent metadata or changing a declaration's spelling can change the result. | Rust explicit calls have visible sequence; C# has no implicit chain to order. | Convenient implementation iteration, but not a stable semantic input. | Equivalent metadata must not supply different sequences. | Reject. |
| Require commutativity or sort by textual owner names | Commutativity is undecidable for ordinary JavaScript bodies; renaming is not a sensible conversion control. Symbols and imports complicate textual order. | Neither Rust nor C# infers algebraic laws for arbitrary conversion bodies. | Proof or dynamic comparison costs cannot establish general equivalence. | Running bodies to compare outcomes repeats effects. | Reject. |
| Use selected declarations' established declaration order | The author can see the sequence; changing declaration order deliberately changes noncommuting transforms. Imports retain their declaration-establishment order. | Closest to explicit Rust call order, although this sequence is implicit and therefore less visible. | A retained ordinal produces a stable short list; no per-value property reads or shape transitions. | Deterministic across metadata spellings; executes each selected declaration once. | **Choose.** The import-order sensitivity is a real tradeoff; libraries should use identity or commuting casts where order should not matter. |

Selection keeps the numeric lookup precedence explicit and applies it independently for each owner. For a bare Number source, first consult `primitive number`; then consult the destination's fixed primitive and then its family. Other supported bare numeric sources start with the destination's fixed primitive and then its family. In the first level with coverage for an owner, an exact whole-target declaration is more specific than a meta-type-wide declaration; equal candidates are ambiguous. An exact target covers only that complete target, not another target with extra fields. A whole-target declaration selected for several owners is invoked once. It is atomic coverage: if lookup would combine it with another selected provider, the plan is ambiguous. Do not slice that body into a contribution for only the otherwise-uncovered owners. Running the overlapping whole-target body would perform work already supplied by the other provider; globally preferring it would discard lookup precedence. Rejecting that conflicting plan preserves both rules and makes the missing explicit composition visible, with only a descriptor-overlap check and no shape or liveness change. Rust coherence and C# ambiguity are limited analogies for rejecting an undetermined provider; neither defines this owner protocol. Distinct selected declarations execute in their original establishment order across lookup levels, not in the order those levels were searched.

Preparation of the same declaration in the same lexical environment by checking and evaluation is not a second candidate. Retain its original position and closure. Distinct declarations remain distinct even when their text is identical. A statically established missing or ambiguous plan is a type error at the existing checking boundary; a runtime failure is a TypeError before cast-body entry. Selection never runs a body to discover its applicability. A bare annotation alone does not prove the supplied value carries no metadata; retain the existing rule that such a value may already carry the destination constraint.

## Implementation and remaining work

The interpreter shares a pure bare-cast planner between literal checking and runtime dispatch, retains declaration/environment identity and order, binds each selected body's captures, and threads the raw checked value. Its portable `implicit-cast-composition.json` corpus covers coverage, specificity, order, effects, captures and closures, raw failures, final validation, defaults, ordinary boundaries, imports and object-represented numeric families. The delivery verification records the exact counts and baseline observations.

This increment is the bare-numeric composition repair. The separate `ConvertParameterization` implementation still lacks its specified missing-owner cast arm; audit that path with subtype admission, factors, quantization and transported source portions together. It must not be approximated by sending an already-parameterized source through this bare planner. Broader cast applicability, nested patterns/vector dispatch, imported-constructor `instanceof`, hook effects and wider conformance gates remain open.

Rust's `From` is expected to be infallible and does not define general implicit user casts; this proposal's checked boundaries can fail. C# permits at most one user-defined conversion operator in a conversion, so it is evidence for selection and ambiguity, not this composition model.
