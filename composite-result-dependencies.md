# Dependent contracts for named object properties

An inferred object boundary retains the identity supplied independently for each contributing property. After `const holder = { result: choose(flag) }`, the ordinary admission of `holder` must complete its unresolved nominal member using the selected invocation's checked result. Two properties may contain values from two activations of the same local class declaration. Their concrete constructors remain distinct.

The checked object view and the backing object are separate. A conforming plain object stays ordinary mutable storage. Mutation through an alias can change its data, but cannot change the already established view's nominal target. A later receiving boundary checks the value it actually obtains against that target. Checking the view does not freeze the object, make its properties readonly, or exempt subsequent reads from reference-liveness checks.

## Requirements and decision

Use an independently established target, preserve per-property and per-activation identity, keep written and erased contracts authoritative, and retain ordinary evaluation and failure order. Do not derive a target from the value being checked, replay an expression, add getter reads or key conversions, or modify a shared symbolic publication. A failed initialization must leave its binding uninitialized. Already initialized bindings and prior effects remain. No inferred check promotes an already conforming plain object into invariant typed storage.

## Contribution order and checked reads

A fresh object's evidence comes from its evaluated source contributions. A later literal definition or copied contribution for the same key replaces the earlier one. In particular, a later method or accessor cannot inherit a preceding data initializer's dependency. This ordering follows ordinary evaluation, including computed keys; it does not evaluate a key twice.

An arbitrary backing mutation by a decorator is not a new type-source contribution. It does not retarget the initializer's obligation. Complete the private target from the source evidence, then apply ordinary admission to the resulting object after the decorator. If admission reads a decorator-installed getter, it reads it only as required by that ordinary check. A construction ledger is one implementation strategy; scanning the final descriptors is insufficient because the decorator may already have replaced them.

Once admitted, an immutable binding retains its checked object view. A public member read, keyed binding pattern or ordinary copy projects the applicable named property contract after its ordinary read. Nested object views project recursively. Written member `any` clears stronger backing evidence. An entry absent from that view supplies no replacement target; for example, fresh accessors excluded from eager inferred admission can supply the checked result of the later getter call. Selected defaults supply their own result contribution.

This does not establish a structural type where the existing static rules leave one unknown. Arbitrary object spread and object rest do not prove that structural properties are own and enumerable; the checker retains a collected shape only where its separate rules establish one. A dynamic `any` key likewise does not establish a particular inferred member target. Retaining evidence must not introduce an otherwise absent admission boundary.

## Bounded implementation and remaining cases

The interpreter completes nongeneric local ClassDeclaration leaves through named object-property paths, including nested objects and established String or Symbol keys. It retains checked object views on contributing completions and successfully initialized ordinary immutable bindings, with private reference metadata until the ordinary public key conversion and read finish. Memoization keys both the symbolic target and contributing evidence. It does not mutate the shared symbolic type graph.

This closes the two previously recorded whole-object initialization failures and covers distinct activations, copies, keyed patterns, fresh rest, duplicate properties, getter replacement, decorators, erasure, failed state and ordinary mutable storage. Generic nominal leaves, other composite kinds, index signatures, general mutable bindings, optional access and resumable/wrapper paths still need their own coverage. No global identity or convergence gate is declared complete.

A separate probe using a freshly created `Symbol("p")` key still fails object admission, whereas the established well-known `Symbol.iterator` key succeeds. Its failure is present on the pulled base. The next investigation must track the key's lexical identity through checking and evaluation, rather than infer identity from a Symbol's description or erase the property obligation. The runtime property-path machinery supports Symbol identities; it does not make the checker's separately created Symbol identical to the evaluated key.
