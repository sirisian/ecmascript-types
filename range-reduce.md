# Range reduction and accumulator contracts

A range's `reduce` forwards to a fresh forward numeric iterator. Its callback takes `(accumulator: U, value: I, index: uint64) => U`, and its normal result is `U`. `I` is the cursor item contribution from [range-iterator-results.md](range-iterator-results.md), not automatically the endpoint type. The same recurrence applies to established helper-bearing synchronous iterators; structural iteration interfaces do not acquire helper methods.

Without an initial argument, `U` is `I`: the first item seeds the accumulator and subsequent callbacks start at index 1. With an initial argument, callbacks start at index 0. Supplying `undefined` counts as supplying an initial argument. An empty traversal returns a supplied initial value without calling the callback; without one it throws. An absent or positive-infinite range stop retains the existing refusal before iterator acquisition.

## Choosing one recurrence

With an initial argument, a fresh callback's written, non-`any` first parameter type anchors `U`. An existing callback with one established nongeneric signature can provide the same anchor. A wider union deliberately written there is a valid accumulator contract: an initial String and subsequent Boolean can both inhabit `string | boolean`. Use the contract for the first supplied argument: a fixed first tuple-rest position or homogeneous array-rest element can supply it, not the rest collection itself. An unresolved leading rest distribution supplies no anchor. Optional/default inputs include `undefined` before their binding initializer; an empty reduction can return that initial `undefined` without invoking the default. A callback with ignored parameters contributes no first-parameter anchor.

Otherwise, derive `U` from the initial value with ordinary binding widening and reference-value decay. A receiving result context can provide ordinary numeric-literal adoption; it does not erase or override a known incompatible initial type. A written `any` input does not erase an independently known initial type. Unknown contributions remain gradual. An unresolved spread whose argument count or routing determines whether an initial value is present does not select either recurrence by guesswork.

Check the initial value, callback inputs, known callback results and completed reduction against the selected contract. A callback result does not widen the recurrence to make an error pass. A fresh literal adopts independent item/index inputs and the accumulator context through the ordinary contextual-function rules. Written parameter and return annotations take precedence. An existing callback is not retroactively reannotated.

## Admission, effects and gradual callbacks

A fresh callback's adopted binding and return contracts are real runtime obligations, including calls made later by a replacement method that saved the callback. The callback retains its identity. Explicit `any` positions and already created uncontextualized callbacks retain their declaration's gradual behavior. The `uint64` index is admitted at the callback binding; producers are not globally retagged.

An explicit `any` callback result defers the produced-value check while retaining its known parameter obligations. If another iteration occurs, a typed accumulator binding checks the next entry. A required final receiving binding or function return checks the completed result, including the empty-initial path and incompatible method replacements. A discarded result introduces no new receiving boundary. Likewise, an empty reduction does not invoke a callback to validate an unknown initial value. These rules preserve existing declaration provenance rather than adding hidden checks inside the untyped intrinsic algorithm.

| Direction | Ergonomics / autocomplete / wrong guesses | Prior art | Real-engine performance | Correctness / reference liveness | Other / decision |
|---|---|---|---|---|---|
| Wrap or rewrite every callback and check every intrinsic accumulator store | Appears uniform but changes identity or retroactively strengthens explicitly gradual declarations; discarded results can gain effects. | Rust's statically typed closure is not a JavaScript wrapper and has no `any` escape. | Adds allocation/call IC variants or requires new intrinsic call metadata; structural admission can read getters repeatedly. | Changes effects and declaration provenance; cannot justify extra reference authority. | **Reject for this increment's contract.** A broader change would need its own design. |
| Trust the member spelling and omit receiving checks | Fast-looking direct calls fail after replacement; tools promise an invalid result. | Mutable ECMAScript lookup is unlike Rust's statically selected trait implementation. | Unguarded elision breaks under property/IC changes. | Unsound for replacement and failed initialization. | **Reject.** |
| Use ordinary adopted declarations and required receiving boundaries | Known contracts are enforced where declared; explicit gradual escapes retain their cost at the next typed use. | Rust motivates a fixed recurrence; ECMAScript supplies the effect order and mutable method identity. | Reuses existing admission with valid elision guards, no compulsory wrapper or public shape change. | Preserves callback identity, prior effects, failed-binding TDZ and reference-liveness rules. | **Recommend.** Checking itself executes no callback, getter, default or iterator. |

## Member views and scope

Direct, established computed, optional and extracted method views carry the same call-dependent recurrence. Each invocation selects its own accumulator; extracting a method does not bind `this`. Symbolic item types survive ordinary generic substitution. Mutable bindings obey the existing stability rules. A whole `any` receiver or an unrelated user-defined method with the same name does not gain this contract.

This is an operation contribution, not a new public generic callable capability or proof of intrinsic identity. Named intrinsic argument routing, explicit generic invocation, general `bind`/`apply` transport, async helper semantics and the range's default `Symbol.iterator` static view remain separate. `take` and `drop` remain range-returning algebraic adapters. No iterator traversal is used to establish a type or to extend a reference's lifetime.

Primary references: [Rust Iterator::fold and reduce](https://doc.rust-lang.org/std/iter/trait.Iterator.html#method.fold) and [ECMAScript Iterator.prototype.reduce](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-iterator.prototype.reduce). Performance statements are design analysis, not benchmarks.
