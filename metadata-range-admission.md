# Metadata range endpoints and special carriers

A Range value is not proof that every endpoint belongs to the closed metadata language. Ordinary ranges may have class-valued ordered endpoints. Metadata ranges require each present endpoint to be an admitted metadata atom: a supported scalar or numeric value, with the ordinary range's ordering requirements still in force. A range wrapper cannot carry a live class instance, container or unsupported object into a canonical type. This rule does not restrict ordinary ranges outside metadata and does not replace endpoint normalization or the declared constraint-shape check.

Validate actual endpoint values before publishing the structural range marker. Snapshot the start before the end, using the range's internal data; do not call public getters, coercion or an ordering operator for admission. Omitted endpoints remain absent. Each present endpoint pays a value-visit charge, and completing the range pays a container-completion charge under the enclosing snapshot budget. A written range is subject to the same atom admission; pending source dependencies remain pending under the existing checking rules.

Composite and Span values are distinct language kinds. A Composite record or tuple is not an ordinary metadata record or list merely because this interpreter stores it using an Object or Array. A Span is a view over storage, not an owning Array input. Reject these kinds at the metadata snapshot boundary before reading their entries, at the root or at any nested position. Prototype replacement, freezing, an empty payload and a base-form meta declaration do not change admission. Check internal kind evidence regardless of whether the engine stores it in slots, tagged values or side tables.

Explicitly projecting admitted contents to an ordinary record or Array remains available, for example `{...composite}` or `[...span]` before metadata construction. Those ordinary inputs still undergo complete recursive admission. The projection does not certify nested class instances, undefined values or unsupported values. Typed owning Arrays remain list inputs; ordinary frozen and null-prototype records remain record inputs.

## Endpoint directions

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art, including Rust | Production performance, shapes and ICs | Correctness and reference liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Trust any built-in Range wrapper | Completion exposes endpoints whose mutable state can silently affect an interned type; wrong guesses survive construction | Rust Range stores generic endpoints; its wrapper alone does not establish constant eligibility, immutability or structural identity | Cheapest initial check, but invalid cache dependencies and hidden object identity | Bypasses the closed language and retains live references inside canonical metadata | Reject |
| Copy arbitrary endpoint object properties, or call a coercion | Ordered endpoint methods and declared types disappear; getters or conversions make errors origin-dependent | Rust structural values do not justify arbitrary JavaScript object erasure or coercion | Extra user calls, allocations and shape/IC dependencies; no stable determining inputs | Changes endpoint meaning, effects and identity; does not prove liveness | Reject |
| Restrict all ordinary ranges to metadata-compatible endpoints | Useful class-valued ranges fail outside type metadata and editor suggestions become misleading | Rust Range is generic; range representation and admissible constant values are separate questions | Simple global restriction, no inherent object-layout gain | Breaks the existing ordered-endpoint range contract | Reject |
| Admit metadata ranges only after present endpoints pass atom admission | Invalid payloads fail at construction; ordinary range methods and valid metadata atoms keep their expected behavior | Rust's generic Range and separate const rules provide a limited architectural analogy; this proposal defines its own value language | Fixed two-slot kind checks; existing worklist/meter, no user-object fields or shape changes | Prevents live-object smuggling; preserves values, order, missing endpoints, phase and independent reference liveness | Recommend independently of effort |

## Composite and Span directions

| Direction | Ergonomics, autocomplete and wrong guesses | Prior art, including Rust | Production performance, shapes and ICs | Correctness and reference liveness | Other / decision |
| --- | --- | --- | --- | --- | --- |
| Treat every ordinary interpreter carrier as a record or list | A storage implementation detail controls which values autocomplete can safely suggest; a view may become an empty/different record | Rust representation does not erase semantic type distinctions; ECMAScript ordinary-object tests alone cannot classify extension values | Cheap but accepts different domains across engines using different layouts | Kind erasure violates origin independence; a view's backing/liveness contract is not a record contract | Reject |
| Explicitly add Composite and Span as metadata kinds, or implicitly convert them | Convenient direct use, but users must learn whether reflection preserves a Composite/view or yields a record/list | Rust const aggregates and borrowed slices motivate considering support, but Rust has no equivalent runtime metadata interning contract | Could be optimized, but needs specified equality, materialization, backing snapshot and invalidation rules, not just a kind check | Composite equality/typed shapes and Span extent/backing differ from metadata record/list identity; implicit erasure loses those contracts | Reject for this closed language; any future extension must define the complete semantics |
| Reject all aggregates or require literal syntax | Prevents useful builders, reflection and valid owning Arrays; needless rewriting | Rust const aggregate construction supplies no reason for a literal-only restriction | Easy rejection removes useful specialization, with no necessary shape benefit | Contradicts existing record/list metadata forms | Reject |
| Reject unsupported semantic kinds and permit explicit projection into supported inputs | Direct errors identify the unsupported input; ordinary record/Array completions accurately describe accepted forms; explicit copying makes the cost and loss of kind visible | Rust distinguishes owned values and views; the analogy is limited, while this proposal controls admission and snapshot effects | Constant-time internal-kind checks, then existing traversal; side tables or engine tags do not alter user shapes/ICs | Preserves the closed domain and all recursive checks; no new reference permission or lifetime extension follows | Recommend independently of implementation effort |

## Scope

Cover defaults, builders, reflection, written range projection, nested records/lists, missing endpoints, explicit projections, typed owning Arrays, failure recovery, Modules, and snapshot resource limits. Keep class-valued ordinary ranges as positive controls. This increment does not close host-base endpoint normalization, all special carrier kinds, deep downstream traversal, general effect-dependent availability or portable evaluation/cache accounting.

Primary comparisons: [Rust Range](https://doc.rust-lang.org/std/ops/struct.Range.html), [Rust constant evaluation](https://doc.rust-lang.org/reference/const_eval.html). Rust's supported constant forms and generic range behavior are not imported as this proposal's admission rules.
