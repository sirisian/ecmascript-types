# Static results of range derivation

The normal result of `r.scale(factor)`, `r.take(count)`, `r.drop(count)` and unary `-r` has the view `RangeBounds<T>` when the built-in receiver has endpoint domain `T`. Built-in binary `+`, `-`, `*` and `/` contribute that view when both operands establish the same domain. This retains complete numeric metadata, type parameters and declaration identity. It does not evaluate endpoints or prove normal completion. The actual result still has the concrete shape produced by the runtime algorithm.

This is the result-contract increment following [range-properties.md](range-properties.md). Parameter admission, heterogeneous intersection and iterator contributions are distinct judgments. Existing runtime domain validation, overflow, metadata admission, method lookup and reference liveness remain required.

## Required outcomes

An unused function with `r: ClosedRange<uint8>` must reject `const x: string = r.take(2).start`, just as it rejects that annotation on `r.start`. It must not assume a computed range is still closed, two-ended, or even bounded. Dot access, established computed keys, finite key domains, optional chains, extracted methods and receiver unions use the same return contract. An unannotated parameter remains gradual.

A result's `start` and `end` therefore have `T | undefined` under the ordinary RangeBounds property table. Autocomplete can offer the range operations and domain while advertising possible endpoint absence. An explicit annotation can require a more precise view only when the ordinary checking rules establish it; the runtime object's reflection continues to expose its actual shape.

## Result shape

| Direction | Ergonomics / autocomplete / wrong guess | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |

| Leave all derived results unknown | Calls run, but chains lose autocomplete and wrong annotations wait for execution. | Rust's typed adapters retain their item type; its ranges are not untyped results. | Loses useful downstream facts without simplifying runtime layouts. | Fails the stated normal-result contract. | **Reject.** |
| Copy the receiver's concrete shape and bounds | Pleasant chaining until a zero/negative factor or singular divisor contradicts it. | Rust's concrete range types distinguish shapes, but it has no built-in interval arithmetic with these shape changes. | Unsound specialization can remove necessary absence/shape guards. | Scale can swap one-ended shapes or produce a point; division can produce full. | **Reject.** |
| Publish a value-dependent union of every possible precise shape | More precision in some cases, but autocomplete and annotations depend on factor, count, emptiness and domain proofs. | Rust's iterator adapter types express their own operation, not these runtime-dependent interval shapes. | Larger type joins and caches; runtime shape guards are still needed. | Can be sound with complete proofs but supplies a new dependent result contract beyond the existing API. No liveness advantage. | **Reject as the public contract.** Engines may independently prove more precise runtime facts for optimization. |
| Publish `RangeBounds<T>` and preserve actual runtime shape | Predictable signature and domain-aware chaining; endpoint absence must be handled explicitly. | Rust RangeBounds abstracts concrete shapes while retaining its endpoint type. Its Bound wrappers and borrowing API differ from this proposal's properties. | Constant-size result view; no new allocation/layout beyond the existing result. This choice is about the declared API, not implementation effort. `take` and `drop` are range-returning adapters here. Rust's Iterator `take`/`skip` return iterator adapters; copying those results would erase this proposal's reusable interval contract. Likewise `step` and `reverse` return iterators here, and must not acquire RangeBounds merely because their receiver is a range. Kotlin IntRange is a discrete Int progression; it is not an analogy for arbitrary coordinate interval arithmetic.

## Binary endpoint agreement and erasure

| Direction | Ergonomics / autocomplete / wrong guess | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Promote to Number, strip metadata, or join disagreeing domains as a new carrier | Convenient-looking expression, but changes exactness or makes incompatible domains look compatible. | Rust requires explicit numeric conversions and does not define a range promotion lattice. | Conversion and polymorphic-domain guards; unnecessary new cache identities. | Contradicts the one identical full domain required by coordinate arithmetic. | **Reject.** |
| Use the left domain even when an erased left supplies no domain | Simple rule but loses the right operand's useful contract. | Rust does not have JavaScript's `any`; its operand constraints cannot decide erasure policy here. | Cheap but discards facts already required for normal completion. | Safe only as a weak `any` view, not a faithful common-domain contribution. | **Reject.** |
| Refuse any result contribution as soon as either endpoint is erased | Predictable conservatism but loses safe information in `RangeBounds<any> + RangeBounds<uint8>`. | Rust's absence of `any` again limits the analogy. | Leaves more downstream checks without changing object shapes. | Stronger than necessary: a normal result must agree with the known operand. | **Reject.** |
| Keep equal complete domains; let endpoint `any` contribute the other's domain; otherwise retain gradual result checking | Stable autocomplete when agreement is known, no guessed conversion when it is not. | Comparable to preserving a chosen typed operand contract, with erasure handling specific to this proposal. | Existing identity comparison and union machinery; no endpoint reads or new runtime layout. | Runtime validates both stored domains and all endpoints before shortcuts. Any contribution does not waive that check. | **Recommend.** |

Both erased endpoints yield `RangeBounds<any>`. A whole operand of unknown/any type is different: it does not establish built-in range dispatch, so this rule contributes no result type. If two known domains differ, this result rule contributes no common domain; it does not define a new early-error policy or authorize an implicit union/promotion. Existing admission and runtime failure rules still apply. A symbolic type parameter equal to itself retains its identity; two different parameters are not unified merely because a call might later supply the same type.

For union operands, apply the contribution to every alternative pair and join only if every pair contributes. A non-range, unknown, cyclic or otherwise unresolved alternative prevents a complete result proof. The implementation memoizes pairs within one query; it neither executes type expressions nor installs a persistent cross-source cache. This is a normal-result judgment, not path-sensitive inference of which operand values will pass the runtime domain checks.

## Parameters and operation availability

A known return contract and successful invocation are different facts. The normative numeric operation clauses already describe admitted counts, factors, endpoint families and failure order. Do not replace them with an index-type count, an endpoint-typed factor, or a small fixed union that excludes supported wide integers, decimals or rationals. Do not coerce an argument to make it fit a convenient signature.

| Direction | Ergonomics / autocomplete / wrong guess | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Reuse iterator `take(index)` or require factor `T` | Familiar signatures, but wrong guesses about accepted counts/factors become breaking rejections or conversions. | Rust `take(usize)` belongs to its iterator contract; it does not define this proposal's numeric count policy. | Cheap signatures at the cost of incorrect boundaries. | Excludes existing accepted domains and may coerce values before required validation. | **Reject.** |

| Keep runtime argument validation while independently publishing the result view | Result chains become useful immediately; invalid numeric arguments retain their specified runtime errors. | Rust shows the value of separate item/result and input constraints, but lacks this gradual boundary. | Adds static return information with no new coercions or runtime layouts. | Preserves existing evaluation order and admitted domains. | **Recommend for this increment.** Complete static capability/parameter admission remains a follow-up, not a claim closed here. |

The proof of concept represents the single factor/count position as gradual in this result-only signature. That does not make arbitrary values valid factors or counts. The stale closed factor union in the overview sketch is replaced by a generic factor position governed by the numeric scaling clause. Generic and class endpoint identities may appear in a result contract without granting custom scalar operators an enclosure implementation. Runtime unsupported-domain rejection remains in force.

## Replacement, effects and reference liveness

Assuming that a static method signature proves the current implementation is rejected: JavaScript permits own-property and prototype replacement. Sealing the prototype or bypassing ordinary lookup is also rejected, because it changes reflection and effects. Retain receiving and return checks unless an independent stability proof establishes the actual method. Rust's statically selected implementations do not model JavaScript's replaceable method properties; a production engine can use guarded ICs and deoptimization without changing this API or its shape layout.

Evaluate the receiver, method lookup, arguments and call in their ordinary order. A bad replacement result must fail before initializing an inferred typed binding; prior effects remain and the failed binding remains uninitialized. Extraction does not bind `this`, optional short-circuiting suppresses the call and arguments, and stale references still fail when read. Built-in operator results remain subject to their own domain validation and admission; declared operators dispatch first and retain their declared return contracts. The result judgment itself calls no getter, iterator, comparison or metadata hook and grants no borrow authority.

## Completed admission must remain recognizable

The bounded regression run exposed a runtime defect as soon as result inference introduced an inferred binding boundary. A metadata validator can admit a manufactured bare numeric endpoint without changing its representation or attaching its parameterization. The range carried `T`, but its endpoints still reported the base type. An inferred receiving check ran validation again, and a subsequent binary range operation rejected the endpoint/domain disagreement. An explicit receiving annotation could elide that check and hide the inconsistency.

| Direction | Ergonomics / autocomplete / wrong guess | Prior art, including Rust | Production performance, shapes and ICs | Correctness and liveness | Other / decision |
|---|---|---|---|---|---|
| Change tests to accept repeated validation | Existing programs gain extra effects and potentially fail after a successful operation. | Rust typed values retain their type; it has no comparable dynamic validator replay. | Extra hooks at every inferred boundary. | Does not repair reflected identity or subsequent arithmetic failure. | **Reject.** |
| Skip receiving checks whenever the static return is a range | Hides duplicate hooks on intrinsic calls, but trusts replacement methods returning arbitrary values. | Rust's fixed dispatch does not justify skipping JavaScript property checks. | Removes essential guards without a stability proof. | Reopens the replacement-method admission bug. | **Reject.** |
| Trust only the range's domain tag and ignore endpoint types | Avoids some repeated checks but leaves endpoints reflecting the wrong domain and breaks later per-endpoint checks. | A typed container contract is not a reason to misreport its elements. | Fewer checks, inconsistent specialization keys. | Conceals the manufactured endpoint defect and widens the trust surface. | **Reject.** |
| After successful full admission and representation checks, carry the admitted domain on each manufactured endpoint | Reflection and subsequent arithmetic agree with the returned range; hooks run only for the new endpoint admission. | Rust retains a constructed value's chosen type. Dynamic metadata admission is proposal-specific. | Existing primitive/family carriers; no extra hook or public property, and constant work per new endpoint. | Preserves numeric value, zero sign, decimal cohort, admission failures and liveness. | **Recommend.** |

The shared endpoint admission helper now retains that full domain after success for scaling, arithmetic and adapter cuts. It neither mutates source endpoints nor weakens validation. Identity and empty copies retain their existing no-readmission rule. Binary128's carried-type query recognizes its existing TypeRecord, as the decimal and rational queries already do, so receiving checks and reflection agree. This correction preserves the existing hook-order tests unchanged and adds endpoint-reflection and chained-arithmetic regressions.
